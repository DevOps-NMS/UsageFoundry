# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js 15 (App Router) app that (a) reads Claude Code's local session transcripts to show subscription usage against 5-hour / weekly windows, and (b) runs Claude Code headlessly against a mounted folder, stopping between iterations when a budget guard trips. Ships as a single Docker container. `README.md` explains the domain reasoning in depth — read it before changing anything in `src/lib/`.

## Environment gotchas

- The app reads `WORKSPACE_ROOTS` (multiple mounts, `Label=/path` entries joined by `|`) and falls back to the single `WORKSPACE_ROOT` when it is unset. `.env` / `.env.example` define `UF_WORKSPACE`, `UF_WORKSPACE_N` and `UF_WORKSPACE_N_NAME`, which are **only** consumed by `docker-compose.yml` — to pick the host mounts and to compose `WORKSPACE_ROOTS`. Running `npm run dev` without either set falls back to `~/workspace`, so `/api/folders` will look empty even though `.env` names a directory.
- An entry in `WORKSPACE_ROOTS` with an *explicitly empty* label (`=/workspace2`) is **skipped**, while a bare path (`/workspace2`) is labelled from its basename. That asymmetry is load-bearing: compose cannot omit a volume conditionally, so all four slots are always mounted and an unset `UF_WORKSPACE_N_NAME` is what switches a slot off. Adding a workspace must stay an `.env` edit, not a compose edit.
- `CLAUDE_HOME` (default `~/.claude`) determines which transcripts are parsed; `DATA_DIR` (default `./.data`) holds the SQLite file.
- `UF_AUTH_TOKEN` blank disables auth entirely. `ANTHROPIC_ADMIN_KEY` blank leaves the API-account page in an explicit "not configured" state rather than showing zeros.
- `UF_GITHUB_TOKEN` blank means runs cannot use GitHub at all, and the Settings header says so — the failure otherwise arrives mid-run, inside a tool call nothing here reads. The `UF_` prefix is load-bearing rather than cosmetic: `gitEnv()` and `reviewEnv()` strip that namespace, so the token is withheld from every child except the one `githubEnv()` hands it to.
- All process-level config is centralised in `src/lib/config.ts` and fixed at boot. User-editable values belong in the settings table (`src/lib/settings.ts`), not here.
- `UF_WORKSPACE` and `HOME` use compose's `${VAR:?message}` form, so a missing one aborts `docker compose up` instead of substituting. Both previously had defaults, and both failure modes were silent: Docker *creates* a bind source it is handed, so a wrong path yields an empty folder picker and a dashboard of zeros — indistinguishable from a quiet week. Do not restore a default to either. `UF_WORKSPACE_2..4` still fall back to `UF_WORKSPACE`, which is what keeps all four slots mountable.
- `user: "${UF_UID:-1000}:${UF_GID:-1000}"` in compose exists because the container writes to both bind mounts. macOS Docker Desktop remaps bind-mount ownership onto the container user, which is why uid 1000 was never questioned; Linux preserves the host uid and a mismatch breaks `/login`, transcript writes, and `.uf-worktrees` creation. The image still sets `HOME`, `DATA_DIR`, `CLAUDE_HOME` and `CLAUDE_CONFIG_DIR` explicitly — required, because a uid with no `/etc/passwd` entry makes `os.homedir()` unreliable.
- The image carries `gh` (`ARG GH_CLI_VERSION`, checksum-verified release tarball rather than an apt source) for the same reason it carries a compiler: an agent asked to open a pull request finds out `gh` is missing halfway through a cycle, inside a tool call, and works around it badly. It is credentialed only by `githubEnv()`, never by a config file in the image — nothing about the image knows a token.
- The image pins `@anthropic-ai/claude-code` (`ARG CLAUDE_CLI_VERSION`) and sets a system-wide git identity. The pin protects a reverse-engineered contract: the `stream-json` parser and the OTLP shapes were captured from one build, and both degrade *quietly* when it moves — an unparsed line becomes a log entry, a missing `result` event understates spend. The identity is not cosmetic: a container hostname has no domain, so git rejects its own auto-detected address under the strict ident every commit uses, and an isolated run — whose preamble orders it to commit — ends with an empty branch.

## Architecture

**Three** data sources now, still **never summed or mixed in the UI**. The third is Claude Code's own OTLP export (`otlp.ts` → `otlp_requests`), gated on `settings.telemetryForRuns` with one exception below, covering only runs this app spawns. It is first-party per-request cost — no price table, no dedupe key, no file polling — and it is the only way to account for a work cycle killed before the CLI's `result` event. It renders as its own card on the run page and its own card on the dashboard, and must never reach `buildSnapshot()` or `runs.spent_usd`. It reaches a budget decision through exactly one door — `telemetrySpendSince` → a `*Guard*` figure — and that door is narrow on purpose: one run, one cycle, the guard half of a split whose display half stays transcript- and `result`-derived. Two callers go through it and no more: a live run's own spending limit via `RunProgress.spentGuardUSD`, described under the enforcement modes below, and a workflow instance's own budget via `instanceSpend` → `InstanceProgress.spentGuardUSD`, which reads each `running` member's current cycle bounded by `runs.active_started_at`. Same bound, same destination, and neither ever reaches `runs.spent_usd`. It cannot replace transcripts: no backfill, no `cwd`, and `cache_creation_tokens` collapses the 5m/1h split. Wire details were captured from a live CLI, not read from the docs — the docs' `claude_code.api_request` is the record *body*, while `event.name` is the bare `api_request`, and `OTEL_RESOURCE_ATTRIBUTES` lands on both the resource and each record. The payload carries `user.email` and account UUIDs; the parser drops them and the schema has no column for them. `request_id` is the primary key because OTLP delivery is at-least-once, and the ingest route always answers 200 — a batch exporter retries failures, so rejecting a malformed record would cost that batch on a loop.

The two original sources:

| Source | `~/.claude/projects/**/*.jsonl` | Anthropic Admin API |
| Code | `transcripts.ts` → `windows.ts` | `adminApi.ts` |

**Four kinds of child process, from four modules, and no more.** `git.ts` holds the git primitives (`gitSync` for the admission decision, `git` for everything else); `orchestrator.ts` spawns the agent; `review.ts` spawns the one-shot invocations that are not work cycles — a review, or a conflict resolution (`run_reviews.kind`); `chat.ts` spawns the orchestrator chat. All go through an argv array and never a shell. A workflow's orchestrator block is **not a fifth kind**: it is the fourth one invoked without a thread, through `runOrchestratorChild` — the same argv, the same environment, the same capability token, the same MCP config file. That function exists rather than a second `spawn` call site precisely because two of those would be two sets of flags to keep in step, and the flags are what bound the child; what differs between the two callers is a subject, a system prompt and a cwd. The review spawn was the deliberate third and differs from the agent in every way that matters: it is never automatic, it runs `--permission-mode plan` so it cannot write, its cost lands in `run_reviews` and never in `runs.spent_usd`, and it gets no telemetry env even when `telemetryForRuns` is on — `otlp_requests.run_id` is compared against the run's own spend, and a review's requests in that comparison would make an accounted-for run look unaccounted-for. Adding a fifth kind is a decision, not a detail. A **specialised agent** is not one either, and is not a sub-kind of one: `--agents` is a flag all three spawning modules may carry, offering the delegating model a role it may hand a subtask to, and the delegated turn happens *inside* the child that already exists — same process, same permission mode, same allow and deny lists, same cost destination. Three modules, four callers, and only two of the four hand one over today: a work cycle carries the run's own frozen copy and an orchestrator block carries its node's, while `runTurn` withholds one deliberately (see the chat invariant below) and `spawnAssist` takes the argument and has no caller that supplies one — a review is never given a specialist, and nothing about the flag decided that. There is one encoder for it (`agentsFlagValue`) rather than one per site, for the reason that paragraph gives about `runOrchestratorChild`: several copies of a shape the CLI drops in silence would be several sets of flags to keep in step, and nothing would report the drift. "Drops" rather than "rejects" is the whole of why the encoder is worth having — a malformed member costs a run its specialist at exit 0, with nothing on stderr and nothing in the stream.

`orchestrator.ts`'s loop calls `currentSnapshot()` (a fresh transcript scan) *before every iteration*, evaluates the budget, then spawns one `claude -p … --output-format stream-json --verbose` child in the run's working directory. Iteration 2+ uses `settings.continuationPrompt` and `--resume <sessionId>`; the run ends on `DONE`, the iteration cap, a guard, or a non-zero exit.

Several runs can be in flight at once. `createRun` admits a run or leaves it `queued`; `promoteQueued()` starts whatever is startable, and is called after creation and again in `startRun`'s `finally`. A run on a git repository defaults to its own worktree (`work_dir` ≠ `folder`), which is what lets two runs share a project; a run anywhere else takes the folder exclusively.

Events flow: `emit()` writes to `run_events` **and** publishes on a `globalThis` EventEmitter → `/api/runs/[id]/stream` replays persisted history first (honouring `Last-Event-ID`), then tails live. Persist-then-publish is what makes reconnect and late page loads lossless — keep that order.

## Invariants — these encode the product's reasoning, not style preferences

**Unknown must not render as zero.** Anthropic publishes no numeric value for a Pro/Max limit, so ceilings default to `null`. A `null` fraction renders as a hatched indeterminate meter ("no ceiling set"), never an empty 0% bar. Do not add default numeric ceilings to `DEFAULTS` in `settings.ts`.

**…but the *percentage* is readable, and it outranks anything derived from a ceiling.** `planUsage.ts` reads `GET /api/oauth/usage` with the OAuth token in `.credentials.json` — the same figure `claude /usage` and claude.ai print, for the whole account rather than for the transcripts on this disk. `WindowState.fraction` prefers it, then the cost ceiling, then tokens; its reset instants outrank both `sessionResetOverrideAt` and `weeklyAnchor`, which exist only as hand-corrections for a boundary that could not be observed. This is not a fourth cost source and can never be summed with the other three: it carries percentages and reset instants, no money and no tokens, and it must never reach `costUSD` or `runs.spent_usd`. What it fixed was not arithmetic — 4,995 turns cross-checked against OTLP put `pricing.ts` within 0.8% in aggregate, and the derived 5-hour boundary landed 53s off the provider's — but a denominator: a hand-typed $650 ceiling read 1.3% where the provider said 5.0%. Three properties shape the client and none is optional: it is rate limited (a handful of requests a minute earns a `429`), so it is cached on the CLI's own cadence (`fe_`/`pe_` in the shipped binary: refresh at 5 min, discard at 1 h) and a failure re-serves the last good reading; the body reports **percent** where the equivalent response headers carry a **0–1 fraction**, and reading one as the other is a 100x error in the one number this exists to get right; and the token is never refreshed from here, because that file belongs to the CLI. Everything degrades to the derived reading — `settings.planUsageFromApi` off, an expired login, an unreachable host, a reading past an hour — so a missing answer costs the old behaviour, never a zero.

**A fraction guard with no ceiling is refused, not ignored.** `evaluateBudget` returns `code: "no_ceiling"` when `maxWeeklyFraction`/`maxSessionFraction` is set but the window has no ceiling. Silently passing would leave the user believing a guard is active.

**Cost is the primary metric; raw tokens are the fallback.** A Claude Code workload is ~98% cache reads at 0.1×, so a token-denominated ceiling tracks conversation length rather than work. `WindowState` exposes both `costFraction` and `tokenFraction`, but `fraction`/`limitMetric` prefer cost whenever a cost ceiling exists.

**Unpriced models contribute $0 to everything displayed, and are named.** `resolvePrice` returns `null` for unknown models rather than guessing; `costOf(t, null)` is `0`; `scanUsage` collects `unpricedModels` and the dashboard banners them. Dollar totals are a documented floor.

**…but the guard charges them a fallback rate, because a floor is not a guard.** A window made entirely of an unpriced model has `costUSD === 0`, so `costFraction` is exactly `0` and no threshold can ever be crossed — the guard would silently stop existing the week a new model ships. `guardCostOf()` charges `UNKNOWN_MODEL_PRICE` ($10/$50, the priciest *current-generation* rate, so an unknown can never look cheaper than a known model), which flows through `Aggregate.costGuardUSD` → `WindowState.guardFraction` → the threshold comparisons in `evaluateBudget`. Keep the split absolute: `costUSD`/`fraction` are what the user is shown, `costGuardUSD`/`guardFraction` are what the guard acts on, and the two are identical whenever every model is priced. `Meter`'s `upperFraction` renders the gap as a hatched band — do not drop it, or a run gets refused at a threshold the visible bar has not reached. The `no_ceiling` refusal still reads `fraction`: a missing ceiling is a configuration fact, not a pricing one.

**Canonicalise model IDs, never truncate them.** `canonicalModelId()` strips region and vendor prefixes (`us.anthropic.`) and normalises `@date` to `-date`, so Bedrock and Agent Platform IDs resolve to the same rates as first-party ones. Do **not** add short catch-all keys like `claude-opus-4` — a future `claude-opus-4-9` would then be priced at a confident wrong number instead of surfacing as unknown, turning a loud failure into a quiet one.

**Naming the plan is not setting a ceiling.** `account.ts` reads Claude Code's own `.credentials.json` / `.claude.json` to *name* the subscription ("Claude Max 20x"). A tier maps to no published number, so this must never become a ceiling, never populate `DEFAULTS`, and never suppress the indeterminate meter. Both files are undocumented internals of another program — written lazily, mode 0600, possibly replaced by the macOS Keychain — so every read is try/catch to `null`, misses are cached only briefly, and the profile is projected to plan strings before it reaches `apiTypes.ts` (the source objects carry email, display name, and UUIDs). The legacy `~/.claude.json` is consulted only while `CLAUDE_CONFIG_DIR` is still the default: once it is redirected, that file describes whoever is logged in on the host rather than the account whose transcripts are being scanned, and a confident wrong plan name is worse than none.

**A block opens at its first turn, and nothing rounds that off.** The provider issues the reset instant itself — Claude Code reads `anthropic-ratelimit-unified-reset` off each response, and its own renderer prints the minutes whenever they are non-zero, so windows plainly do not begin on the hour. Nothing writes that instant to disk: it is on no transcript record, in no config file, and in none of the OTLP metrics the CLI exports, which is why this stays derived. `buildSessionBlocks` therefore anchors on the entry, and the error left is the opening turn's latency (seconds — the block is anchored on the response we can see, not the request that opened the window). Flooring to the hour, which this used to do, was not a rounding error: each block opens where the last one closed, so the offset carried down the entire chain, and a window rolled over up to an hour early reads as a *fresh, empty* session while the provider is still counting the old one — which is what the meter shows and what `evaluateBudget` acts on. There is deliberately no separate idle-gap rule: `blockStart <= lastActivityAt` always holds, so five quiet hours have already carried the next entry past the window, and reinstating one would assert that going quiet ends a window early, which the provider does not do.

**The 5-hour window is derived, except when the provider resets it.** `settings.sessionResetOverrideAt` is the one number a user supplies about a window rather than about a ceiling, because a tier change restarts the window with no trace in any transcript. `buildSessionBlocks` **splits** at `resetAt - 5h` rather than filtering: the pre-reset block is closed there (so it stops being active) and the next one starts at the reset instead of at its own first entry, which keeps that work in history where it did happen and did count. It is inert once `now >= resetAt` — a stale value keeps splitting history but must never re-open a finished window — and it never touches the weekly rollup. `PUT /api/settings` refuses a value more than 5h in the future with a 400, not a clamp: no window can reset that late, so it is a typo that would blank the session meter when its anchor arrived.

**A calendar period is history, and its percentage is a pace rather than an allowance.** `buildPeriods` cuts spend into days, weeks and months for the dashboard's period card, and it is the one rollup here that measures against a ceiling nobody published for the span it covers: Anthropic enforces a 5-hour window and a weekly one and nothing in between, so a day and a month are compared with `weeklyCostLimit` spread evenly over their own length. That is derived from a number the operator typed, which is what separates it from the ceilings `DEFAULTS` refuses to carry — but it is still not a limit, so `PeriodSeries.limitBasis` travels beside every fraction and the card says "pace, not an allowance" in words. It comes off the same computation that produced the fraction precisely so the sentence cannot drift from the arithmetic. Nothing here reaches `evaluateBudget`, and nothing should: a guard that trips on a calendar month is a threshold nobody set. It calls the same `buildWindow` the two live windows do, so the cost-over-tokens preference and the `costUSD`/`costGuardUSD` split are decided once — a bucket carries `guardFraction` for the same reason a window does. It is deliberately **not** folded into `buildSnapshot`: the orchestrator calls that before every work cycle and again on every live tick, and none of this feeds a decision, so only `/api/usage` pays for it.

**Calendar buckets are cut in the browser's zone, and a bucket's end is the next one's start.** The container runs in UTC, so a 22:30 turn in CEST is already tomorrow to the reader and yesterday to the server — a day cut in the wrong zone is wrong at every edge. `/api/usage?tz=` carries the zone the page is displaying in and `resolveTimeZone` refuses anything ICU does not know, falling back to the server's rather than throwing. `zonedMidnight` solves the local boundary in two passes because the offset depends on the instant being solved for; on a spring-forward day whose local midnight does not exist it lands an hour to one side, which is harmless only because `periodBoundaries` returns a single contiguous list and each bucket takes its end from the next bucket's start. Never compute an `endsAt` independently — a gap between two buckets silently drops the spend that falls in it, and a table of plausible dollar figures says nothing about the ones missing from it. Weekly buckets follow `settings.weeklyAnchor` when one is set and ISO Mondays otherwise: the newest bucket sits directly under the weekly meter, and a calendar Monday would put a different total under the same word.

**Reserved headroom is applied in exactly one place.** `limitConfig()` subtracts it so meters, guards, and the exhaustion projection all agree. Raw configured values stay on `Settings` for display. Capped at 0.95.

**Per-iteration spend comes from the CLI's own `result` event** (`total_cost_usd`), not re-derived from tokens. The transcript-derived cost math in `pricing.ts` serves the dashboard; the two are independent on purpose.

**A killed cycle's spend is reconciled, into its own column.** A cycle interrupted mid-flight never emits `result`, so it contributes $0 to `spent_usd`. `reconcileKilledCycle` recovers an estimate from the transcript pipeline — same dedupe key, same price table, same cache-TTL weighting — bounded by session id *and* the cycle's time range, because a resumed session copies earlier turns forward with their original timestamps. It lands in `spent_usd_est`/`spent_tokens_est` and **never** in `spent_usd`, which stays a floor of what the CLI itself measured; `RunProgress.spentGuardUSD` is the sum, and only the guard reads it. This is the same display-vs-guard split `costUSD`/`costGuardUSD` already makes for windows. The kill ladder tries `SIGINT` first for the same reason — a CLI that handles it may still print `result`, which is the difference between measured and estimated.

**The cycle in flight is on the row, in its own column, and it is not a count.** `iterations` is written only when a cycle *returns*, because that is what the guard counts — so for the whole of cycle 1, routinely tens of minutes, a working run read `0/N` and `$0.00`, which is bit-for-bit what a run that was marked running and never started reads. `runs.active_iteration` is the same number one tick earlier: stamped beside the `iteration` event at the spawn, cleared in the post-cycle UPDATE and again in `startRun`'s `finally`, so between cycles it is null rather than naming one that has already returned. It is display only — nothing derives a limit from it and `evaluateBudget` is passed exactly what it was before, including the live guard's deliberate `iterations - 1`. `fmtCycleInFlight` is the single reader and it refuses the column on any status but `running`, because nothing clears the row when the container dies mid-cycle and a finished run claiming an open cycle is the same lie pointing the other way. The wording is "cycle N of M **in flight**" for the reason `spent_usd_est` is a separate column: a reading that could be added to the completed count would be worse than no reading. `spent_usd` is untouched by this — it stays a floor of what the CLI measured, and the figure that moves during a cycle is still telemetry's.

**Attribution comes from the transcript, not from telemetry.** `effort`, `attributionAgent`, and `attributionSkill` are on the assistant record already, so `byEffort`/`byAgent`/`bySkill` cover full history with no collector, no config, and no second source to reconcile. Before adding a breakdown, check whether the field is already on the record — `agentId`, `gitBranch`, `usage.server_tool_use`, and `message.stop_reason` are all still unread. All five rollups go through one `groupBy()` in `windows.ts`, and every turn must land in a bucket (`MAIN_THREAD_BUCKET`, `(no skill)`, `(unspecified)`) so each column reconciles to the window total rather than silently omitting a remainder. The agent column now also says which of its buckets this install has a definition for — see the invariant below, and note what it does *not* do: nothing about the registry moves a turn between buckets.

**An agent bucket is annotated, never moved, and "nobody checked" is not "no such agent".** `byAgent`'s key stays whatever `attributionAgent` recorded — the same `groupBy()`, the same reconciliation to the window total — and `AgentOrigin` rides beside it saying where *this install* found a definition for that name: `registry`, `ambient`, `both`, `unknown`, or `main` for the bucket that is not an agent at all. That distinction is the point: an agent the operator wrote down and a name that came from somewhere else were indistinguishable on the card, and renaming a saved agent must move no spend between rows — it only stops the annotation matching, which is the truth. `both` exists rather than a winner because CLAUDE.md already records the saved-versus-ambient collision as **unverified**, so claiming the operator's own agent did work a file on disk may have done would be exactly the confident wrongness the registry exists to end. `agentOriginIndex` case-folds for `idx_agents_name`'s reason. The lookup is an **argument** to `buildSnapshot` rather than a read inside it, `normalizeWorkflowInput`'s shape: `windows.ts` knows nothing about SQLite or the filesystem, and the orchestrator — which calls that function before every work cycle and again on every live tick — passes nothing, so its guard path costs neither a query nor a directory walk and its rows carry `origin: null`. Null is "nobody asked" and must never collapse into `unknown`. Only the **user** scope of the ambient set is consulted, `GET /api/agents`' rule: the project scope depends on a cwd and this column covers every transcript on the machine, so a repository's own `.claude/agents` reads as `unknown` — which is why unmarked is the ordinary case and the card states in a footnote what it means rather than chipping most of the column.

**A run's agent split is the transcript source scoped to one session, and it is display only.** `agentSpend` is `byAgent` for one run: the same `groupBy`, the same `(main thread)` bucket, so the rows add up to the run's own transcript-derived total with nothing omitted. It answers the one question `runs.spent_usd` and telemetry structurally cannot — neither records *who* produced a turn — and it is not a new source: it is the same price table over the same transcripts that `reconcileKilledCycle` already reads for `spent_usd_est`, bounded by session id **and** by time for that function's reason, a resumed session copying earlier turns forward with their original timestamps. `created_at` rather than `started_at` is the bound, because `reopenRun` clears the latter and a run picked up by hand would otherwise report only what it spent since the pick-up under a heading that says it describes the run. It never reaches `runs.spent_usd`, never `buildSnapshot()`, never a budget verdict, and is never added to either of the other two readings — three routes to the same work, so any sum double-counts it. `costGuardUSD` travels beside `costUSD` here as everywhere, drawn as the hatched band past the fill; no session id is `spend: null` on the wire and the hatched *indeterminate* bar on the page, because a run whose agents spent nothing and a run nobody could measure must not look alike. Its own route and its own 30s poll rather than a field on `/api/runs/[id]`: that one is polled every three seconds against an agent competing for the same CPU, which is the reason the dashboard's own poll stops at 5s.

**A sub-agent's words are in the log and are never the run's own report.** `settings.forwardSubAgentText` (on by default) carries `--forward-subagent-text`, verified present on the pin (2.1.226) and gated by the CLI on `--print` and `--output-format=stream-json`, which `buildArgs` supplies unconditionally. Without it a delegation is a `Task` call followed by silence for as long as the sub-agent takes. What makes it safe is that the new shape is handled **by name** rather than falling through: `handleStreamLine` reads `parent_tool_use_id` — off the envelope, with the message as a fallback, so a key that moved fails *towards* treating a delegated turn as delegated — and routes it to its own `subagent` event kind. Three things it must never touch, each silent: `finalText`, which the `DONE` test is matched against **per line**, so a sub-agent reporting `DONE` would end a run whose main thread had not finished; `apiError`, latched on first sight, so a sub-agent that met a wall would park a run whose cycle then completed; and the `assistant` kind, which `cycleOutputs` takes the last of as the cycle's report — a report that silently interleaves two voices is worse than one that omits the second. `cycleOutputs` checks the kind *and* `parentToolUseId`, so the two readers cannot disagree. `thinking` blocks and forwarded `user` turns are dropped by name for the same reason they are named at all: a shape that arrives and is silently ignored is indistinguishable from one that never arrived. The `Task` call's `subagent_type` is kept per cycle so a forwarded line can say who is speaking; a sub-agent's tool calls stay `voice: "tool"` and are attributed in the label, because a `Grep` between two of the main thread's lines otherwise reads as the main thread's. The setting is the escape hatch and it is a real one: the CLI rejects a flag it does not know, so a pin that moves past this flag fails every run at the spawn — loud rather than quiet, which is the right direction, but it wants a switch that needs no rebuild.

**A default specialist is `settings.defaultAgentId`, and a form seed is not a naming.** `settings.defaultModel`'s precedent — one place for that kind of default — and an **id**, `run_templates.agent_id`'s rule, so fixing a reviewer's prompt reaches the next run. It carries no capability (an agent holds no tool list and no permission mode), so the two routes to `--permission-mode` stay two. `PUT /api/settings` refuses one that names no usable agent through the same `agentRefusal` every other door uses, which is `normalizeTemplateInput`'s rule: refuse where the person is. The one place this reads differently from the registry's "never fall back to none" is a default whose agent is deleted *afterwards* — the new-run form then starts with no specialist and **says so**, because that rule is about a run whose operator named a specialist, a pre-filled field nobody has looked at is not a naming, and the alternative is a new-run page that refuses every run until somebody visits Settings. The cost of that is on the Settings page rather than absorbed, and it is deliberate: one Save commits every field, so a default whose agent has been deleted refuses **any** settings edit until the picker is changed — the option stays on the list reading "Agent no longer in the registry" rather than reverting to none, so the refusal names something the operator can see and fix without leaving the page. Refusing where the person is, with the control in front of them, is the whole of `normalizeTemplateInput`'s rule; silently reverting the stored value would be the same page saying the setting had never been made. Nothing downstream changes: `POST /api/runs` still refuses a named agent that is gone, by name. The Settings row declares the ambient set beside itself through the same `describeAmbientAgents` the run form and the canvas use, because the registry is a part of the set and not the whole of it.

**A calendar period is history, so its percentage is a pace and never a guard.** `buildPeriods` cuts the same entries into days, weeks and months for the dashboard's period card, and it is deliberately *not* part of `buildSnapshot`: the orchestrator calls that before every work cycle and again on every live tick, and none of this feeds a decision. Anthropic enforces a 5-hour window and a weekly one and nothing in between, so the weekly ceiling is the only configured number a bucket can be measured against — a week uses it as it stands, a day and a month get it spread evenly over their own length, and `PeriodSeries.limitBasis` carries which of the two it was so the card's sentence cannot drift from the arithmetic that produced the fraction. Pro-rating is legal here for the reason `DEFAULTS` still refuses a numeric ceiling: this is derived from a number the operator typed, not invented from a plan name, and no guard reads it. The rest is the same rules as everywhere else — a missing ceiling is `null`, never `0`, and `guardFraction` rides alongside so an unpriced model widens the meter rather than understating it. Boundaries are cut in the **browser's** zone (`/api/usage?tz=`, validated by `resolveTimeZone`, falling back to the server's), because the container runs in UTC and a day cut there files an evening's work under the wrong date; a bucket's `endsAt` is taken from the next bucket's `startsAt` rather than computed, so DST cannot open a gap that silently drops spend. Weekly buckets follow `settings.weeklyAnchor` when it is set, or the local Monday when it is not — a calendar week under the same word as the weekly meter, showing a different total, is the disagreement this alignment exists to prevent.

**What a run is spending *now* is a third reading on the dashboard, never a correction to the meters.** A cycle's spend lands on `runs.spent_usd` only when the CLI emits `result`, so a cycle in flight contributes $0 there for its whole duration and the page can say nothing about which run is responsible or what it has cost so far. `telemetryWindow(since)` groups `otlp_requests` by `run_id` over the *snapshot's own* `session.startsAt`, so the card covers the same five hours as the meter above it — and the two are still never added, because one is Claude Code's per-request cost for agents this app spawned and the other is our price table over every transcript on the machine, covering overlapping work. Rows with a null `run_id` are excluded: the orchestrator stamps one onto every agent it spawns, so an unattributed record is something else pointed at the ingest route, and the card claims to describe runs. The listed runs are capped at the heaviest few while `runCount` reports the whole set, for the same reason a shortened diff says so. The poll drops from 10s to 5s **only** while `workingRunCount > 0` — `buildSnapshot` re-aggregates the full history on every request and the agent is competing for the same CPU, so a permanently faster dashboard would be paid for by the run it is watching.

**Transcript parsing details that materially change the numbers:**
- Dedupe key is `${message.id}:${requestId}`, applied across files (a resumed session copies earlier turns forward). Naive summing over-reports by ~3×.
- Files are read from a cached byte offset; the bytes after the final `\n` are left unconsumed so a partially-flushed line is re-read next pass. A shrinking file means rotation → re-parse from 0.
- `cache_creation` splits into 5m (1.25×) and 1h (2×). Unsplit legacy records are attributed to the **cheaper** 5m bucket so ambiguity understates rather than overstates.
- Pricing changes over time: `resolvePrice(model, {at, speed})` is date- and speed-aware (Sonnet 5 intro pricing has an end date; `speed: "fast"` has its own table). Keep new rates in that shape rather than flattening them.

**How guards are enforced is the operator's choice, and none of the three modes is a hard cap.** `BudgetPolicy.enforcement` selects it per run.

- `between-cycles` (the default) reads the guards only before each iteration. Overshoot is bounded by one iteration **per run active at the time**, and this is the only mode whose accounting is exact — every cycle reports its own cost.
- `live` also reads them on a global ticker (`liveGuardTick`, `settings.liveGuardIntervalSeconds`, floor 15s) while a child is in flight, and interrupts it. That bounds overshoot to *one model turn plus one interval plus the kill* instead, and costs the in-flight cycle's work. Every input moves per tick, but from three different places: `duration` off the wall clock, the two window fractions off a fresh `currentSnapshot()`, and the run's own spend off telemetry (see below — the locals cannot supply it). Neither usage source is instant: window usage comes from transcripts Claude Code flushes as each turn completes, and telemetry from a batch exporter a second or so behind. Tighter, not exact — say so in every piece of copy.
- `live-resume` is `live`, except the 5-hour window parks the run instead of ending it.

`LIVE_ENFORCEABLE_CODES` is the whitelist. `iterations` is excluded because the loop increments before it spawns — a live check must be passed `iterations - 1` or it kills the cycle the pre-cycle guard just authorised. `no_ceiling`/`no_terminus` are excluded because re-reading configuration mid-flight means a Settings edit in another tab kills a running agent. The ticker deliberately emits **no** `run_events` row per tick; only an interrupt is recorded.

**`run_cost`/`run_tokens` are live only because telemetry makes them live — this is the one place OTLP feeds a budget decision.** The ticker's `progress()` closes over `startRun`'s locals, and `spentUSD`/`spentTokens` only move when the CLI's `result` event is folded in *after* `runIteration` returns — by which point the `finally` has already removed the `liveGuards` entry. Those locals are therefore the *completed cycles'* total and nothing else, which made `maxRunCostUSD` overshoot by one full cycle under `live` exactly as under `between-cycles`: a between-cycles guard wearing a live label. `telemetrySpendSince(runId, cycleStartedAt)` supplies the missing half, bounded by the cycle start so the cycles that already reported through `result` are not counted twice, and added to `spentGuardUSD`/`spentGuardTokens` — **never** to `spentUSD`, so `runs.spent_usd` stays a floor of what Claude Code itself measured. Same display-vs-guard split as `costUSD`/`costGuardUSD`. The window fractions were never part of this: they move on every tick already, off a fresh snapshot, and a run's own turns land in that scan — but that is the whole machine's counter, not this run's, which is why it does not substitute.

**A guard whose input is optional is not a guard, so the input stops being optional.** `settings.telemetryForRuns` opts into *reporting* — the dashboard card and the run card. A run whose policy needs telemetry to be enforceable (`needsLiveSpendTelemetry`: live enforcement, plus a run cost or token limit) gets `telemetryEnv(runId, required)` regardless of that setting, because a guard that silently stops guarding when an unrelated toggle is off is the failure `guardCostOf()` exists to prevent for unpriced models. Refusing such a run at the door would have been the consistent alternative and was rejected: it refuses a policy that works today. `/api/usage` still gates its card on the setting, so nothing about the dashboard changes. What is *not* covered is an export that is configured and does not arrive — so the loop compares the CLI's own figure for each finished cycle against what telemetry reported for it, and logs a `run_events` line naming the cost when a paid cycle reported nothing. The alternative is a guard reading zero, which refuses nothing and looks exactly like a guard that was never reached.

**A cycle cut short by a pause is refunded to the counter.** The loop increments before it spawns, so a live interrupt — and a provider refusal, which does no work at all — lands on a cycle that has already been charged. Left charged, `live-resume` with `maxIterations: 1` can only park and then stop at `cycles` without ever finishing: the pre-cycle guard checks cycles before the session window. `MAX_PAUSES_PER_RUN` bounds the refund, so one work cycle is at most four billed invocations. The refund is applied at the post-cycle interrupt site only — `applyInterrupt`'s two other call sites run *before* the increment and would discount a cycle that completed. It also means `iterations` can no longer be read as "has this run worked before": the prompt/`--resume` choice keys on `sessionId === null`, and `ensureWorktree`'s orphaned-branch guard keys on `pause_count`.

Concurrency multiplies overshoot — `maxRunCostUSD` is per run, so N runs at $5 is a $25 worst case — and `maxConcurrentRuns` (default `null`, no limit) is what bounds N. The cap is enforced in `promoteQueued`, counting **running** rows only: it is a limit on work in flight, so a run over it waits rather than being refused, and queued *or paused* rows — which cost nothing — must never consume it.

**Only the 5-hour window can be waited out.** It is the sole quantity that refills on its own, on a schedule, with no configuration. The weekly window does not qualify: with `weeklyAnchor` unset (the default) `weekly.endsAt === now`, so there is no reset instant at all — the trailing total merely decays over days. `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume` and for nothing else, as a discriminated union so `resumeAt` is unreachable without narrowing. The check order — terminus, cycles, duration, run spend, weekly, *then* session — is load-bearing: a run that is out of time **and** out of window must end, not park, or the clock stops being a terminus.

**A run parks on two triggers, and only one of them needs configuring.** Our own guard is the first: `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume`, which needs both a per-run fraction *and* a numeric 5-hour ceiling — and ceilings default to `null` by design, so on a stock install that trigger never fires. The provider's own refusal is the second, and it needs neither. Claude Code reports API-level refusals as an assistant turn whose `message.model` is the literal `<synthetic>` (the marker `transcripts.ts` already keys on to keep an all-zero record out of the unpriced warning); `isUsageLimit()` decides whether that refusal is an exhausted allowance. Nothing parses a reset instant out of the message: the CLI renders a *formatted local time*, and the `usage limit reached|<epoch>` form every community wrapper keys on appears nowhere in the shipped binary. The refusal test sits **before** the exit-code test *and* before the `DONE` test — a refusal exits non-zero, so the exit code would file the provider's decision as the agent crashing, and a refusal that exits 0 would otherwise match nothing and re-spawn straight back into the wall.

**A refused run backs off; it does not trust the window boundary.** `refusalResumeAt` reads the end of the last block with real spend in it — not `session.endsAt`, because the refusal's own zero-token `<synthetic>` record opens a block of its own that reads as a window five hours out. Even that boundary is approximate in both directions: it runs late by the opening turn's latency, and early whenever the window was really opened by work this app cannot see — claude.ai, Desktop and Cowork spend the same allowance and write no local transcript. A boundary still in the future is waited for; one already passed falls through to a 20/40/60-minute backoff, floored so nothing re-spawns immediately and capped at six hours. `MAX_PAUSES_PER_RUN` bounds the whole thing, because unlike the guard path — where wall clock is checked ahead of the window and terminates the run — a refusal is someone else's claim about someone else's counter, and a misread one must not park forever.

**A `<synthetic>` turn is not by itself a refusal — the cycle's own outcome decides.** When a stream drops after some blocks have been yielded, Claude Code finalises the partial response with an ordinary `end_turn` and carries the cycle on (`tengu_streaming_partial_finalized`, and the watchdog/stale-connection retries beside it). The `API Error: Connection closed mid-response` turn it leaves behind is then a warning *about a completed cycle*, followed by a clean `result` and exit 0 — but `apiError` latches on first sight, so the marker alone was ending runs whose work cycle had finished. `recovered` requires the CLI's own verdict (a `result` event, a success subtype, a zero exit) — never anything inferred from the text — and excludes an allowance refusal by name, because a wall that exits 0 must still stop the run rather than re-spawn into itself, which is the reason this whole test sits ahead of the exit-code test.

**A refusal has three answers, not two, and the third one is not a park.** A cycle can also die because the connection dropped mid-response or the upstream was briefly overloaded — `isTransientApiError`, matched on the five stream-truncation sentences read out of the shipped binary, on the statuses and `error.type` names the provider documents as retryable, and on the socket errors that never reach a status. That is neither the wall nor the agent failing, so the loop retries it in place: 5/20/60 seconds of backoff and another spawn into the same session. Retried rather than parked because `resume_at` exists to wait out a five-hour window and a run that parks yields its folder — for a fault measured in seconds, on a run whose session is intact. `MAX_TRANSIENT_RETRIES` is **consecutive**, reset by any cycle that gets through and held in `startRun`'s frame rather than on the row (a restart hours later is not "in a row"), so a long run meeting one blip an hour is never terminated by the total while a dead upstream ends the run in ~85s and names the attempt count. The retried cycle is refunded to `iterations` *and* to `cyclesThisSegment` — the first for the reason a parked cycle is, the second because that counter means "no cycle in this segment has completed yet", which is what lets `looksLikeResumeFailure` still recognise a retry that cannot resume the truncated session. The order of the three tests is load-bearing: `isUsageLimit` first, because a wall can arrive as a 429 and no backoff refills an allowance. `refusalInStderr` deliberately does **not** consult this — an agent's own build output says "connection error" constantly, and a run must not re-spawn because its test suite could not reach a registry.

**A paused run is reconsidered, not trusted.** `resume_at` decides *when to look*; `evaluateBudget` decides *whether to run*. `sweepPaused` (60s, lazily started and stopped) re-evaluates from a fresh snapshot and re-queues through `promoteQueued` rather than calling `startRun` directly — that is what keeps FIFO order, folder reservation and the concurrency cap in one place. A verdict that can never clear ends the run instead of leaving it holding a folder. A cleared verdict is still not enough on its own: a run whose folder was taken while it waited stays `paused` and re-checks next tick, because the alternative is a `queued` row that a restart would close out.

**Reopening a finished run is an operator decision, not a resume.** `reopenRun` (`failed`/`stopped`/`completed` — `REOPENABLE`) puts a terminal row back in the queue keeping its folder, checkout, branch, session id and spend, so `startRun` continues the same conversation. It takes a **budget**, because the usual reason a run needs picking up is that its own limits ended it, and re-queueing under the limits that stopped it just reproduces the stop; the three carried-forward guards (`iterations`, run spend, run tokens) are therefore checked at the door rather than left to the pre-cycle check, which would refuse seconds later with the row already flickering queued → stopped and nothing said about what to change. `started_at` is **cleared**, and that is the one deliberate divergence from a pause: a parked run keeps its original start so wall clock stays a terminus it cannot wait out, while a run picked up by hand days later would otherwise be refused by its own time limit before it spawned. `permissionMode` is not accepted from the wire — the stored value carries forward, so reopening adds no second route to `--permission-mode`. An isolated run whose slot an active run has since taken is refused by name, because `allocateSlotPath` only avoids slots held by *active* rows and a terminal row is not one.

**A template is form input, and the two settings that decide what an agent may do are applied but announced.** `run_templates` holds a task, guards, and optionally a target; it takes no folder claim, consumes no concurrency slot, and nothing derived from `activeRuns()` can see it. `permissionMode` is narrowed three times — on save, on read, and again by `POST /api/runs` — because a template is the *second* route to `--permission-mode`, the flag `reopenRun` deliberately refuses to become a third route to. Only the last narrowing guards anything; the first puts the mistake where it was made, and the second (unknown → `plan`, the only mode that cannot write) is what stops a row from a build this one does not understand from ever *widening* what it permits. Never invert that fallback. `enforcement` is the other one: there is no `settings.defaultEnforcement` precisely so that no single edit turns every run into a cycle-killing run, and a template that quietly carried `live` would reintroduce exactly that — so a carried non-default mode, and a carried `bypassPermissions`, each raise a banner above the form with a one-click way back to the safe value, and the banner clears the moment the control is touched. `normalizeTemplateInput` also refuses the `no_terminus` pair at the door rather than leaving it to `POST /api/runs`: a template that can be saved but never instantiated fails weeks away from the form that caused it. `folder` is nullable and `""` is *not* the null — the empty string is the mount root, the one selection that blocks every other run in the tree. The template holds no model: `settings.defaultModel` is the single place for that. It *does* hold an `agent_id`, which is not a second place for one and not a fourth route to `--permission-mode` — an agent carries a role and no capability, and the model on it belongs to a delegated turn rather than to the run. See the agent invariant above for why that one is a reference where `runs.agent` is a copy.

**A saved agent is the fourth thing here that is form input, and it carries a role rather than a capability.** `agents` holds a name, a description — what the delegating model reads to choose it — a prompt, and optionally a model; it takes no folder claim, consumes no concurrency slot, nothing derived from `activeRuns()` can see it, and deleting one cannot reach a child that has already been spawned, because every spawn writes the whole definition onto its own argv rather than a reference to the row. It reaches a child as one `--agents <json>` pair through `agentsFlagValue`, and that is `--agents` rather than `--agent` deliberately: the plural flag *offers* a specialist to the delegating model, which is what a sub-agent is and the only thing a `description` is for, where the singular replaces the session's own main agent — a different feature answering a different question, and one nothing here wires. **A `tools` field is refused at save, and the refusal is the decision.** `--agents` members accept one and this app will not store one, because capability in this app comes from a guard set a person wrote — the permission mode, `ISOLATED_GIT_TOOLS`, `PROCESS_KILLERS` — reached through exactly two routes and re-narrowed at every one; an agent record is a third kind of thing that would carry it, and the surfaces that pick one put it within reach of a model, where `planProposal`'s rule is that prompt text is the one half of a run a model may write and capability is the other. There is also a concrete hazard behind it: `PROCESS_KILLERS` is a `--disallowedTools` entry and deny is *verified* to beat `--permission-mode`, but whether it also beats a sub-agent's own `tools: ["Bash"]` is **not** verified, and the incident behind that list is one `pkill` that restarted the container and failed fourteen runs. Refused by name rather than dropped, for `normalizeTemplateInput`'s reason: an operator who typed a tool list and got a saved agent that ignored it would believe their agent was narrowed when it was not. **A model is the one field `run_templates` refuses that this holds**, and it is not the same field — a template's model would be a second place to set the *run's* model, where this is the model one delegated turn runs on, which nothing else here can express. It moves cost and not capability, and every cost guard already covers it, since a delegated turn's spend lands on the run's own `result` event and in its telemetry like any other. It is free-form for `settings.defaultModel`'s reason: a list this build knows would refuse whatever ships next week. **The registry itself has no page.** `GET /api/agents` is read by four surfaces — the run form, Settings, the workflow canvas and the chat's mention popover — and `POST`/`PUT`/`DELETE` are reachable by hand and by nothing else, so every picker in this app is empty until somebody writes a row through the route. That is a gap rather than a decision, and it is worth knowing before reading the refusals below: they are worded for a person looking at a form, and the form they are in front of today is an HTTP 400.

**The CLI drops a malformed agent in silence, so this app refuses one at the door.** Measured against the pin (`@anthropic-ai/claude-code@2.1.226`), not read from the docs: a `--agents` member with no `description` is dropped, one with no `prompt` is dropped, one whose `model` is JSON `null` is dropped, an empty name registers as an empty entry, and a `--agents` value that is not JSON at all is ignored outright — exit 0 in every case, nothing on stderr, no line in the stream. The whole class of fault has one shape, and it is the expensive one: a run that was given a specialist and does not have it, which is bit-for-bit a run that was never given one. Nothing downstream can tell them apart — not the event log, not the cost, not the transcript's own `attributionAgent`, which simply never names it. The five are answered in three places rather than one, because they are not one kind of fault. `normalizeAgentInput` refuses the three a person can type — a missing description, a missing prompt, an empty name — where they were typed. `rowToAgent` reports a row that has *decayed* into one as `usable: false` rather than repairing it with a placeholder the delegating model would then choose on, and every door reads that flag. And the last two are the encoder's, because they are shapes rather than values: `agentsFlagValue` **omits** `model` instead of nulling it — the only spelling of "inherit" that survives — and it is the one thing that writes the JSON, so there is no second place for a payload to stop being JSON. It is that one encoder for every caller that can carry the flag (`buildArgs`, `runOrchestratorChild` for both of its callers, `spawnAssist`) precisely because a second copy of a shape whose every violation is silent would drift with nothing reporting it. A name that collides with one the CLI already answers to (`claude`, `Explore`, `general-purpose`, `Plan`, `statusline-setup`) is refused too: such a member does not appear as a second entry in the CLI's own list, so it either does nothing while the operator believes it is in play or replaces a built-in the main thread delegates to, and the CLI does not say which. That list can go stale when the pin moves, in the direction that costs a shadow rather than a crash.

**The agents this app did not write are left in play and declared, never silently mixed.** `docker-compose.yml` bind-mounts the operator's `~/.claude`, so `$CLAUDE_CONFIG_DIR/agents/**` already reaches every child this app spawns — runs, chat turns, orchestrator blocks and reviews — and an isolated run's worktree carries the repository's own `.claude/agents/` for the same reason. `--agents` **merges** with that set rather than replacing it, verified. Excluding them is what `--strict-mcp-config` does one door over, and it was rejected on the mechanism rather than the principle: agent discovery is governed by `--setting-sources`, where `user` keeps the user scope, `project` keeps the repository's, and only the empty value drops both — and that flag governs settings *whole*, so passing it to exclude agents would silently drop the operator's own `settings.json`, hooks, permissions and environment from every child. There is no agent-scoped exclusion in 2.1.226, and a change that large made in passing for a feature nobody has switched on yet is worse than the thing it fixes. The second reason is that these are not new: a repository's `.claude/agents/` is part of the repository the agent was pointed at, and withholding it would make a run behave differently from the same checkout opened in a terminal. So the registry is a *part* of the set and the app has to say so wherever an agent is chosen. `listAmbientAgents` is what that sentence is built from, `GET /api/agents` returns it as `ambient` beside `agents` so no two surfaces can say it differently, and `parseAgentFile` reads a definition the way the CLI does — the name off the frontmatter `name:` key and never off the filename, a file with no `name:` key not registered at all, subdirectories walked. Only the **user** scope is on that payload, being the half that holds whatever a child's cwd turns out to be; `listAmbientAgents` takes a directory for a caller that has already resolved one, and resolving an arbitrary one on the wire would be a containment surface this does not need. A saved agent whose name collides with an ambient one is *not* refused — the ambient set is per-cwd and a pure validator cannot see it — so which definition wins is unverified and a surface that lists both is what makes the collision visible.

**A run records the specialist it was given; a template records the one it names; and the difference between a copy and a reference is the whole of it.** `runs.agent` holds the entire definition as JSON, the treatment `runs.budget` already gives `permissionMode` and the reason deleting a template cannot reach a run started from one. An id there would be wrong twice: a run spawns a child per work cycle, so an agent deleted between cycle 3 and cycle 4 would leave cycle 4 with no specialist and nothing saying so — the CLI's own silent drop, reproduced by this app, at the one door built to stop it — and a run picked up by hand days later would lose it the same way. `run_templates.agent_id` is a reference for the opposite reason: a template is applied again and again, so an operator who fixes their reviewer's prompt expects the next run from it to use the fixed one. **What that reference reaches is the new-run form and nothing else** — it is a seed for a field, the treatment the template's mount and folder already get, and it is *not* inherited by the two paths that read a template on the server. `planProposal` takes the specialist off the proposal and `planNode` takes it off the node, both deliberately (the workflow invariant below argues that one out), so a template supplies a proposal its prompt and its guards and never its agent. Which is the honest reading of "carries onto the run exactly as the guards do": true where a person applied the template to a form, and false everywhere a model named the template instead. **A deleted agent is refused by name at every door and never falls back to none**, which is `planProposal`'s rule for a deleted template and the same reasoning — the operator started the run that said "and hand the review to the reviewer". `agentRefusal` is that one wording for every door handed an **id**, pure and unit-tested: `POST /api/runs` through `resolveAgentForRun` (which takes an id off the wire and never a definition, since a definition would be a route to an agent nobody saved), `normalizeTemplateInput` through the `TemplateKnowledge` it is handed — `normalizeWorkflowInput`'s argument-rather-than-read shape, for that function's reason, and the `no_terminus` rule applied to a second field so a template cannot be saveable and never startable — `PUT /api/settings` for the form default, `propose_run` and `approveProposal` for a chat proposal, `normalizeWorkflowInput` at save and at `/api/workflows/validate`, `planNode` at both moments a block becomes a run, and `startBlockTurn` for a deciding turn's own. The two doors that were shown a **name** rather than an id — `planEmission` for a spec and `createEmitted` when that spec becomes a run — refuse in their own words for that reason and no other; the answer is the same refusal, and the sentence has to name what the turn typed. An agent that exists but has decayed into something the CLI would drop is refused the same way and *named*, because `rowToAgent` reports rather than repairs. `reopenRun` carries the column forward by not touching it: there is no argument on the function and no field on the reopen route that could reach it, which is `permissionMode`'s rule one field over and also what lets a run whose agent has since been deleted still be picked up with the specialist it ran with. What the surfaces say is bounded by what the flag does: `--agents` *offers* a role to the delegating model, so the run page states it beside the guards and never among them — an agent carries no tool list and no permission mode, and a row inside that group would claim it bounds something — and the form's picker declares the ambient set beside itself, because the registry is a part of the set and not the whole of it.

**The orchestrator chat picks what work to do; something a person wrote picks what an agent may do; a person decides whether it happens.** `chat.ts` is a conversation with a read-mostly tool surface, and the two tools that write anything add a `chat_proposals` row or a template's *prompt* — both inert, holding no folder claim and no concurrency slot. `planProposal` is where a proposal becomes a run, and the branch that matters is the one that is *not* in it: no value off a proposal sets a budget, a permission mode or an isolation choice. Those come from the named template, or from `settings.chatDefaultGuards` when it names none — the second one exists because requiring a template made the chat useless on a stock install, and it is a *person's* configuration either way, which is the property that matters. A proposal that names a template that has since been deleted is refused by name rather than falling back to the defaults: the operator approved the card that said "Fix a bug", and a run under different rules than the card stated is what this gate exists to prevent. `--permission-mode` is not something a model should be able to reach for — the same reason `reopenRun` refuses to become a third route to that flag. The approval route takes an explicit list of ids the page displayed, so a proposal the chat added between render and click is not swept into an approval nobody saw, and it approves in one synchronous pass because `createRun`'s folder claim is only atomic inside an event-loop turn. An id that is not pending in *that* chat is dropped rather than approved — and `decisionNote` then has to say which of the two things it was, because "already decided" is a sentence about this thread's proposals and a selection carried over from another one is not. A batch where every id is dropped is a 400 for the same reason an empty list is: a 200 with nothing started is indistinguishable from a batch that worked, and the page clears the selection on `res.ok`. **There is deliberately no setting that approves a proposal automatically, and the chat itself starts nothing — but auto-start does exist, in one place, and the approval it needs is a different one.** A workflow's orchestrator block starts its runs with nobody clicking anything, because a person saved a graph that had already named that block's folder, its guard set and the most runs it may ever start. The approval moved from the run to the graph; it did not disappear, and everything that made this paragraph's gate worth having survives the move unchanged — see the orchestrator-block invariant below.

**Prompt text is the one half of a run a model may write, and it is written down as an exception rather than absorbed.** `chat_proposals.prompt_override` replaces the template's prompt for one run, and `save_template` writes a name and a prompt back for reuse — taking `chatGuards()` for a new template and the row's existing guards for an update, so no argument on that tool can move one. The distinction is not cosmetic: guards decide what an agent *may* do and prompts decide what it is *asked* to do, and a chat that cannot adapt a prompt just restates its objections inside the task, which puts the same text in the run with nothing recording that it happened. `composeTask` keeps the two halves in order and separated by a heading, and emits the task alone when there is nothing standing above it — a section marker for a section that is not there is worse than no marker. Every proposal card says which guard set applies, spelling out the untemplated one, and marks a rewritten prompt.

**Who does the work is the third half a model may write, and it is the same act as writing the task.** `chat_proposals.agent_id` and a proposed graph's `agentId` name a saved specialist, and neither is an exception to the paragraph above: an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so `planProposal` and `planNode` gain no branch that reads a guard off either. It is an **id** rather than the frozen copy `runs.agent` holds, which is `run_templates`' rule and for its reason — a proposal is form input a person decides on, so it should name the agent as it stands at the click rather than as it stood when the model wrote the card, and the copy is taken where it always is, by `createRun`. A deleted or decayed one is refused **by name** through the same `agentRefusal` at both moments the template is checked at: when the tool records the proposal, where a model can act on the sentence, and again at approval, where the operator can. `list_agents` is what a turn reads first, and it is on the **shared** tool list rather than the chat's: a block names a specialist too, and the alternative is a deciding turn guessing at names out of its system prompt. It grants neither subject anything — the same reason naming one is allowed at all — and it declares the ambient definitions beside the registry, because those reach every run whatever is named and cannot be named at all. The card carries the agent in the line that already carries the folder and the guard set, and *outside* the guard mark: a phrase under the shield would claim a specialist bounds something, which is the one thing about it that is not true. `summarizeProposedGraph` says it per block for the same reason it says the fan-out cap.

**The chat's own turn is not offered one, and the asymmetry with an orchestrator block is the whole reason.** `runOrchestratorChild` takes `agents` and a block hands it the one its node names; `runTurn` deliberately hands it none. This is the only child in the app whose boundary is *prose* — `bypassPermissions`, no allowlist, and `systemPrompt`'s look-do-not-build paragraph carried by `--append-system-prompt`, which is the **main thread's** system prompt. A `--agents` member carries a system prompt of its own for the turn it is delegated, and whether the appended text reaches that turn as well is **not verified against the pin**; every other child can absorb the question because what bounds it is a permission mode and two tool lists a delegated turn inherits by running inside the same process — which is a much smaller assumption than a `--append-system-prompt` reaching a member that carries a system prompt of its own, but is itself reasoned rather than measured and is on the README's *Not yet verified* list by name. The second half is that there is no work here for a specialist to do: a chat turn looks and proposes, so what an agent would change is how the orchestrator *thinks*, which is the one thing that prompt fixes on purpose. The `@`-mention in the composer is what an operator actually wants from this — it names the specialist the proposed *run* carries. Nothing in this app parses it back out of the message: it is text, read by a model that has `list_agents`, which is why a name with a space in it is inserted as it stands rather than quoted into a syntax nothing else here speaks. The popover takes **Tab**, the arrows and Esc and never Enter or ⌘↩, because this composer sends on Enter and a list that accepted a completion with it would swallow the send exactly when the operator had finished typing a name.

**Order is the other half of the work a model may write, and it is a label until a person approves it.** `chat_proposals.spec_id` is the chat's own name for a proposal and `depends_on` is what it says that proposal starts after — labels rather than ids, because the model writes several proposals in one turn and has to point one at another before either has an id. They resolve to *run* ids at approval and nowhere else: `planApprovalBatch` is that decision, pure and unit-tested for `planProposal`'s reason with `releasableRuns`' failure modes. A label naming a sibling in the same click resolves to the run this pass is about to create; one naming a proposal of this chat that already became a run resolves to it; anything else **fails that one proposal by name**, and everything behind it fails too with its own sentence naming the one in front of it. Dropping the edge instead is the failure this exists to have none of — a run told to wait and started immediately is bit-for-bit a run that was never told, and the two agents then work in the same checkout in whatever order the queue felt like. The batch is created in `topologicalOrder`, which moved to `orchestrator.ts` beside `dependencyCycle` for that function's reason: three callers now create runs in one synchronous pass and "every one after what it waits for" has to mean one thing. Without it the order is whatever the page displayed, and a proposal is refused as naming a missing run — an artefact of a render, reported as a fact about the work. Everything `admitDependencies` already decides is deliberately *not* re-decided here — one branch handed over, both ends isolated, no rival continuation, no loop against the live graph — because those need rows and a second copy would be a second set of rules to keep in step; what `propose_run` does check at the door is the subset it can, for the reason it validates everything else there.

**The chat can write a workflow, and approving one saves it rather than starting it.** That asymmetry with `propose_run` is the whole design. An orchestrator block's runs start with nobody looking *because a person fixed its folder, its guard set and its fan-out cap when they saved the graph* — and a graph a model wrote has no such person in it. Saving rather than starting puts one back: the operator reads a card that spells out every guard-shaped fact a canvas would show (`summarizeProposedGraph` — which template supplies each block's guards or the untemplated set written out, where each block runs, how many runs a deciding block may start, whether a merge block may pay to reconcile), then opens the graph, then presses Run. Two separate human decisions stand behind every number in it before an agent exists. `planWorkflowProposal` re-normalizes through the *same* `normalizeWorkflowInput` and the same `folderRefusal` the save route and the validate route call, with the same `currentKnowledge()`, so a template deleted between the proposal and the click is refused by name exactly as `planProposal` refuses one — a second set of rules about what a workflow may be would be confidently wrong about what Approve does the day one of them changed. The **instance budget is not carried**, and there is nothing on the wire that could carry it: no field on the tool, no column on the row, no argument on the plan. That is `startWorkflow`'s "there is nothing to raise it *with*" applied one level up, and its cost is stated rather than absorbed — a proposed workflow runs by hand and `scheduleRefusal` will not let it be scheduled until the operator sets one, which the card says in words. `propose_workflow` requires a `folder` on every non-merge block even though `normalizeWorkflowInput` accepts `""`: the empty string is a real answer from the editor's picker and an *omitted* field is not that answer, and reading one as the other would silently put a block on the mount root — the one selection that blocks every other run in the tree.

**A workflow is the third thing here that is form input, and it is not the fourth route to `--permission-mode`.** `workflows` holds a name, a graph and one budget for the whole instance (below); a node in it holds the *work* — mount, folder, task, an optional prompt override — and names a **template** for every guard, or names none and takes `settings.chatDefaultGuards`. That is `planProposal`'s rule reused rather than restated, and `planNode` is deliberately shaped like it, down to refusing a node whose template has been deleted **by name** instead of falling back to the untemplated set: the operator saved a graph that said "under these guards". There is no `permission_mode` column, no budget blob and no model on a **node**, so the three narrowings stay three and the two routes to that flag stay two — the instance budget is on the workflow rather than on a node precisely because it bounds the graph and not a block, and it holds none of those three. Prompt text is the one exception and the same one a proposal makes — `promptOverride` replaces the template's standing instructions for one node, joined to the task by the *same* `composeTask`, so how the two halves are ordered and marked has one definition. The mount and folder are on the node rather than inherited from its template, which is where this *diverges* from a proposal: a proposal is approved minutes after it is written, where a workflow is saved once and run for months, and a template edited in between would silently move a node's run to another repository with nothing in the graph changing. **The specialist is on the node for that same reason and is deliberately not inherited either**, which is the one place a workflow block and the run form read a template differently: the form applies one as a seed for every field, where a node reads one for exactly two things — its guards, through `guardsFor`, and the standing instructions `promptOverride` replaces. `run_templates.agent_id` therefore decides nothing about a block, and `guardsFor` still returns three fields, which is the absence this whole design rests on. It is an **id** rather than a copy, `run_templates`' rule and the opposite of `runs.agent`'s: a graph is applied again and again, so an operator who fixes their reviewer's prompt expects the next press of Run to use the fixed one, and the copy is taken where it always is, by `createRun`, so an agent deleted between two blocks of one instance cannot reach a run already started. It carries no capability — an agent holds no tool list and no permission mode — so this is not a fifth route to `--permission-mode`; and it is refused **by name** at save, at `/api/workflows/validate` and at instantiation, through the same `agentRefusal` the run door and the template door use, never falling back to none. Which child it names differs by kind and the field does not: a run block's own run, an orchestrator block's *deciding turn* (the runs that block emits name their own, per spec — the opposite way round from `promptOverride`, which it holds on behalf of those runs, because standing instructions are what a run is asked and the deciding turn is asked by `blockSystemPrompt`), and a merge block **none**, where one is refused rather than dropped: that block spawns no child at all, so accepting it would be this app performing the CLI's own silent drop at the one door built to end it. Everything else follows `run_templates` — no folder claim, no concurrency slot, invisible to `activeRuns()`, and deleting one cannot reach a run that has already started. A node's `kind` is the one thing that changes what it *becomes* rather than what it says: `run` is a fixed run and the default, because every graph saved before this existed says nothing there and the other reading would turn one of them into a graph that starts agents nobody wrote. `orchestrator` is the other, and it adds exactly one field a node may hold — `fanOut`, which is not nullable — and no route to a guard; see the orchestrator-block invariant below.

**A workflow is instantiated in topological order, in one synchronous pass, all or nothing.** `topologicalOrder` — in `orchestrator.ts`, beside `dependencyCycle`, because a saved graph, an orchestrator block's emitted specs and a batch of approved chat proposals all create runs in one pass and all need one answer to "every one after what it waits for" — is pure and unit-tested because both ways of being wrong are silent: a node released before its dependencies exist is a `createRun` whose `dependsOn` names rows that are not there, and an unplaceable node is a row that sits `waiting` for ever — `releasableRuns` reaches a fixed point and leaves it alone, which is the one outcome the dependency design has none of. Ties break on the node's declaration order, so two presses of Run on one graph produce the same queue; runs are admitted oldest-first and a queued run reserves its folder against everything younger, so an unstable order would silently reorder work on one repository. The pass itself has no `await` between the `createRun` calls, for the reason the chat's approval route batches: the folder claim is only atomic inside one event-loop turn. Everything checkable is checked *before* anything is created — the graph against the templates and mounts that exist now, `resolveWorkspaceFolder` for every node, and every node's guards — so a mid-pass failure should be unreachable; if one happens the created runs are **stopped** (never deleted: one may already hold a checkout and a child, and the row is what the kill path and `reconcileOnBoot` need) and the instance is recorded `failed` with the reason. Half a graph is not a smaller workflow. Re-running while a previous instance still has live runs is refused with a count rather than left to chance: the second instance points the same nodes at the same folders, and a node continuing a branch would be refused mid-pass because the first instance's run already continues it. `normalizeWorkflowInput` refuses the same things at *save* that instantiation does — the `normalizeTemplateInput` rule, because a graph that can be saved and never started fails weeks away from the form that caused it — and it takes the templates, mounts and default isolation as an argument rather than reading them, which is what makes it pure and what makes "saved, then no longer startable" a sentence instead of a surprise. `folderRefusal` is the one check that is *not* in it, because it is a syscall; it runs beside it at both moments.

**A workflow is drawn on a canvas, and where a block sits is not part of it.** The obvious home for a coordinate is `WorkflowNode`, and it is wrong twice over: `normalizeWorkflowInput` rebuilds each node from a fixed list of fields, so an `x`/`y` would be dropped in passing and the drag would silently not persist; and let through, it would make moving a block two inches a rewrite of the object `topologicalOrder` reads, bumping `updated_at` and landing in the blob an instance copies. So the graph is untouched and a position is a *view* of it — held per browser under `uf.workflow-layout.<id>`, and reconciled by `resolveLayout` against an arrangement `autoLayout` derives from the edges. That derivation is what makes "a graph saved before the canvas opens readable" true with **no migration at all**, which is the only way to be sure a layout change cannot lose an edge; the cost, stated rather than absorbed, is that a hand-made arrangement does not follow the operator to another browser. `autoLayout` is bounded rather than run to a fixed point because it has to be able to draw a **cycle**: refusing a loop is `normalizeWorkflowInput`'s decision and it can only answer about a graph it has been sent, so one is on screen between the second click and the answer, and an unbounded relaxation there is a frozen tab that typechecks. **Nothing in the browser decides what a workflow may be.** `POST /api/workflows/validate` calls the same `normalizeWorkflowInput` and the same `folderRefusal` the save route calls, with the same `currentKnowledge()`, and the editor renders the sentence it gets back — a second copy of those rules in the client would be a second set to keep in step, confidently wrong about what Save would do the day one of them changed. That route answers **200 for a refusal**, because a 400 is indistinguishable from the route being unreachable and the editor says different things in those two cases; Save stays enabled behind it for the same reason, since a disabled Save behind a failed advisory check strands the operator with no way to reach the authority at all. A drawn link carries `edge: ""` all the way onto the wire and is refused by name: `on-success` terminates a chain the operator meant to run regardless and `on-finish` starts a run on top of a dependency that crashed, so the picker offers the unanswered state as a real option rather than pre-selecting one. Adding a block, linking two and removing a link each have a keyboard route as well as a pointer one, and `handledByPointer` is what keeps them from both firing — a captured pointer sequence still dispatches a trailing `click`, which would otherwise add a second block or disarm a link that had just been drawn; the `click` handler stays because it is also what a screen reader dispatches, with no pointer events in front of it. There is no canvas library: the drag is `setPointerCapture` and the edges are cubics in an SVG overlay, about 4 kB over the form this replaced. **The surface is a framed pane and the selection is a halo, never a border.** The frame is a toolbar strip (the palette, and the block and link counts), a recessed scroll region standing on a faint `dot-grid`, and a footer naming the gestures — the grid is the only cue that an arrangement is somebody's rather than the app's. Replacing a card's border on selection is what this had before and it cost the one thing that border is for: an orchestrator block wears the warn edge permanently *because* it starts runs with no approval, and painting it accent at the moment somebody selected it withdrew that statement exactly when it was being read. A ring is outside the box and sets a different property, so both facts are on screen and neither class string can outrank the other. **Delete removes the selection, and there is no undo.** The surface handles it for whatever the inspector is showing; a block's name and a link's condition chip handle it for their own identity and stop it there, so the *focused* thing wins over the *selected* one on the rare occasion Tab has moved them apart. `preventDefault` on that key is load-bearing rather than tidy — Backspace outside a text field is the browser's own Back on more than one engine, and losing the whole draft to it is worse than anything this key is for. A ⌘Z was considered and rejected: this app has no undo model, and one that put a block back without its links, or without the position it was dragged to, is worse than the absence because the operator stops checking. What stands in for it is that nothing on the canvas is saved until Save. **The inspector is a sticky column beside the canvas, not a form under it**, and every block states in one sentence what a press of Run is approved against — which template supplies its guards or that it takes the untemplated set from Settings, where it runs, which saved agent it may hand a subtask to, how many runs a deciding block may start with nobody looking, and whether a merge block may pay to reconcile a conflict. `BlockStatement` is that sentence and it is prose on purpose: those five facts were five separate pickers to read off, and the card the operator approves against has to say them rather than imply them. The specialist is stated *outside* the guard clause and its picker sits outside the guards group, because an agent bounds nothing — a phrase inside "under …" would claim it does — and the picker declares the ambient set beside itself for the reason the run form's does: the registry is a part of the set and not the whole of it.

**A workflow instance is halted through one door, and the door is closed before anything is signalled.** `stopInstance` is that door: an operator's control and a tripped instance guard both call it and differ *only* in the recorded cause, because a second implementation of "which members does this take down" is a second chance to miss one, and a missed member goes on spending under a page that says the workflow is stopped. The instance is marked `stopping` by an UPDATE guarded on `status='started'` — the closed door and the idempotence in one statement, a second stop changing no rows rather than running a second kill ladder over children that are already dying — and from there to the last member there is **no `await`**, the property `createRun`'s folder claim already documents for the same reason. Every kind of member is covered at once and each keeps the machinery it already had: `running`, `queued` and `paused` go through `stopRun` and its existing branches, so there is still exactly one way to signal a child and the `SIGINT`-first ladder still buys a cycle the chance to report its own cost; a `waiting` member is written `blocked` — what this app already writes for a run refused before its first work cycle, and the true thing to say, which also keeps it out of `REOPENABLE`, since picking one link of a halted chain back up would start it on work that never happened; a member already terminal is **left alone**, because a `completed` row rewritten as stopped destroys the record of work that landed and nothing on the page afterwards says it happened; and a node whose `createRun` never ran is not a member at all, so it is never created. `haltPlan` is that whole decision, pure and unit-tested, for the reason `releasableRuns` and `landRefusal` are. **Waiting members are blocked before any other member is touched**, because stopping a run releases its dependents and a dependent released a moment before the halt reached it would be admitted, promoted and spawned — a member starting *because* the workflow was stopped. Stopping a queued member can still promote another queued member inside the same turn; that is harmless and deliberately not designed around, since `stopRun` re-reads the row and `startRun`'s pre-spawn checkpoint sees the interrupt before any child is spawned, costing a transcript scan rather than a billed cycle. The halt never removes a checkout, never touches a branch and never commits: uncommitted work stays in its slot with its own branch checked out, where `slotIsDirty` keeps the next run out and `commitRefusal` — which already settled whose work is in a slot — still decides whether it may be committed. Queued `merge_queue` rows for those runs are cancelled and one in flight is left to finish, exactly as `cancelBatch` has it. The instance records that it was stopped, by what and when, and the member's own reason distinguishes the three endings on sight: halted with its workflow, halted by that workflow's budget guard, or stopped on its own run page (`stopRun`'s unchanged default). `stopped` is **derived** rather than stored — `stopping` plus no live member — because a signalled child takes seconds to die and nothing would run a second pass after a restart; `reconcileHaltsOnBoot` exists only for the crash *inside* the walk, where `reconcileOnBoot`'s deliberate exception for a recently `paused` row would otherwise leave the sweeper to re-queue a member of a stopped workflow. A halt is terminal: there is no pause and resume for an instance — **and no way back in through a member either**. `reopenRun` refuses a run whose instance is `stopping`, naming the workflow, and `reviveBlockedDependents` leaves those runs out of its candidate set; `haltedWorkflowOf` is the one condition both read, so a run refused on its own page cannot be woken from the page in front of it, and it tests `stopping` alone because that is the only stored value — `stopped` is the same row read later. Neither the status nor `REOPENABLE` is the gate any more: a halted `waiting` member is `blocked` with no `work_dir`, which is exactly the shape `reopenRun`'s `waitingAgain` branch accepts and exactly the row the revive selects, so without the membership condition **Try again** — or reopening the stopped run in front of it — put agents back to work under an instance the page reads as "Stopped", with the instance guard unable to stop them because it acts only on a `started` one. `RunDTO.haltedWorkflow` carries the same answer to the run page, which declines to offer the button rather than let the operator find out by pressing it. **Orchestrator blocks go first, before any member is touched**, and that is the waiting-member rule sharpened: a block does not merely get *released* by a stop, it creates runs, so one left `thinking` while the walk ran could emit into a workflow being taken down and every run it started would be a member the halt had already walked past. A `waiting` block becomes `blocked` and a `thinking` one `failed` — that turn was billed, and saying it never ran would hide the spend already on its row — both written before the child is signalled, so the guarded UPDATEs in `emitBlockRuns` and `settleBlock` refuse whatever the dying turn still tries to do.

**A workflow instance carries its own budget, and it is checked between blocks rather than during one.** `run_templates` bounds one block; ten blocks under a $5 block limit is a $50 workflow, and `InstanceBudgetPolicy` — `maxInstanceCostUSD` plus the two window fractions, all nullable, `null`/`""`/`0` all meaning off — is what bounds the graph. It goes through `evaluateInstanceBudget`, which is the *same* `BudgetVerdict`, the same `BudgetStopCode` vocabulary and the same `readWindowGuard` reading as `evaluateBudget`, because an instance limit with its own words for "no ceiling configured" would be a second set of budget rules to keep in step. `readWindowGuard` is that shared half and it exists to make one thing unmissable: `fraction` answers "is there a reading at all" and `guardFraction` answers "is it past the threshold". Those are **different fields for different reasons** — `fraction` is what `windows.ts` fills from the provider's own percentage when `planUsage.ts` answered, so a window can carry a perfectly good reading with nothing typed into Settings and refusing it as `no_ceiling` would disable the guard on a stock install, while `guardFraction` is what charges an unpriced model the fallback rate so the guard does not quietly stop existing the week a new model ships. Both are null together, by construction in `buildWindow` and again in `makeWindow`. What it does **not** share with `evaluateBudget` is that function's body, for two reasons that are the whole design: an instance needs **no monotone terminus** — the run loop requires one because the loop manufactures its own next unit of work, where an instance is a finite graph created in one pass whose members each already carry a terminus, so all three limits are legally null together and the `no_terminus` refusal has no analogue — and an instance **never parks**, because parking is a decision about a run that yields its folder and keeps its checkout for the same conversation, and an instance holds neither. Enforcement is **between nodes**: `enforceInstanceBudget` is called from `startRun`'s pre-cycle guard off the snapshot that check has just read, which for the default `maxIterations: 1` is literally between two blocks and for a longer block is every cycle boundary. An orchestrator block is the other kind of boundary and is checked at it — `enforceInstanceBudgetForBlock`, same door, same verdict vocabulary, called from `startBlockTurn` before the child is spawned. Without it a graph of nothing but deciding blocks would carry a workflow-wide limit that never fires, since nothing in it ever reaches a *cycle* boundary. There is deliberately **no live mode**, and the copy on the editor and the instance page says so in words: `liveGuardTick` reads one run's policy against that run's own progress and every code on `LIVE_ENFORCEABLE_CODES` is a fact about a run, so extending it would kill every member mid-cycle and turn each one's measured `result` cost into a reconciled estimate, for a bound that is already one cycle in the ordinary case. The cost of not doing it is stated rather than absorbed — a block already working carries on until some block reaches a boundary, so the total can overshoot by up to one work cycle per block running at the time, and concurrency multiplies it. The limiting case is a graph whose blocks all start at once with one cycle each: there is no boundary between them and the guard never fires, which makes `settings.maxConcurrentRuns` the lever for this exactly as it is the lever for `maxRunCostUSD`'s N-runs-at-once worst case. Both the editor and the README say so. A tripped verdict calls `stopInstance` with `{ kind: "guard" }` rather than re-deciding which members to take down, and `startRun`'s pre-spawn checkpoint picks up the resulting interrupt like any other. `INSTANCE_ENFORCEABLE_CODES` is the whitelist, and it is `LIVE_ENFORCEABLE_CODES`'s reasoning applied to the one code that is about configuration rather than spending: `no_ceiling` is refused **at the door** by `startWorkflow`, which has an error channel, and is deliberately not acted on afterwards. On a stock install the reading behind `fraction` is the provider's own percentage, discarded after an hour without a fresh answer, so halting on its absence would turn an unreachable Anthropic host into every fraction-guarded workflow stopped and every one of their blocks killed mid-cycle. It is not ignored either — the run whose check found it logs that the guard had nothing to read, the same answer this app already gives a live spending limit whose telemetry never arrived.

**The instance total is a fourth reading, and the door telemetry reaches it through is the same one, widened by one caller.** `instanceSpend` returns two figures and never one. `spentUSD` is the sum of the members' `runs.spent_usd` — a floor, since a cycle in flight has emitted no `result` and contributes zero for its whole duration — and is what the instance page draws as the meter's solid fill. `spentGuardUSD` adds each member's `spent_usd_est` and, for `running` members only, `telemetrySpendSince(runId, active_started_at)`; it is what `evaluateInstanceBudget` compares, and it is drawn as the hatched band past the fill, the same rendering an unpriced model's gap already gets. It never reaches `runs.spent_usd`, `buildSnapshot()` or any dashboard meter, and it is not a fifth cost source. The telemetry door was "one run, its own current cycle, its own live guard"; it is now also "each member, its own current cycle, the instance guard" — same function, same per-run and per-cycle bound, same `*Guard*` destination, and that widening is written down here rather than absorbed. `runs.active_started_at` is what made it readable from outside `startRun`'s frame: the other half of the fact `active_iteration` already carries, stamped and cleared in exactly the three places that column is, and read only for a `running` row for the reason `fmtCycleInFlight` refuses it on any other status. Both figures also carry what this instance's **orchestrator blocks** spent deciding, out of `workflow_instance_blocks.cost_usd`. That is not a fifth source and not a widening of the telemetry door: it is the CLI's own `total_cost_usd` for a turn that ended, the same authority `runs.spent_usd` has, so it is measured rather than estimated and belongs in the display figure as well as the guard's. It never touches `runs.spent_usd`, `buildSnapshot()` or a dashboard meter — the split that matters is display-versus-guard, and this is neither side of it, it is simply money the press of Run spent that no member run's row records. Where a figure has no denominator — no `maxInstanceCostUSD` — the meter is the hatched indeterminate bar, never an empty one: an instance whose share of a limit is unknown and one that has spent nothing must not look alike.

**A person sets an instance budget, and there is nothing on the wire that could.** It lives on the saved workflow, is normalized by `normalizeInstanceBudget` (total and idempotent, `normalizePolicy`'s rules), and is **copied onto the instance** at `startWorkflow` — the treatment the graph blob already gets, so editing the workflow cannot move the guard under a graph already running. `POST /api/workflows/[id]/run` still reads no body, there is no override argument on `startWorkflow`, and no route writes `workflow_instances.instance_budget`, which is the strongest form of "an orchestrator block must not raise its own instance's budget": there is nothing to raise it with. The route's one new job is to `await currentSnapshot()` and hand it over, because `startWorkflow` must stay synchronous from its first `createRun` to its last and the door check needs a real reading — a fraction guard with no ceiling behind it, or a window already past the guard, is a 400 with a sentence rather than a graph that halts before its first block does anything. `normalizeWorkflowInput` deliberately does **not** refuse the missing ceiling at *save*, the one place it departs from its own "refuse at save what instantiation refuses" rule: a ceiling is a Settings value that can be typed at any moment, so such a graph is not unstartable, only unstartable today. The editor warns beside the field.

**A block can decide what runs next, and those runs start with no approval — because the approval moved to the graph rather than disappearing.** An orchestrator block is a node whose `kind` is `orchestrator`, holding a brief, a folder, an optional template and a **fan-out cap**; when the workflow reaches it the server spawns one headless turn through `runOrchestratorChild`, and the specs it emits become runs that enter the queue. No `chat_proposals` row, no card, nothing between the decision and the spawn. What makes that defensible is not the block, it is the four things a person fixed when they saved the graph, and every one of them is unreachable from anything the model emits. **Guards** come from the block's named template or from `settings.chatDefaultGuards` — `planProposal`'s rule reused a third time, through the shared `guardsFor`, and `planEmittedRun` has no branch that reads a budget, a permission mode or an isolation choice off a spec, for the reason `reopenRun` refuses to become a third route to `--permission-mode`. **The folder** goes through `resolveWorkspaceFolder` against the block's *own* mount and no other, so containment is `resolveInMount`'s two checks unchanged. **The cap** is not nullable: `normalizeWorkflowInput` refuses an orchestrator block without one at *save*, which is the `no_terminus` rule applied where it bites hardest — this is the one block whose runs start with nobody looking, so a missing ceiling is an unbounded number of billed agents from one press of Run. And **`emit_runs` is a spec and nothing more** — a title, a task, a folder, an optional specialist, and edges among the runs being emitted — with `/api/mcp` publishing it only to a `block` capability and `propose_run`/`save_template` only to a `chat` one, checked again in `callTool` because a tool absent from a list is not a tool absent from the wire. **The specialist is the exception that is not one**: an emitted spec may name a saved agent, and that is the same class of act as writing the task text beside it — an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so it decides *who* does a piece of the work and never what the run may do. It is named by **name**, because a name is what `blockSystemPrompt` showed the turn and an id is a thing only this app's own forms hold; `planEmission` refuses one this install does not have, beside the cap and the loop, before anything is created, and stores the registry's own spelling so what reaches `--agents` is what the operator saved. The block's *own* deciding turn takes the agent the node names, refused by name before it spawns rather than dropped. The block's own spend lands in `workflow_instance_blocks.cost_usd`, never in `runs.spent_usd` and never in a meter, bounded by `settings.chatTurnBudgetUSD` inside the CLI exactly as a chat turn's is; it *is* added to the instance's own total, in both figures, because it is measured money this press of Run spent and a graph with several deciding blocks would otherwise understate itself against the one limit meant to bound the whole thing.

**And what the turn said is kept, in three fields that are three voices.** A block that starts nothing blocks every node behind it, so it ends the graph — and the row that says so used to carry a status, a count of zero and nothing else, which is one appearance for three different endings: it decided there was nothing worth doing, this app refused what it asked for, or it never reached a decision. `reply` is the model's own account, which its system prompt asks for in as many words and which was read off stdout and dropped; `notes` is *this app's* — an `emit_runs` refused by `planEmission`, a tool call the CLI declined, the instance guard `startBlockTurn` could not read — appended as each happens, because they arrive from three places across a turn and an operator reading them for a cause needs all of them rather than the last; `error` stays the turn failing and nothing else. `blockSettlement` is that decision, pure and unit-tested for `mergeBlockOutcome`'s reason one level over: every way of being wrong here typechecks and looks identical on the page. It is also why `settleBlock` reads the row before it writes — the flat `error=?` it used to run wiped the guard note on every turn that did not itself fail. `decided` is `emitted_specs IS NOT NULL` and is on the DTO for the one distinction the count cannot make: `[]` is a turn that called the tool and named nothing, null is a turn that never called it. Every emitted run is a `workflow_instance_runs` row, so the instance budget guard, `stopInstance` and the second-press refusal all cover it with no new code.

**A block can land what the blocks in front of it built, and every protection that made `land.ts` safe stays where it is.** A merge block is a node whose `kind` is `merge`: no agent, no task, no template, no mount and no folder — it holds a strategy and one switch. When the instance reaches it, the runs its satisfied edges resolved to (the same `dependsOn` a run block would have been created with, so an orchestrator block's fan-out is covered with no second reading of what it emitted) go through `mergeQueue.enqueue` and nothing else. That is the whole design: one merge in flight for the process, every item re-previewed against git at *its* turn, a conflict reconciled on the run's own branch in a throwaway checkout, and `landRefusal`'s requirement that the operator's checkout be clean *and* on the recorded target **not weakened** — a dirty tree halts that repository and the block says so, because landing onto the wrong branch is the one mistake here with no undo. The target is never named on the node, for `worktree_base_branch`'s reason: a run records where it branched from, and that is where it goes back to. `mergeAutoResolve` is the one thing it can spend, and it is on the saved graph rather than in settings for `merge_queue.auto_resolve`'s reason — configuration that can change under a graph already running is not authorisation — so `enforceInstanceBudgetForBlock` is consulted **only when it is on**, since halting a graph at a free step would leave work already paid for unlanded for a limit that block cannot move. `mergeBlockOutcome` is the verdict, pure and unit-tested for `landRefusal`'s reason one level up: it decides whether the blocks *behind* the merge start, and both readings are silent — a chain that landed cleanly stopping with nothing to do, or a follow-up run starting on a target that never received the work. Its load-bearing distinction is skipped-versus-failed: a branch with no commits and one already merged both leave the operator with what they asked for, where a predecessor that *should* have had a branch and has none is isolation having degraded at run time, which is the case where silence would leave someone believing work landed. A merge block reuses `BlockStatus` verbatim rather than adding `merging`/`landed` — `thinking` and `emitted` are what every liveness query, every halt and both boot reconcilers key on, and two more words would be five more places to remember, one of them a merge running under an instance the page says is stopped; the page says "merging" and "landed", the column says what the machinery reads. An edge *out* of one carries no run at all (it created none), so its condition is the whole of what it says: `on-success` waits for every branch to land, `on-finish` is satisfied by the block finishing either way, and `blocked` — it never ran — satisfies neither, which is `edgeSatisfied`'s rule for a run that did no cycle. Two things are refused at *save*, where there is a person: a merge block on either end of a `continueBranch` edge (it has no checkout, so it has no branch to hand over or carry on) and one with no predecessor that runs something whose guards isolate — the second being the `fanOut` rule applied where it bites, since the alternative is a block that reaches the front of the graph and can only report that it was pointless.

**Acyclicity stops being a property of who wrote the graph, so it is checked as a property of the data.** `createRun` mints a run's id after reading its edges, which is why nothing could point at it and why a cycle was impossible by construction. That still holds for each individual insert — but the graph being inserted is now one a **model** wrote, and a cyclic set of specs has no creation order at all, so the first one would be refused for naming a run that does not exist rather than for the loop it is part of. `planEmission` therefore runs `dependencyCycle` over the specs and names the loop before anything is created, `admitDependencies` re-runs it over the whole live graph at every one of those inserts, and a spec may only depend on its siblings in the same emission — an edge onto a run the block did not create is an edge into a graph it cannot see.

**A block that emits nothing blocks what is behind it, and that is a decision rather than a fallout.** `planInstanceStep` is `releasableRuns` for the half of a graph that is not runs yet, pure and unit-tested for the same two silent failures, and it reads `edgeSatisfied`'s rule one level up: a dependency that did no work satisfies nothing. A block behind a fan-out exists to review it, land it or follow it up; started with nothing in front of it, it spends a billed cycle finding that out, where `blocked` costs nothing and names the block that decided there was nothing to do. Nodes behind an orchestrator block are **not created** at `startWorkflow` — their edges would name runs a model has not decided on yet — so each holds a `waiting` row in `workflow_instance_blocks` instead, which costs nothing for the reason `waiting` costs nothing one level down: no folder, no checkout, no place in the queue. A node is created only once every edge into it is *satisfied* rather than merely resolvable, so its edges are recorded on a run `admitDependencies` then re-checks, and a node that becomes a run gives up its ledger row so it is never in both tables. The cascade is the same fixed point `releasableRuns` uses, so every link gets its own sentence naming the one in front of it. `advanceInstances` is called from `releaseDependents` — one place rather than the five call sites that would have to be kept in step — and it is synchronous end to end for `createRun`'s reason, with a guarded UPDATE claiming each turn so two overlapping passes cannot both spawn one. A restart closes out **every** unsettled block of an instance it left nothing alive in, not only the ones behind a turn in flight: `on-finish` is satisfied by a run that did a cycle and then died with the container, so a block left `waiting` would be released into an unattended agent hours after anyone asked for it — which is `reconcileOnBoot`'s rule for a queued run. **Unless a member survived that same boot**, and that is `reconcileOnBoot`'s own exception rather than a second one: a `paused` run inside `settings.resumeGraceHours` is kept, because it is a run the operator started in a mode chosen precisely so it would carry on across a restart. Every premise above fails for the blocks behind it — nothing they are waiting for was closed out, the sweeper *will* wake it, and the agent the next advance starts is the one already being paid for and waited on. Closing them out anyway wrote off the tail of a live graph, under a sentence claiming the run in front of them had been closed out by the restart while it was parked and about to resume. So the question is asked per instance: `bootBlockPlan` is that decision, pure and unit-tested for `haltPlan`'s reason, and it reads `LIVE_STATUSES` rather than testing for `paused`, so what survives is decided in one place. It tests `started` **positively** rather than merely excluding a halt: a `stopping` instance's blocks still come down whatever its members are doing, and a `failed` one is `startWorkflow`'s own rollback, which wrote every other block off in the same pass — reviving half of either is a graph nobody finished building, started again. Ordering is what makes the survivors readable rather than guessed at — `src/instrumentation.ts` runs `reconcileOnBoot` first — and a spared block is decided later by `planInstanceStep`, off what is true when the member settles.

**A schedule is the first thing here that starts an agent with no person present at all, and every property that makes that defensible is somewhere else.** The run form, the chat's approval route and a workflow's Run button all have somebody pressing something at the instant the spend begins. A schedule keeps the press and removes the person, so what bounds it has to be true *before* it fires — and none of it is new machinery, which is the point. **Guards** come from the block's template or from `settings.chatDefaultGuards`, because a schedule calls `startWorkflow` and nothing else: there is no field on the wire, no argument on `putSchedule` and no column on `workflow_schedules` that could reach `--permission-mode`, a budget or an isolation choice, which is the same "there is nothing to raise it *with*" that already keeps an orchestrator block out of its own instance's budget. **The instance budget guard and the instance stop** cover a scheduled instance exactly as they cover a clicked one, for the same reason — it is the same `startWorkflow`, the same copy of the guard taken at instantiation, the same `stopInstance`. And **a workflow whose instance budget sets nothing cannot be scheduled**: `scheduleRefusal` is checked at the door, where there is a person and an error channel, and again at every fire, because clearing that budget afterwards is one edit away and nothing about that edit knows a schedule exists. Refusing rather than warning is `normalizeWorkflowInput`'s rule for an orchestrator block's fan-out cap, reused one level up and for the identical reason: a banner is read once, when the schedule is created, and the spend it is about happens every hour for the next month. Any one of the three limits is enough, and it asks `instanceBudgetIsOff` rather than naming a cost limit, because the two window fractions are the ones that bound *repetition* — an instance that would start into an already-spent window is refused at `startWorkflow`'s own door.

**A missed window is not made up, an overlap is skipped rather than queued, and both are on the page.** `decideSchedule` is that whole decision — fire, skip, missed, idle, paused — pure and unit-tested, because both ways of being wrong are silent and each is expensive in the opposite direction: a window fired twice bills twice with nobody watching, and a schedule that never fires is bit-for-bit what a working one looks like between occurrences. `cursor_at` is the last occurrence *decided about* rather than the last one started, and `reconcileSchedulesOnBoot` moves it to the instant of the boot without firing anything — the queued-run rule and the queued-merge rule arrived at from a third direction, that a server coming back up must not start unattended agents because of something that should have happened hours ago. `FIRE_GRACE_MS` is therefore only ever a late *tick*: two minutes, far shorter than the shortest recurrence this app accepts, so it can never honour a window a later one has superseded. An overlap is decided here rather than left to `startWorkflow`'s existing refusal — which still stands behind it — and it is a **skip**, never a retry, because a queued press of Run is a press nobody is present for by the time it happens; the cursor moves past it and the next occurrence is the next chance. Consecutive identical outcomes collapse into `streak`/`streak_since`, keyed on `last_code` and never on `last_reason`, since the sentence carries a count that moves and a streak breaking on that would be the fifty identical rows again with a counter stuck at one.

**The zone is stored with the schedule, and an unknown one is refused rather than replaced.** The container runs in UTC and the operator does not, so a wall-clock recurrence read in the server's zone fires an hour out for half the year — the failure this app already solved once for calendar buckets, where `/api/usage?tz=` carries the browser's zone. `isTimeZone` is split out of `resolveTimeZone` precisely because the two callers want opposite things from an unknown name: a bucket falls back to the server's zone, since a day cut an hour out is a display error in front of the operator, where a schedule refuses, since an hour out is an hour out for months with nobody looking. `nextOccurrence` solves a local time with the two-pass offset solve `zonedMidnight` uses, and on a spring-forward day whose nominal time does not exist it lands an hour to one side — which is the answer a schedule wants: the day still gets exactly one occurrence, within an hour of the time asked for, strictly between its neighbours. Returning nothing would silently skip one day a year, which is again indistinguishable from working. `everyHours` is deliberately an *interval* off an anchor rather than a wall-clock time, so it is DST-immune by construction and the zone only affects how it is displayed. The surface is three plain choices and no cron expression: `0 0 * * 1` and `0 0 1 * *` differ by one character and by a factor of four in what they spend, and a raw expression would first have to earn `describeSchedule`'s ability to render itself back in words. The page states the next fire time as an **absolute instant** beside those words, because a schedule the operator cannot verify at a glance is a schedule they will not trust with an unattended agent.

**One timer per process, `globalThis`-pinned, lazily started and stopped.** `sweepPaused`'s shape, for `sweepPaused`'s reason: module state that is not pinned silently resets on every request in dev, and an install with no schedules must hold no interval at all. It is started from the boot hook, from `putSchedule` and from a resume, and it stops itself the moment no active schedule is left. `currentSnapshot()` — the expensive half — is read only on a tick that actually fires. The boot start is inside `claimDataDir`'s `owned` branch with every other reconciler, and that is not tidiness: two servers firing one schedule is one window pressed twice, and the row they both read says nothing about whose it is. The cursor advances *before* the snapshot is awaited, so a tick that overruns cannot decide one window twice; the cost is that a process dying between the two loses that window with nothing recorded, which is the safe direction and the same one the boot takes.

**The chat's tools run in this process, and that is a correctness requirement rather than a convenience.** `/api/mcp` speaks MCP over HTTP by hand — `initialize`, `tools/list`, `tools/call` — and the handlers call `createRun`, `listTemplates` and `scanWorkspace` directly. A stdio MCP server would be a second process doing check-then-insert against the same SQLite file, which silently permits the two-agents-in-one-directory collision the folder claim exists to prevent. `workspace.ts` exists for the same reason in miniature: the picker and the chat must not be able to disagree about which folders exist or which are busy.

**The chat's child authenticates with a capability, never with `UF_AUTH_TOKEN`.** `middleware.ts` exempts `/api/mcp` because the edge runtime cannot reach SQLite to check a per-turn credential, so the route checks it itself — the exemption and the check must stay together, or the tool surface is public. The capability is minted per turn, written to a 0600 file rather than into argv (where `ps` would show it), and revoked when the child exits. It names a **subject** rather than a chat id, and that is a discriminated union rather than two optional ids on purpose: the subject is what decides which tool list the caller is offered, and a shape where both ids can be absent is a shape where the route can forget to check which it has. `telemetryEnv` does hand a child `UF_AUTH_TOKEN`, and that precedent was deliberately not followed: that token opens every route for as long as it is set, where this one opens a read-mostly tool surface — the two things it can write are a proposal and a template's prompt, neither of which does anything until a person acts on it — and dies with the turn.

**The chat runs with no tool allowlist, so the system prompt is the boundary.** It runs `--permission-mode bypassPermissions` with no `--allowedTools` and no `--disallowedTools`: an orchestrator's whole job is to find out enough to propose good work, and the allowlist this replaced — this app's tools, `Read`/`Glob`/`Grep`, read-only `gh`, `git log`/`status`/`branch`, `cd` — refused every question it had not anticipated (a build log, `gh api`, `git -C <path> log`, anything compound), which is a bad proposal an operator then approves believing it was researched. Not `plan`, which refuses MCP tool calls outright (measured: `Cannot call mcp__uf__list_templates while in plan mode`) and would leave the chat able to read GitHub and not this app; not `acceptEdits`, which holds mutating shell for an approval a `-p` child has nobody to give — the same failure `ISOLATED_GIT_TOOLS` exists to fix — so it would reproduce the refusals less predictably. What replaces the allowlist is `systemPrompt()`, which states the role rather than a list of forbidden tools: look, do not build; do not edit, commit, push, or act on GitHub; a task small enough to just fix is a proposal that says it is small. Everything that bounds this child is elsewhere and unchanged — nothing it can call starts a run, `--strict-mcp-config` keeps the mounted `~/.claude`'s MCP servers out, the capability token dies with the turn, `chatTurnBudgetUSD` caps the spend, and `--add-dir` still names only the mounts. The costs are real and are written down rather than absorbed: the chat can write into a checkout the operator also works in, and `githubEnv()`'s token now authenticates writes as well as reads. `permission_denials` is still read and shown in the thread — now because it should be *empty*, so an entry is the CLI declining something on its own.

**A chat turn is spend with no `evaluateBudget` behind it.** It passes the same gate a review does — `assistRefusal()`, the operator's own configured ceiling already spent — and nothing else, because there is no per-chat fraction and inventing one would be a threshold nobody set. `settings.chatTurnBudgetUSD` (default $2, null disables) is therefore the only other bound besides the ten-minute timeout, and it is enforced *inside* the CLI via `--max-budget-usd` rather than between cycles. `chat_sessions.cost_usd` is displayed on the chat page only: never added to `runs.spent_usd`, never to the meters. `githubEnv()` reaching this child is a real widening of "GitHub credentials reach a work cycle and nothing else" — a chat asked to read issues cannot without it — and is written down rather than absorbed quietly.

**A reopened run carries one message, resolved at the door and consumed at the spawn.** `reopenRun` writes the literal first-cycle prompt into `runs.follow_up`; `nextPrompt` prefers it over the continuation, and the loop clears the column the moment it hands it to a spawn — not after the cycle returns, because a run that parks or is killed from there on has already had it delivered and replaying it would say the same thing twice. Resolving to *text* rather than to a flag is what lets `completed` be reopenable at all: the substitution depends on the status the row is being picked up **from**, which a queued row no longer records. With no operator note, a run whose agent replied `DONE` gets `donePushbackPrompt` — the continuation prompt asks for `DONE` when the work is complete, so replying to a `DONE` with it is the same billed spin `continueAfterDone` already avoids — while `failed`/`stopped` get the continuation as before. **`completed` is not that reply**: it is also what a run that used up `maxIterations` is written as, and `maxIterations` defaults to 1, so keying the substitution on the status told the ordinary interrupted run that it had reported the task complete and then forbade it from starting new work. `runs.reported_done` records what the agent actually said, at the moment the cycle ends and the answer still exists — the stop reasons differ, but they are user-visible prose and not something to parse — and `reopenPrompt` is the one branch that reads it. Rows written before that column read as not-done, which is the cheaper error: a continuation into a finished session buys one billed cycle that says `DONE` again, where the pushback costs the work the run was reopened for. A note with no session to resume into is **appended** to the original task rather than sent alone: the run is starting over, and a reply-shaped note would read as the whole job. `nextPrompt` and `reopenPrompt` are pure and unit-tested for exactly these branches; every one of them is billed.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && !sawResult && finalText === ""`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind". It deliberately does **not** also require `pause_count > 0` — a session truncated mid-turn is truncated whether a guard parked the run or a crash ended it, and a run picked up by hand has `pause_count === 0`, so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for.

**A restart on top of existing work says so in the prompt.** `nextPrompt` takes `priorCycles` (read *before* the loop's increment) and, when it has to open with the task text on a run that has already been charged for cycles, prepends a notice naming the branch for an isolated run and the folder otherwise. Nothing else in that prompt refers to the earlier attempt — the conversation that held it is gone by definition — and an agent handed a bare task does the first thing it says, which is the work it is standing on. This is the floor under a restart, not a replacement for resuming: `DEFAULT_CONTINUATION_PROMPT` still restates nothing, because on a conversation that really is intact a restatement is spend for no information.

**`cancelled` is checked twice per cycle, and both matter.** Once before committing to a cycle (the top-of-loop check is separated from the spawn by a transcript scan that takes seconds, and `stopRun` has already promised no further cycle will start), and once after the child returns, *before* the exit-code test — a SIGTERM'd child closes with a null code that reads as `-1`, so testing the code first files every deliberate stop as `failed`. Likewise `runIteration` resolves on `exit` with a grace period, not on `close` alone: `close` waits for inherited pipes, and an agent that leaves a grandchild behind would otherwise hold its folder until the next restart.

**One writing run per folder subtree, unless the run is isolated.** A **paused** run holds two claims and yields one of them. Its **worktree slot** is absolute — it resumes onto the same branch carrying its own commits, so `activeRuns()` still selects `('queued','running','paused')` and `allocateSlotPath` still skips it. Its **folder** is not: `selectPromotable` reserves for `running` rows only, so a run submitted afterwards takes the folder and works while the parked one waits. Nothing is in the directory twice, because the parked run cannot come back until the folder is free — `sweepPaused` refuses to un-park it while a run is in there, and says so in its stop reason rather than leaving "waiting for the next 5-hour window" standing after that window cleared. It stays `paused` while it waits, deliberately: `paused` is what `reconcileOnBoot`'s grace exception keys on, and joining the queue instead would make a restart close it out. The cost is that a younger queued run can be promoted ahead of it in the ≤60s before the next sweep — accepted, because a parked run losing priority to work that is ready now is the point. `/api/folders` reports the two separately (`busyRunId` blocks, `parkedRunId` is a note), and a parked run has never consumed a concurrency slot. "Folder" means `(physical tree, path within it)` — `conflictKey()` — compared segment-wise and case-folded by `overlaps()`. Path equality is wrong three ways, all reachable from shipped config: the picker offers the mount root, which contains every folder under it; two mounts can be one host directory (compose defaults `UF_WORKSPACE_2..4` to `${UF_WORKSPACE}`); and macOS is case-insensitive. Mount identity is resolved once, at first use, because `/api/folders` annotates up to 400 folders per request and because a per-check `stat` that throws would fail **open**, permitting exactly the collision this prevents.

**The folder claim is a synchronous check-then-insert.** `createRun` runs from entry to INSERT with **no `await`**, so one event-loop turn covers deciding a folder is free and recording that it was taken. Adding a single `await` to that path silently reintroduces two agents in one directory; the `db().transaction()` wrapper does not save you, because better-sqlite3 is synchronous either way. Never key occupancy on `isRunning()` — `procs` is emptied at the end of every iteration, so it reads false while a running run sits in its pre-iteration scan.

**A restart must close out its own runs, except a recent pause.** `reconcileOnBoot()` (via `src/instrumentation.ts`) marks stale `running` rows failed and `queued` rows stopped. Without it one crash blocks a folder permanently. It **never signals a pid**: the DB outlives the container, so a recorded pid names something else after a restart — plausibly this server. Queued rows are stopped rather than resumed, because auto-starting a days-old prompt as an unattended `acceptEdits` agent is the one thing a queue must not do by itself. A `paused` row within `settings.resumeGraceHours` (default 24) is the deliberate exception: it is not an unreviewed prompt but a run the operator started in a mode chosen precisely so it would carry on across windows, and the sweeper re-evaluates its budget from scratch before anything spawns. Past the grace period it is closed out like any other stale row — that boundary is what keeps the exception from becoming the rule it exempts. A `running` row stays `failed` even under `live-resume`: the child is gone with unknown state, and mapping that to `paused` would be guessing. A `waiting` row is closed out like a queued one, and the reasoning is in the dependency invariants below.

**A run can be told to start after other runs, and while it waits it holds nothing.** `run_deps` is a join table rather than a `depends_on` column because fan-in is the case that matters — "after both of these" is a list with identity — and because the condition belongs on the edge rather than on the run: one dependent can reasonably want "only if that one worked" from one dependency and "once that one is out of the way" from another. `waiting` is a status rather than a flag on `queued` precisely for what it must *not* hold. `activeRuns()` cannot see it, so it reserves no folder, takes no checkout slot, spends no concurrency slot and has no place in line. That absence is the whole design: a `queued` run reserves its folder against everything younger — deliberately, or a run on the workspace root is overtaken for ever — so a four-run chain admitted up front as `queued` would stall every unrelated run on that repository for the length of the chain. Isolation is planned at *release* rather than at admission for the same reason: choosing a checkout slot is claiming it, and a run that may not start for days must not hold one. `isolate: false` is the one thing recorded at admission, because that is the operator's own answer and the release must not overrule it — everything else (`work_dir`, `repo_root`, the branch, the base commit) is null until `admitWaiting` fills it in, which is also why a waiting row is invisible to `landState` rather than a branch with nothing on it. `continues_run` is the second, and it is not an exception to any of that: it names a run rather than claiming one, and the isolation invariants below say why the landing rules need it before there is a branch to see.

**A dependency succeeds by reaching `completed`, and a run that never ran a work cycle satisfies nothing.** The first half is the choice `reopenPrompt` already forced once: `completed` is written both for a `DONE` reply and for a run that used up its cycle cap, and `maxIterations` defaults to 1, so keying success on `reported_done` would mean a dependent almost never starts and the chain would terminate saying "it did not report done" about a run that did exactly what it was asked. Success here is the *absence of a fault* — no crash, no guard, no operator stop — which is the question a person chaining two runs is asking; `reported_done` is on the DTO for anyone who wants the stronger reading and decides nothing here. The second half is what makes a chain terminate rather than sit there: a guard refusing a run at the door, a run whose own dependency failed, a run stopped before it started and a run closed out by a restart are all terminal with `iterations === 0`, and reading `on-finish` as "any terminal status" would start the next run on the strength of a run that never opened a file — and would leave a `blocked` run satisfying its dependents, so nothing would ever end the chain behind it. Both conditions are named explicitly on the wire and neither is defaulted, because a silent default is wrong half the time in both directions: `on-success` terminates a chain the operator meant to run regardless, `on-finish` starts a run on top of a dependency that crashed.

**A dependent that can never start is terminated with a sentence naming what stopped it, and so is everything behind it.** The status is `blocked` — the one this app already writes for a run refused before its first work cycle, and the true thing to say: nothing ran, nothing was spent. `releasableRuns` is the whole decision and it is pure and unit-tested for exactly this, because both failure modes are silent: a run released too early starts on top of work that has not happened, and a run neither released nor terminated sits `waiting` for ever holding a prompt the operator believes is queued. The cascade is a fixed point rather than a graph walk — a run blocked in one pass is a settled dependency that ran no cycle in the next — so every run in a chain gets its own reason naming the run *in front of it* rather than one shared verdict about a run at the head it never heard of.

**A loop is refused at admission, because nothing downstream of it would ever be woken or ended.** `releasableRuns` reaches a fixed point and leaves a cyclic set alone, which is precisely the row nothing wakes; admission is the only moment an edge is created, so it is the only place this can be caught. `dependencyCycle` names the loop, and a self-reference is reported as the one-run loop it is. `createRun` cannot construct a cycle today — it mints the run's id *after* reading the edges, so nothing can already point at it — and the check is what keeps acyclicity a property of the data rather than of who happens to write it.

**Every terminal transition wakes the dependents, and a boot deliberately does not.** `releaseDependents` is called from `startRun`'s `finally`, from both of `stopRun`'s pre-spawn branches and its new waiting branch, and from the sweeper's never-clearing verdict — missing one leaves a dependent asleep with nothing that will ever wake it. Released runs join the queue rather than starting there, so folder reservation, FIFO order and the concurrency cap stay in `promoteQueued`, the same reason `sweepPaused` re-queues instead of calling `startRun`. `reconcileOnBoot` is the exception and needs both halves of its reasoning: what a waiting run is waiting for is a row that same boot has just failed or stopped, so releasing it would promote a days-old prompt into an unattended agent that accepts edits — the queued rule arrived at from the other side — while leaving it alone would strand it on a dependency that is now terminal and can never satisfy it. So it is closed out, before the rest of the loop, so no transition that loop makes can find a waiting row to release.

**An isolated run is granted the two git commands it is ordered to use.** `acceptEdits` — the default the run form and `chatDefaultGuards` both start from — auto-approves file edits and read-only shell, and holds mutating git for a human: `git add` and `git commit` each come back `This command requires approval`, and a `-p` child has nobody to give it. So the isolation preamble told the agent to commit as it went and the permission mode made that impossible. Measured, not reasoned: four runs finished `completed`, on their own branches, each having tried to commit and been refused, with the whole change left uncommitted in a worktree that `landState` then read as a branch with nothing on it. `buildArgs` therefore passes `--allowedTools Bash(git add:*) Bash(git commit:*)` for `isolation === "worktree"` only — additive, so everything else still follows the mode, and verified against the real CLI along with the fact that `--allowedTools` does not restrict what it does not name. Not `bypassPermissions`, which would also hand the run the network and `rm`; and not for a run in the operator's own checkout, which is told nothing about committing.

**A refused tool call is reported, because the alternative is a run that looks like it chose not to.** The `result` event carries `permission_denials` (confirmed on the wire for `stream-json`, not only for the `--output-format json` that `chat.ts` reads), and `permissionDenials()` groups it by tool *and command* — every entry's `tool_name` is the bare `Bash`, so "Bash ×7" would say nothing. This is the line that turns the failure above from a transcript-archaeology exercise into a log entry.

**A run can be told to carry on the branch its dependency was working on, and what it claims is the branch rather than the checkout.** `run_deps.continue_branch` is the operator's request and `runs.continues_run` is the resolved decision — the same split `isolate` and `isolation` already make, and the second one exists because `ensureWorktree`, `landState`, `nextPrompt` and the run page all need one greppable column rather than a join. It is on the *edge* because only an edge can say which dependency hands the branch over; a fan-in has several, and at most one may set it. Unlike every other isolation column it is written at **admission**, while the run is still `waiting` and still holds nothing: it is an id and a statement of intent, it costs nothing, and the landing rules have to be able to see a chain coming before its branch exists — a dependent's `worktree_branch` is null until it is released, so a chain read off the branch column reports one link right up until the second one starts, which is exactly the window in which the first looks landable and is not. Two runs continuing the same predecessor is refused at admission: it is two runs on one ref, which git will not check out twice and which leaves the landing rules with no last link to name. Picking a failed continuation up again is `reopenRun`'s job, and that keeps a chain a path.

**A continued branch takes the chain's base, never the predecessor's tip.** `resolveIsolation` is the whole decision — pure, unit-tested across the three modes, and separated from `planWorkspace`'s syscalls for the reason `selectPromotable` is separated from the spawn: both ways of being wrong land on disk and neither throws. `worktree_base` is what `diff.ts`, `review.ts`, `emitHandoff` and the merge itself all measure from, so anchoring on the predecessor's tip would show and land only the last link, with the earlier agents' commits invisible in the review and missing from the patch. `worktree_base_branch` is copied forward for the same reason: the chain lands where it started, not where the folder's HEAD has since got to. The one asymmetry that matters is the error channel — an ordinary run that cannot be isolated degrades to `mode: "none"` with a reason and still does the work in the folder, serialised, while a continuation that cannot be honoured **throws**. Degraded the same way it would silently commit to the target branch with the predecessor's work nowhere in sight, which is the exact failure this mode exists to prevent, so every one of them is a sentence naming what is missing.

**The chain claims a branch, not a slot, and that is what makes an unrelated run taking the checkout harmless.** A fresh branch is named from its run's own id, so no other run can ever mint it and a continuation only ever adopts one it was pointed at. The predecessor's slot is preferred and is taken in the same event-loop turn that records it — the property `createRun` already documents — so nothing interleaves between reading `activeRuns()` and joining it, and `allocateSlotPath` skips it from then on. When an active run does hold it, a fresh slot is used and git attaches the existing branch to it: that run took a slot `allocateSlotPath` had already found *clean*, so no uncommitted chain work is ever stranded behind, and it moved the slot off this branch with `checkout -b`, so the branch is free. If it has not got that far, `worktree add` refuses by name rather than branching from somewhere else. `ensureWorktree` therefore takes the third path at each of its three forks — `checkout` rather than `checkout -b`, `worktree add <path> <branch>` rather than `-b`, and past the orphaned-branch guard rather than into it. That guard loses nothing by it: it exists because `-b` would create a *second* branch at the base and leave the run's commits on a ref nothing points at, and attaching to a branch that already exists cannot orphan anything. Its other half is kept as `requireBranch` — a branch `purgeBranch` has destroyed is refused by name, because a `worktree add` there would quietly create a fresh one and produce a run that looks like it is continuing work and is in fact starting over.

**A handed-over checkout keeps what the predecessor left uncommitted, and says how much.** `commitRefusal` already settled whose work is in a slot: it belongs to the run whose branch the slot has checked out, and for a continuation that is this chain. So it is inherited rather than refused — the alternative strands a chain on a directory state the operator has a button for and no reason to look at — and the count goes in the run log and into the agent's own preamble, because silently inheriting somebody else's half-finished edits is the part that would be surprising. A run resuming its *own* checkout is told the old sentence: `iterations`/`pause_count` are what tell a hand-over from a pause, since a continuing run that has worked is resuming its own tree whatever it started from.

**One branch, one Land button: the last run on it, and only once nothing behind it can still commit.** Three runs extending each other share a ref, so every one of them would offer to land it — the operator merges the first, the second still reads unmerged because the branch has moved, and the merge queue takes the same branch once per link. `landRefusal` is where that is decided, pure and unit-tested for exactly this, and both refusals **name a run**: a greyed-out button on a page whose whole purpose is getting work merged is a dead end. The owner is the last member that is not terminal-with-zero-cycles, which is `edgeSatisfied`'s rule reused — a dependent blocked because its dependency failed is recorded on the branch and put nothing on it, and letting it own the branch would leave the run that did the work unlandable for ever. `waiting` counts as unsettled here and nowhere else in this app: it holds no folder and no checkout, but it is a declared future commit on this exact ref. `deleteBranch`, `purgeRefusal` and `resolveConflicts` take the same test through `chainBlocker`, because all three were written when "this run's branch" picked out a branch and a chain is what stopped that being true — the first two would destroy the starting point of a run that has not begun, and the third would pay for a resolution against a branch another run is about to move. `branchInventory` collapses to the owner for the same reason and not merely to tidy the page: that table keys its rows on the branch, so a three-link chain was three rows with one React key, three Land checkboxes and identical counts, and picking two of them queued one branch twice. It is deliberately the only place here that decides a chain from `worktree_branch` rather than from `continues_run`, so a `waiting` link — which has no branch yet — is invisible to it and a row can read landable while a run is queued up behind it. That is `canLand`'s existing approximation, and `landRun` re-derives the whole verdict from git and the full chain before anything merges.

**A continuing agent is told whose commits it is standing on.** A different case from `priorWorkNotice` and the difference decides what it does: there the work is the run's own and "carry on from where you stopped" is right, here it is a separate agent's, there was never a conversation to resume, and the branch is the only record. Handed a bare task it does the first thing the task says, which is work already committed under it. `continuedWorkNotice` names the branch, the predecessor and the two commands — `git log --oneline <base>..HEAD` and `git diff <base>...HEAD`, the same range the run page's diff and any review are measured over, so the agent, the reviewer and the merge all look at one thing. The facts are generated and only the guidance is `settings.continuedWorkPrompt`: a placeholder an operator can delete is a notice that can silently stop naming the branch. Both notices render when both apply, branch history first — read the other way the agent meets "carry on from where you stopped" before it has been told the work is not its own.

**An isolated run works on a branch, and a worktree contains committed work only.** `seedWorktree` copies the gitignored config files named in `settings.isolationCopyGlobs` and nothing else — dependencies are the agent's job, and slot reuse is what makes that cheap. The handoff card withholds the `git merge` command entirely while the operator's own checkout is dirty rather than showing it with a caveat, because a copyable command gets copied.

**The tool does now merge, and every protection the old "never merges" rule bought is a check in `land.ts` rather than a caveat.** The operator's checkout must be clean (unreadable counts as dirty, same rule as `emitHandoff`) *and* standing on the recorded target branch — landing onto the wrong branch is the one mistake here with no undo, so it is refused by name rather than caveated. An active run's branch is never landable: `running`/`queued`/`paused` can commit again, and the base that merges cleanly now will not be the base in ten minutes. A failed merge is aborted immediately and the conflicting files reported, so a half-merged index never survives the request. `landRefusal` is pure and unit-tested for exactly these branches, because it is the decision that writes into a directory a person also works in.

**Finding out whether a merge works must cost the operator nothing.** `merge-tree --write-tree` does the three-way merge in memory — no checkout, no index, only unreferenced objects in the object store — so the preview is honest *before* any decision. It needs git ≥ 2.38; an older git reports `unknown`, never "clean". `parseMergeTree` treats every exit code other than 0 and 1 as undetermined for that reason. Those unreferenced objects are also what makes the conflicting *content* free: the tree it writes holds each file as a real merge would leave it, so `withRegions` reads the `<<<<<<<` blocks straight out of it — capped at `MAX_CONTENT_FILES`, since this runs on every load of the land card. A file past that cap keeps `regionsRead: false` rather than an empty list, because "not looked at" and "nothing there" are different sentences and a modify/delete really does leave no markers.

**What conflicts comes from the stage records; why comes from the messages, and only the first is trusted.** `-z` is what makes the conflict type readable at all — the plain output states it only in prose, and finding the path in "CONFLICT (content): Merge conflict in f.txt" means parsing a filename out of a sentence, which is the mistake `splitPatches` exists to avoid. But the informational section's field layout was captured from git 2.50 and the container ships 2.39, so it is parsed defensively and contributes nothing but annotation: an unreadable one loses the type and the explanation and still lists every conflicting file. A message naming a path the stage records did not is **ignored**, never added — what counts as conflicting is what `landRefusal` counts, and that must not shift with a prose format.

**A resolution is shown as what it did, not only as what it said.** `run_reviews.resolved_commit` is read off the isolated checkout the moment the merge commits, because that checkout is removed seconds later and the commit is the only handle on the work afterwards; `resolved_paths` is recorded at the same time so the display is the resolution rather than everything the merge brought across. `resolutionChange` diffs that commit against its **first** parent — the branch as it stood — which is the one framing that never comes back empty: a `--cc` combined diff shows nothing at all for a clash settled by taking one side whole, and "the resolution changed nothing" is exactly the wrong thing to tell someone about to land it.

**Several branches are a queue, never a batch, and the queue re-decides at every turn.** `mergeQueue.ts` reverses the "one button per run" rule, and earns it by keeping what that rule protected: one merge in flight (a single sequential worker, one per process), and `landRun` re-deriving the whole `LandState` for every item at *its* turn rather than trusting the answer the page had — each landing changes the base for the one behind it, so a preview taken when the queue was made is worthless by the second item. `position` is the operator's order and the only thing that decides what runs next; `created_at` would silently reorder two rows queued in the same millisecond.

**A queue tells a branch's problem apart from the checkout's.** `planItem` returns `fail` for the first — the branch behind it is unaffected — and `halt` for the second, which marks every remaining row *in that repository* skipped with one reason instead of scrolling ten identical refusals past. It therefore tests the checkout **before** the conflict, the one place it deliberately disagrees with `landRefusal`'s ordering: that function answers "why can this not be landed", where the conflict is the fact about this branch; this one answers "what should happen next", and paying a model to reconcile a branch into a checkout that will refuse the merge anyway is money spent on nothing.

**Auto-resolution is authorised per batch and recorded per row.** `review.ts` says nothing automatic may reach it, because spend nobody asked for is spend nobody authorised — queueing with the toggle on *is* that authorisation, which is why `auto_resolve` lands on every `merge_queue` row rather than in `settings`, where it could change under a queue already running. `POST` reads it as `=== true` for the same reason `continueAfterDone` does. A refusal that is about the operator's *window* rather than about the branch stops later resolutions being attempted at all: it will refuse every one of them identically, and each attempt costs a full transcript scan to find that out again.

**A queued merge is cancelled on boot, never resumed.** Same rule as a queued run, for a stronger reason: this one writes into the operator's own checkout, and a server coming back up and merging four branches into the tree someone is working in is the one thing a queue must not do by itself. A row caught mid-merge is failed without a guess about what happened — `landState` will say, from git, the next time anyone asks. Cancelling a batch leaves the row *in flight* alone: a merge is a multi-step write and a resolution is a child holding a checkout, and interrupting either part-way is worse than the second it takes to finish.

**The merge target is recorded, never assumed.** `worktree_base` is a *commit*: it says where a branch started, not where it belongs. `probeIsolation` now also records `worktree_base_branch`, and a detached HEAD stores null rather than the literal `HEAD`. Rows written before that column existed fall back to the branch currently checked out — but only after proving the run's base commit is an ancestor of it, which makes it a deduction, and `targetInferred` says so in the UI.

**A squash is landed work that git cannot see.** Squashing rewrites the commits, so the branch is never an ancestor of its target and `merged` is false for ever — which would both offer it for landing a second time and leave it undeletable. `landed_tip` records the branch tip at land time; `landedUnchanged` (tip unmoved) is what stands in for ancestry, and it stops being true the moment the branch gains a commit, which is exactly when deleting would lose something. Branch deletion uses `-d` wherever git can see the merge itself and `-D` only in this case.

**Work an agent left uncommitted goes onto its own branch, and nowhere else.** `commitPending` exists because that state is reachable and its symptoms point the wrong way: before `buildArgs` granted `git add`/`git commit` to an isolated run, every such run ended `completed` with a full checkout and an empty branch, which the land card reported as "this branch has no commits of its own" — a run that looks like it did nothing. It is also what frees the slot, since `ensureWorktree` refuses to reuse a checkout with work in it. The decision is `commitRefusal`, and the branch that earns the unit test is the slot one: a slot is reused, so what is uncommitted in it is only this run's while it still has this run's branch checked out — otherwise the commit lands one run's work on another run's branch, authored by nobody. `add -A` rather than the listed paths, because gitignored files stay ignored and a file written since the page loaded belongs to the same work. A failed commit is left **staged** rather than reset: a `pre-commit` hook is the likely refusal, and the agent may have staged part of it itself. `git status --porcelain` is the one output in this app that must not be trimmed — `" M path"` opens with a space that means "unstaged", and `git()` takes `trim: false` for it alone.

**Getting rid of a branch is two doors, and only the careful one is called Delete.** `deleteBranch` still refuses anything git cannot see as merged — that refusal is all that stands between a stray click and work that exists nowhere else — and `purgeBranch` is the deliberate other one, for the attempt that went nowhere and the slot it is holding hostage. It destroys committed work by design, so the caller has to **name the branch back**: that echo is not authentication and never selects anything (the row still decides what is deleted), it is what stops a request aimed at one branch from landing on another, and what forces the interface to spell out what goes. It force-removes the checkout, which `deleteBranch` will not do, and counts the commits and the uncommitted paths *before* anything is removed so the sentence afterwards says what was lost. Neither door is offered for an active run, and the UI never shows both at once.

**A conflict is resolved on the run's branch, never in the operator's checkout.** `resolveConflicts` merges the *target into the branch* — the opposite direction from landing — inside the run's own checkout when it still holds that branch, and otherwise a throwaway `<slug>-resolve` slot that is removed either way. A resolution that goes badly therefore costs a branch nobody has landed yet. The agent resolves **text only**: it runs `acceptEdits` (not `bypassPermissions`) and is told not to run git, because the app stages and commits *after* checking that no marker survived. `unresolvedFiles` treats an unreadable file as unresolved, and any failure ends in `merge --abort` with the branch exactly as it was — an agent that reports success having left `<<<<<<<` in a file is the specific failure this ordering exists to catch. When it succeeds the branch contains the target, so landing becomes a fast-forward and still goes through every check above. `hasConflictMarkers` matches only the two labelled markers, never a bare `=======`, which is a markdown heading underline.

**Reviewing a diff is not a work cycle and is never automatic.** `startReview` exists only behind a POST; nothing in the run loop reaches it. It refuses when the operator's *own* configured ceiling is already spent (`guardFraction >= 1` on either window) rather than going through `evaluateBudget` — there is no per-run fraction for a review and inventing a threshold would be a limit nobody set. The reviewer is given the diff, the run's task and how the run ended, but **not** the event log: the log is the process rather than the outcome, and a reviewer that reads how the agent got there reviews the journey. A large diff is cut at a file boundary and the omitted files are *named* in the prompt, because a reviewer handed a third of a change with no marker writes a confident review of a change that did not happen.

**GitHub credentials reach a work cycle and nothing else.** The container has no other way to authenticate — the `~/.claude` mount carries Claude's login and neither `~/.gitconfig`, `~/.ssh` nor `~/.config/gh` — so `git push`, `gh pr create` and `gh issue view` all fail, and they fail *inside a tool call the run loop never inspects*: the cycle simply ends without the pull request. `githubEnv()` is where the token is turned into an environment, mirroring `telemetryEnv()`, and it sets three things because the failure arrives three ways: `GH_TOKEN`/`GITHUB_TOKEN` for the CLI, a credential helper for `https://github.com` for plain git, and `url.…insteadOf` rewriting `git@github.com:` to HTTPS because no key and no agent reach this container — that last one is the likeliest reason this fails on *some* repositories and not others. It travels as `GIT_CONFIG_*` rather than a config file, so it applies to every git the agent runs and dies with the process instead of outliving the run in a mounted tree; the helper list is **reset** first, because a repository cloned on the host can name `osxkeychain` in its own config and git consults helpers in order. The helper reads `$GH_TOKEN` at call time rather than embedding the token, so `git config --list` does not print it. `GIT_CONFIG_COUNT` must equal the number of key/value pairs — git discards the entire block otherwise, silently, which looks exactly like the unauthenticated container this exists to fix. Withholding is by namespace, not by remembering: `gitEnv()` and `reviewEnv()` strip `UF_*`, so the reviewer (which cannot write) and this app's own git (whose children run repository-controlled hooks, and which never touches the network) are excluded by construction.

**Diffing runs repository-controlled code unless it is told not to.** Every `git diff` here carries `--no-ext-diff --no-textconv`: `diff.external` and a `diff.<driver>.textconv` reached through `.gitattributes` are both *commands git runs*, configured by the repository being rendered. Same class as the `core.fsmonitor` clearing that already applies to every call. Paths that come back from git and go out again as pathspecs are pinned with `:(top,literal)`, or a filename containing `*` would be read as a glob.

**A diff that was shortened says so.** The file *list* is always complete; patch bodies are budgeted (`selectForPatch`), and what the budget leaves out is counted and rendered as "N files listed without contents" rather than dropped. `splitPatches` matches chunks to files **by position**, never by parsing the header path — git re-quotes odd filenames there — and a count mismatch yields no patches at all rather than hunks filed under the wrong name.

**The UI says "work cycle", the code says "iteration".** User-facing copy names the unit a first-time user must reason about; `Settings`, `BudgetPolicy`, the API payloads, and the `runs` table keep `iteration`/`maxIterations`. Don't rename the internals to match the copy, and don't reintroduce "iteration" into the UI.

**Every budget rule can be switched off, but the loop must always have a monotone terminus.** `null` means "no limit" for cost, tokens, duration, and both fractions — `normalizePolicy` maps `null`/`""`/`0` to `null` rather than to a default, so a blank field disables a guard instead of quietly restoring one. `maxIterations` is nullable too, but only alongside `maxDurationMinutes`: those two are the only quantities that move one way and keep moving. This run's own spend stops accruing the moment a cycle is killed before it reports, and both window fractions can *fall*. The pair is enforced in `POST /api/runs` (which has an error channel) and refused again as `no_terminus` in `evaluateBudget`; `normalizePolicy` must stay total and idempotent, so it never rejects — and never coerces the illegal pair into a limit the user did not ask for. Only an explicit `null` asks for an uncapped loop; blank, zero, negative and missing all still mean one cycle.

**`continueAfterDone` sends the agent back in after `DONE`, with a different prompt.** It must be `settings.donePushbackPrompt`, never `continuationPrompt` — that one says "if it is fully complete, reply with exactly DONE", so feeding it back after a DONE produces an immediate second DONE and a tight, billed spin loop. The flag is read as `=== true`, not `Boolean(...)`: it makes a run refuse to stop, so a string `"false"` off the wire must fail safe.

## Security-critical paths

- `resolveInMount()` (`orchestrator.ts`) checks containment on the lexically resolved path **before** touching the filesystem, then **again** after `realpathSync` — a symlink inside the root can still point out of it. Both checks are load-bearing. `resolveWorkspaceFolder()` runs that pair against **one mount at a time**; multiple mounts widen which roots are legal, never what counts as contained. A run is confined to the mount it started in.
- Containment stays **per mount**, while collision detection is deliberately **cross-mount**: `conflictKey`/`overlaps` see two mounts onto one directory as one folder. Widening what counts as a collision never widens what a run is permitted to touch.
- Worktrees live at `<mountRoot>/.uf-worktrees/<repo>-<slot>` so the unmodified `resolveInMount` validates the agent's cwd. `ensureWorktree` `lstat`s that directory and refuses a symlink **before** git writes — validating afterwards would mean a full checkout had already landed wherever the link pointed.
- The agent is spawned with an argument array and `stdio: ["ignore", "pipe", "pipe"]`, **never a shell**, so prompt metacharacters are inert. `gitSync` does the same, and additionally strips `ANTHROPIC_*`/`UF_*` from the child environment and clears `core.fsmonitor`: both `worktree add` (via `post-checkout`) and `status` (via fsmonitor) can execute repository-controlled commands.
- `gitArgs` also passes `safe.directory=*`, and the image sets it system-wide for the agent's own git. This is a deliberate waiver, not an oversight: a bind mount carries the *host* uid, and git's ownership refusal reaches `probeIsolation` as an unreadable repository — indistinguishable from "not a repository", so isolation would switch itself off and say the wrong thing about why. The check guards against repositories encountered by surprise on a shared host; every path that reaches `gitSync` has already been proved inside a configured mount by `resolveInMount`, which is the containment guarantee that actually matters here. Keep it paired with `UF_UID`/`UF_GID` in compose — the waiver makes git *work* against a foreign-uid mount, it does not make the mount *writable*.
- `UF_GITHUB_TOKEN` is scoped twice over. It reaches only the agent's work cycles (`githubEnv()`), and the credential helper it installs is keyed to `https://github.com`, so a repository whose submodule or remote points at another host asks for credentials and gets none — with `GIT_TERMINAL_PROMPT=0` alongside it, that fails in a second rather than hanging until the run's duration limit.
- `permissionMode` is narrowed against the four literals in `POST /api/runs` before it reaches `--permission-mode`.
- **A specialised agent is not a capability surface, and the absence of two columns is what enforces that.** `--agents` members accept a `tools` array; `normalizeAgentInput` refuses one by name and the `agents` table has no column for it, and none for a permission mode either — so the routes to `--permission-mode` stay the two they were, and no chat proposal, workflow block or emitted spec can reach one by naming an agent. Two things follow that are worth not re-deciding by accident. The deny list is the one that matters: `PROCESS_KILLERS` is `--disallowedTools`, deny is *verified* to beat `--permission-mode`, and whether it would also beat a member's own `tools: ["Bash"]` is **not** verified — which is why the field is refused rather than stored and narrowed. And what a child may delegate to is never taken off the wire: `resolveAgentForRun` accepts an **id** and looks the definition up, so an agent that nobody saved cannot be assembled in a request body.
- **Reading an agent definition off disk is scoped, and only the scope that needs no path is on the wire.** `listAmbientAgents` walks `$CLAUDE_CONFIG_DIR/agents/**` and, for a caller that has already resolved a folder, that folder's `.claude/agents/**`. `GET /api/agents` and `/api/usage` pass no folder and report the user scope alone — not because the project scope is secret, but because taking a directory off a request would be a second path-resolution surface beside `resolveInMount`, for a payload that only feeds a sentence on a page. Nothing in that walk bounds what a child may do; the definitions it finds already reach every child, mounted from the operator's own `~/.claude`.
- **An agent cannot select processes by name to signal them.** `buildArgs` passes `--disallowedTools Bash(pkill:*) Bash(killall:*)` on every spawn — a deny rejects the whole Bash call, so a `pkill` buried in a `;`-chain takes the chain with it, which is the form the incident arrived in — and `--append-system-prompt` carries the reason *and the safe recipe*. The deny alone buys one turn, since `kill $(pgrep -f next-server)` is not `pkill` and is exactly as fatal; a bare prohibition buys the opposite failure, a dev server nobody can stop holding its port for the life of the container. So the notice spells out pid capture, the `pgrep -P` child form, and selecting on the port rather than the title. Next renames this server's process to `next-server (v…)`, which is *also* the title of any dev server an agent starts to check its work, so a name match cannot tell the two apart and reaches whichever was there first. One `pkill -f "next-server|next dev"` ended the container (`restart: unless-stopped` brought it back) and `reconcileOnBoot` marked fourteen runs failed 690ms later, including the run that issued it. There is no ownership boundary to enforce this with instead: compose runs a single uid. Plain `kill` stays permitted — a pid is a handle on a process the agent started, a pattern is a guess about the machine — and denial survives `bypassPermissions`, which is the only reason the argv is worth anything here.
- `src/middleware.ts` runs in the **edge runtime**: it reads `process.env.UF_AUTH_TOKEN` directly and must not import `lib/config` (which pulls in `node:os`/`node:path`). Comparison is constant-time; API paths get 401, page paths redirect to `/login`. `/api/mcp` is the one exempted path, and it authenticates itself — removing the check there makes the chat's whole tool surface public.
- The chat's capability token is compared constant-time against every live token in `chatForCapability`, rather than looked up by key: a `Map.get` on a secret leaks its prefix through timing. The live set is the number of turns in flight, which is one.
- `bypassPermissions` is offered in the new-run form with a warning; the default stays `acceptEdits`.

## Conventions

- **Server-only vs client.** `src/lib/apiTypes.ts` holds the DTO mirror of the server types so client components never transitively import `node:fs`. `src/lib/format.ts` is likewise client-safe. Don't import `windows.ts`/`transcripts.ts` types into a `"use client"` file — add to `apiTypes.ts` instead.
- **Route handlers** that touch SQLite or the filesystem need `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`. Every existing data route has both.
- **Module state survives dev hot reload** via `globalThis` singletons: `__ufDb`, `__ufBus`, `__ufProcs`, `__ufCancelled`, `__ufTranscriptCache`. New long-lived state must follow the same pattern or it silently resets on every request in dev.
- **Schema changes** go in `migrate()` in `db.ts` as idempotent `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements — there is no migration framework or version table.
- **Pages are client components** that poll their API route (dashboard 10s, run detail 3s for the row while SSE carries the log). There is no server-side data fetching or React Server Component data layer.
- **A run's page is a split view, and the pane shows one thing at a time.** The inspector on the right holds what the run *is* — state and the one control that acts on it, spend, work cycles, guards, telemetry, its checkout, its task — and is `lg:sticky` with its own scroll region, so it stays put while the pane scrolls. Column and row are placed explicitly rather than left to source order, because on a narrow window there is one column and the state is what the reader came for. The pane holds what the run *produced*, behind a `SegmentedControl`: log, report, changes, review, land. Three rules on it. **The log leads and nothing switches tabs on its own** — a run that finishes while you are reading one pane must not move you to another, which is the same reasoning that freezes the old log's open/closed state at the first status seen. **A tab is offered only when there is something behind it**, which is why `cycleOutputs` runs on the page rather than inside `RunOutput`: the bar has to know whether the agent said anything before it offers a Report tab, and two walks of the same event stream per paint is what the alternative costs. **Only the active tab is mounted**, so Changes re-reads the repository each time it is opened — the same cost as loading the page, against four polling cards alive behind the one being looked at. The guard block draws each configured limit as a `Meter`, and the spend one keeps the display-versus-guard split the windows already make: `runs.spent_usd` is the solid fill and the killed-cycle estimate is the hatched band past it, never one summed fill, so the bar shows the threshold that will actually stop the run without presenting the estimate as a correction to what the CLI measured. The time bar reads `finished_at` where there is one, since the clock only ticks while a run can still move. On the runs list, the cycle in flight is a **column of its own** on the in-flight list and nowhere else, and `fmtCycleInFlight` is the only thing that decides it, wording included — for the reason that function documents, and separated from the completed count for the reason the wording says "in flight". That list's box is deliberately not a scroll container: the sticky header then pins to the content pane as the page scrolls, where a wrapper of its own would pin it to a box that never moves.
- **The chat's transcript says who is speaking with structure, never with colour.** The answer is the pane: plain prose at a readable measure with nothing drawn round it, because it is what the reader came for. The operator's own words are a bezelled block pulled right — the raised chip every secondary control here wears — and were an accent-tinted bubble, which is the web-chat idiom and which spent the app's one accent saying "a human typed this", a fact the position and the speaker label already carry. A `system` turn is this app speaking and keeps its own treatment, because a sentence about what the app did, rendered as though the model said it, is one the operator will later attribute to the wrong party. Proposals are rows of one grouped box and selection is a `--selection` wash rather than a border, since a row that gained a border would shift the two beside it; the action row puts the one default action at the right edge, where every `Sheet` here already puts it, and Select-all at the other end because it is not a decision about the work. Everything that makes a proposal card approvable is unchanged and must stay: the guard set spelled out (including the untemplated one), a rewritten prompt marked, the dependency order named, what the click starts counted in words, and the **explicit list of the ids the page displayed** on the wire. The composer is pinned to the foot of the pane and takes **⌘↩** as well as Enter — ⌘↩ is the chord the run form already commits with and the one the shell's keyboard layer deliberately binds to nothing; the `isComposing` guard is tested *after* it, because an IME composition can only be ended by a bare Enter. The waiting state stays legible frozen (`@layer base` flattens the spinner to a still, and the word and the clock beside it never moved), and it claims no progress it does not have: elapsed time is the only real measure of a turn.
- **The shell is a window, not a page.** `src/components/shell/` holds all of it — `AppShell` (the frame, and the app's one keyboard listener), `Sidebar`, `Toolbar`, `QuickOpen`, `panes.ts`, `shortcuts.ts` — and `layout.tsx` does nothing but the theme script, the skip link and `<AppShell>`. There is no centred column: the source list is fixed-width and full height, and the content pane owns its own scroll region, which is what makes a `sticky bottom-0` bar inside a page stick to the pane rather than to the document. A `fixed` bar is still positioned against the viewport and has to step around the sidebar itself — the branches page's selection bar does, with `left-[var(--sidebar-w)]`. `panes.ts` is the single list of destinations because four things read it: the source list draws them, the toolbar titles from them, ⌘1…⌘7 navigates to them and quick open searches them, and a pane added to one and missed in the others is a row you can reach and cannot get back from. Its `activePane` matches on a path *segment*, not a prefix — `startsWith("/runs")` is what the top nav did, and it also matches a future `/runsheet`. The toolbar's title and action are derived from the **route** rather than published by the page: the pages still carry their own `<h1>`, so the strip renders a plain `<div>` and not a second heading, and the action is only ever a *destination* — Start, Run, Approve and Land all need page state, and a toolbar button wired to one would be the shell reaching into a body it does not own.
- **A box inside the pane is never sized in viewport units, because the pane is not the viewport.** It is the window less the toolbar less the pane's own `pt-5`/`pb-12` less whatever heading the page puts above the box — so `62vh`, `68vh` and `calc(100dvh - var(--toolbar-h))` all named a box taller than the space it had, and every one of them hung past the bottom edge and gave the pane a scrollbar whose whole travel was empty: a screen-deep band under a 62vh log that the inspector beside it had already stretched the row past, a composer under the fold behind a thread that was scrolling itself. What replaces the figure is a mechanism rather than a better figure — `main`'s wrapper is a **flex column of `min-h-full`**, so `flex-1` means "fill what is left" and `min-h-full` rather than `h-full` keeps a page longer than the pane growing exactly as before. A box that fills that way must not also report its *content* as its intrinsic height, or the row is sized by the transcript instead of by the pane: the run log fills by being taken out of flow (`lg:absolute lg:inset-0` in a `relative` parent that has the height), which contributes nothing to the measurement. The fill is `lg:`-only on both split pages — stacked at one column there is a second column of content below the fold and the page is *meant* to scroll, so the box stays bounded there. `--pane-h` (`100dvh` less `--toolbar-actual`, which is the `max()` the toolbar and the sidebar's brand strip already compute inline) is for the one case a flex parent cannot reach: a `sticky` inspector's own cap. And a `sticky bottom-0` bar is never pushed *past* where it sits in flow, so the pane's `pb-12` stayed underneath it as a band of nothing — the three pane footers pair `-mb-12` with it exactly as they already pair `-mx-4` with `px-4`.
- **A table must not be the reason the pane scrolls sideways.** A truncating line is `white-space: nowrap`, so its min-content width is the whole sentence — a `max-w-[56ch]` cap on it is therefore a *floor* under the column, and the runs list stayed 916px wide however narrow the window got, scrolling sideways into empty canvas beside cards that had stopped at the pane's own edge. `w-full max-w-0` on the cell is what makes it the column that gives: zero as its max content contribution, 100% as its preference, so the fixed columns keep their widths and this one takes what is left, which is what the ellipsis was for. The `56ch` stays as an upper bound on a wide window. The list view is deliberately not wrapped in `overflow-x-auto` — that would pin its sticky header to a box that never scrolls — so the column that gives is the whole of what keeps that decision affordable.
- **The collapse is a document state, and it is settled before the first paint.** The rail is 168px narrower than the list, so a state read after hydration would shove the whole content pane sideways one frame into every page load — a louder version of the flash the theme script exists to prevent, which is why it rides in the same script. `[data-sidebar="collapsed"]` on `:root` swaps `--sidebar-w` and hides the row labels (kept in the accessibility tree, since the glyph is then the only thing naming the destination), and that is the whole of what it changes. The attribute is the source of truth; React mirrors it so the toggle can announce `aria-expanded`, and `writeCollapsed` writes the attribute and `localStorage` together. Storage failing costs the next page load, not this one.
- **The shell is installable, and the toolbar knows it.** `src/app/manifest.ts` declares `display: "standalone"` with `window-controls-overlay` first in `display_override`, which is what makes a browser hand the whole title bar to the page and publish `env(titlebar-area-x/y/width/height)`. The toolbar's height is a *floor* — `max(--toolbar-h, env(titlebar-area-height, 0px))` — and its left padding steps around the traffic lights by however much the sidebar has not already absorbed; every one of those env values is zero in an ordinary tab, so nothing anywhere branches on which case it is in. The empty part of the strip is `app-drag` and every control on it is `app-no-drag`, because a drag region swallows the pointer press; the sidebar's brand strip is deliberately not a link home so the whole of it can be drag space. `apple-mobile-web-app-capable` is declared through `metadata.other` **alongside** Next's own `mobile-web-app-capable`: Next emits only the standardised name because Chromium deprecated the Apple one, and WebKit reads only the Apple one, so Safari's Add to Dock needs both present. Icons are generated from `public/icon.svg`'s own geometry by `scripts/make-icons.py` rather than hand-drawn — an SVG covers a tab and Chromium's install criteria, but not `apple-touch-icon`, which Safari will not read as SVG, or a maskable icon, which is separate artwork (full bleed, mark inside the safe zone) rather than the rounded one relabelled. The manifest route sits inside `middleware.ts`'s matcher like every page, so installing behind `UF_AUTH_TOKEN` means signing in first; the exemption list is **not** widened for it — see the note beside the one entry it already has.
- **⌘ and nothing beside it, and never over a text field.** `AppShell` registers one `keydown` listener; `shortcuts.ts` holds the two rules it obeys, separately, because both are easy to get wrong in a way nothing reports — a layer that swallows a keystroke in a field looks like a dropped character, and one that claims a chord the browser owns looks like the browser broke. `isPlainCommandChord` refuses Ctrl as an alias for ⌘ (on Windows and Linux, Ctrl+1…8 switches browser tab and Ctrl+K is the address bar) and refuses ⌥ and ⇧, which make other people's chords. `isTextEntry` lists the input types that are *not* text entry, so a type this app has never seen is assumed to be text and left alone — the direction that costs a shortcut rather than a keystroke. ⌘↩ is the one carve-out from that exclusion and the shell binds it to nothing: the rule is stated where the exclusion is, so this layer can never become the reason a form's own commit chord stops working. Bound: ⌘1…⌘7 and ⌘K. Never bound: ⌘R, ⌘L, ⌘T, ⌘W — and Esc, because the quick-open sheet is a `<dialog>` and the browser already routes Esc through `onDismiss`, so a second handler would be two things closing one sheet. Every binding is announced with `aria-keyshortcuts` on the control it belongs to. **Quick open navigates and does nothing else.** That is a constraint on what the component may be rather than a feature not yet written: a keystroke away from spending money is what every approval gate in this app exists to prevent, and a palette is exactly where such a thing would look convenient. It reads `/api/runs` and `/api/workflows` through `jsonRequest`, only while it is open, so a failed read is a notice above a list that still offers the panes.
- **Styling** is Tailwind v4, CSS-first — no `tailwind.config.js`, no CSS modules, no third-party component library. Primitives live in `src/components/ui/`. Four things in `src/app/globals.css` are load-bearing and were each arrived at by measurement, not preference:
  - **The `@layer theme, base, legacy, components, utilities` statement.** Layer precedence is declared, never inferred: `next dev` and `next build` emit the blocks in *different* orders, so an inferred order means the legacy sheet beats utilities in the browser and loses to them in the shipped image.
  - **`@import "tailwindcss" source(none)` plus an explicit `@source`.** Automatic content detection respects `.gitignore`, and `.dockerignore` hides `.gitignore` from the build context — so the container would scan `CLAUDE.md` and `tsconfig.tsbuildinfo` and emit a different stylesheet than the host. A class would work in `next dev` and be missing from the image.
  - **Tokens keep their existing semantic names** (`--bg-raised`, `--fg-muted`, `--warn`) and `@theme inline` maps them to utilities. `inline` is mandatory — without it a utility freezes one theme's value at the definition site. Three theme states come from `color-scheme` + `light-dark()`: absent `[data-theme]` follows the OS, the two explicit values override it. Do not put `font-size` back on `html`; it redefines `rem` and silently shrinks every spacing and type utility by 12.5%.
  - **Variants are typed props with `Record<Union, string>` lookup maps, never `data-[…]` Tailwind variants.** Three reasons, all silent: React renders `data-x={false}` as the string `"false"`, which a bare `data-x:` variant matches on presence; Tailwind scans source as text, so an interpolated `text-${tone}` emits nothing; and `Meter` carries both `data-sev="ok"` and `data-unknown="true"` for an unknown reading (`severityFor(null)` is `"ok"`), where losing the tiebreak paints a solid green 100% bar instead of the hatched indeterminate one. `src/components/Meter.test.tsx` pins that last one. Shared tone unions live in `src/lib/format.ts`, not beside the components, because `src/lib` is what `tsconfig.test.json` compiles. The two attribute selectors on `:root` are not exceptions to this and must not be read as a precedent for one: `[data-theme]` and `[data-sidebar]` are *document* states written before React exists, by the pre-paint script, precisely because they have to be settled before the first paint. They change geometry and `color-scheme` and nothing else, and no component reads either as a variant.
  - The `@layer legacy { … }` block is the migration's remaining surface and shrinks as pages move onto the kit. It still beats Preflight and still loses to utilities. When it is empty, delete it — and with it `--radius`, `--mono` and `--sans`, which exist only for its sake.
- **Design language.** What the kit already decided, so a page does not decide it again differently.
  - **One thing leads on every screen, and elevation says which.** `Card`'s `emphasis` is the whole mechanism: `primary` (extra padding, `shadow-e2`) for the one card a page exists to show, `default` (`shadow-e1`) for everything the reader came for, `quiet` (flat) for a card that is scaffolding — a form section, a picker, a footnote table. More than one `primary` per screen means none of them is. Hierarchy is said with size, weight, elevation and whitespace; a second border or a colour is not a substitute for any of them.
  - **The palette and the type scale are AppKit's, not the web's.** Surfaces are four steps rather than three: `--bg` is the window, `--bg-raised` a card or a sheet, `--bg-inset` a *recess* into one (a field, a meter track, a log), and `--bg-grouped` a grouped list inside a card. The last one moves in opposite directions per scheme — AppKit lightens a grouped row against a dark window and darkens it against a light one — so one hex pair cannot express it and `light-dark()` is what carries the difference; it is also why a bezeled control is `--bezel` and never `--bg-inset`, which is the recess a text field sits in and reads as the same object at a glance. `--border` is a hairline at AppKit weight, far lighter than the box border it replaced, and `--shadow-e1` is now barely more than a seam, so a `default` card reads as a grouped box separated by its hairline rather than a card floating off the page. Body is 13px on the SF stack (`-apple-system` first, so macOS resolves SF rather than whatever `system-ui` has been remapped to), and `--text-sm` is 13px as well, deliberately: AppKit sets a control's own text at body size, and the two names stay apart so a call site still says which of the two it meant and the body step can move again without dragging every control with it. Nothing shouts — `CardTitle` and `Th` are sentence case at a weight step, never uppercase with tracking, and the legacy `th` rule matches them.
  - **There is one accent, and two different things are measured against it.** `--accent` is the *text* blue and clears 4.5:1 as text on `--bg` and `--bg-raised` in both schemes. `--tint`/`--tint-fg` is the fill-and-label pair a filled control wears, and in dark it is a different, deeper blue, because no single one does both jobs — `#4a9bff` carries white at 2.8:1. Where the browser exposes the operator's own accent, `--tint`/`--tint-fg` and everything mixed from `--accent-source` (the ring, the selection wash) switch to it; it is taken as a **pair**, because `AccentColorText` is specified as the colour of text placed on `AccentColor` and that is the only thing keeping a Graphite or Yellow accent legible under its own label. `--accent` is deliberately left alone — nothing guarantees an arbitrary accent reads as body text on a card. The `@supports` test names the whole `color-mix(in oklab, AccentColor …)` expression rather than the keyword alone: the two features shipped years apart, and a browser with one and not the other would leave `--ring` invalid at computed-value time, which is a focus ring in `currentColor` — visible, wrong and silent. `Highlight`/`HighlightText` was the other candidate and is rejected: engines return the selection *wash* there rather than the accent, and a white label on a pale wash is the failure this split exists to prevent.
  - **One focus treatment, stated in one place.** `@layer base` draws `outline: 2px solid var(--ring)` at 2px offset on everything focusable, and the legacy sheet no longer sets `outline: none` on `input:focus` — that suppression is what made a *second* treatment necessary, and it is why a button and the input beside it used to wear different rings. `--shadow-focus` is gone with it; a second way of saying this is how the two drifted apart. A component may override the ring's **colour** and nothing else, which is how `Button` keeps `--ring-danger` on the one control that cannot be undone, and why no component in the kit states an outline width or offset.
  - **Tokens.** Colour and type as above, plus: `--motion-fast|base|slow` (120/180/240ms — a control answering the pointer, something arriving or leaving, something travelling a distance) and `--ease-standard`/`--ease-entrance`; `--control-h` (32px, the floor for anything clickable) and `--control-h-lg` (36px, a button or a text input), stated as `min-h-[var(…)]` so a control keeps its box when its content changes; `--ring`/`--ring-danger` (the focus halo, at 45%) and `--shadow-press` (inset, so a pressed control recesses without moving); `--selection`, the accent wash behind selected text, at an alpha low enough that `--fg` keeps its own contrast whatever accent it turns out to be; `--ok-line`/`--warn-line`/`--danger-line`/`--accent-line`, each tone at 40%, for an *edge* that has to say which tone without outshouting the text it annotates — full strength stays for a conditional warning, the tint is for anything permanently on screen; `--fill-hover`/`--fill-active`, a neutral wash at 8% and 14% of `--fg`, translucent rather than a hex pair because it lands on three different surfaces and has to darken a light one and lighten a dark one — every opaque token in the palette is within 2% of `--bg-inset` in light mode and reads as no change at all. The shell adds three of its own: `--sidebar-w` (14rem, swapped for `--sidebar-w-rail` at 3.5rem by `[data-sidebar="collapsed"]`) and `--toolbar-h` (52px, a floor rather than a height — see the shell notes below). `--canvas-dot` is the workflow canvas's ground, and it is a token rather than the `color-mix` written into the utility that reads it: Lightning CSS emits a fallback declaration for a `color-mix` it cannot resolve, and that fallback is the *first operand at full strength* — a grid of solid `--fg` dots on any browser without it. Behind a `var()` it gets the `@supports` pair every other translucent token here gets. Eight named utilities: `hatched`, `mono`, `ui-transition`, `skeleton`, `sheet-enter`, `dot-grid`, and `app-drag`/`app-no-drag` for Window Controls Overlay — named rather than written as arbitrary values because the property is `-webkit-app-region`, which has no unprefixed spelling that ships anywhere.
  - **Motion is explanation.** `ui-transition` is the one transition an interactive surface wears; it deliberately omits `transform` and `width`, because a control must not move or resize between its states. Nothing loops except `Spinner` and `skeleton`, both of which stay legible frozen — `@layer base` flattens every duration under `prefers-reduced-motion`, and that blanket is not to be defeated with a `!important` or a JS-driven animation.
  - **`SegmentedControl` is how a short, fixed set of choices is offered, and `Icon` is the app's only glyph set.** The control is a radiogroup with a roving tabindex — one tab stop for the whole thing, arrows moving *and* selecting, focus following selection back so the next arrow press announces the right option. Both states carry a border and the same font weight, because a chip that gained either on selection would shift every segment beside it. `Icon` draws every glyph in a 16×16 box and sets the stroke attributes on the `<svg>`, so nothing can arrive a half-weight heavier than its neighbour; a glyph that is genuinely a filled shape cancels the stroke locally. Icons are decorative by default and only take a `title` where the glyph is the whole message — an icon announced beside the label it duplicates is noise. The set covers the seven panes plus disclosure, status and appearance, and the shell's own two (`sidebar`, `search`); a new destination needs a glyph here before it needs a row in `panes.ts`.
  - **`Sheet` is a native `<dialog>`, and that is a correctness decision.** `showModal()` gives the top layer, the inert background, the focus trap and Esc-to-dismiss from the browser; a hand-rolled overlay would be a hand-rolled focus trap, which is the part that silently stops working the day someone adds a control to the footer. Three rules follow from using the element rather than imitating it: it is always rendered and never conditionally mounted, because mounting in the same commit that calls `showModal()` is a race; nothing sets `display` on it, because a `display` utility outranks the UA's `dialog:not([open]) { display: none }` and leaves a closed sheet lying across the page; and `cancel` is prevented so Esc goes through `onDismiss` and React's `open` stays the single source of truth. It takes **one** default action and Cancel, and a `danger` sheet opens with Cancel focused — `showModal` would otherwise land on the first focusable thing, and one Return on a destructive confirmation is not a confirmation.
  - **What a new component owes.** Five interaction states — rest, hover, active, focus-visible, disabled — with **no layout shift between them**, and a hit target of at least `--control-h`. Where two class strings could set the same property under the same variant, both go in the same `Record<Union, string>` entry: split across a shared string and a per-variant one, the winner is Tailwind's internal sort order rather than anything written down (this is why `Button`'s focus outline colour is per variant). Those states are guarded with `not-disabled:` rather than `enabled:`, and that is what lets `ButtonLink` — a button that is a destination, so ⌘-click and middle click still work — share `Button`'s one `VARIANT` map: `:enabled` matches form controls and nothing else, so on an `<a>` every hover and press state would emit and never match, which is a filled control that does not answer the pointer. Verify a variant spelling in the emitted CSS rather than assuming it; Tailwind emits nothing for one it does not know, silently. And the four states that are not interactions — empty, loading, error, stale — are designed, not left to a spinner: `Empty`, `Skeleton`/`SkeletonText`, `Notice`, `Field`'s `error`.
  - **`Field` is finished; do not fork it.** Label, `hint`, `error`, `unit`, `prefix`, `disabled` and the mode-picker-plus-value row (`LimitField`) are all props. A context carries `aria-describedby`, `aria-invalid` and `disabled` down to `Input`/`Select`/`Textarea`/`Switch`, so a hint written as a prop actually reaches the control — children are never cloned, because several Fields hold a fragment. That context is **exported**, and `ListRow` provides it rather than carrying a copy, which is what makes a control behave identically in a grouped row and in a Field. Everything the context supplies is a default the control's own prop overrides. Width is the one thing no control states: two width utilities on one element resolve by stylesheet order, not class order — so a caller that needs a narrow input puts the width on a wrapper, never on the control.
  - **`ListGroup`/`ListRow` is the grouped inset list, and `Switch` is the control that usually sits in one.** Label left, control right, hairlines between rows, a rounded box, a footnote under it. The box deliberately does **not** clip its overflow: rows carry no background of their own, so a hairline never reaches a corner and nothing needs `overflow-hidden` — which matters, because a caller with a marker in the gutter (the settings page draws an edited rail there) would have it clipped away. A row is inert and has no hover tint: every interaction state belongs to the control inside it, and a row that lit up under the pointer would be claiming to be clickable across a width where only the 38px switch is. `Switch` *is* its track, so the focus halo hugs the pill rather than a padded box around it, and the hit target comes from an `::after` overlay stretched to `--control-h` — a target the pointer hits and the layout never sees. `Toggle` is the same switch with its label on the left, for a stack of Fields with no right edge to align against.
  - **Numbers behave.** Every figure `tabular-nums` (`Stat`, `Th`/`Td` with `num`, `Meter`, `mono`) so it cannot jitter as the page polls, units attached, and an unknown reading says so — the hatched indeterminate meter, never a 0% bar. Reserve space for anything that streams in.
