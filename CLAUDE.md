# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js 15 (App Router) app that (a) reads Claude Code's local session transcripts to show subscription usage against 5-hour / weekly windows, and (b) runs Claude Code headlessly against a mounted folder, stopping between iterations when a budget guard trips. Ships as a single Docker container. `README.md` explains the domain reasoning in depth — read it before changing anything in `src/lib/`.

## Commands

```bash
npm run dev          # next dev on :3000
npm run build        # produces .next/standalone (output: "standalone")
npm run typecheck    # tsc --noEmit
npm test             # node --test over src/**/*.test.ts, via tsconfig.test.json
npm start            # serve a production build

docker compose up --build     # the real deployment path; binds 127.0.0.1:3000
```

There is **no linter run** (`eslint.ignoreDuringBuilds` is on), and `npm test` covers a deliberately short list: `overlaps()` and `selectPromotable()` in `orchestrator.ts`, `normalizePolicy` / `evaluateBudget` in `budget.ts`, `isUsageLimit` / `isTransientApiError` / `refusalResumeAt` / `nextPrompt` / `reopenPrompt` in `orchestrator.ts`, where `buildSessionBlocks` puts a boundary in `windows.ts` — both derived and under `sessionResetOverrideAt`, the NUL-record parsers and the patch budget in `diff.ts`, `parseMergeTree` / `landRefusal` / `hasConflictMarkers` / `conflictRegions` / `parseStatusZ` / `commitRefusal` / `purgeRefusal` in `land.ts`, `planItem` in `mergeQueue.ts`, `normalizeTemplateInput` / `rowToTemplate` in `templates.ts`, `githubEnv` / `buildArgs` / `permissionDenials` / `needsLiveSpendTelemetry` in `orchestrator.ts`, `planProposal` / `composeTask` / `chatPrompt` in `chat.ts` with `githubSlug` in `workspace.ts`, `cycleOutputs` in `cycles.ts`, and `fmtCycleInFlight` in `format.ts`. Every one earns it on the same grounds — pure functions whose failure modes are silent and expensive (two agents in one working tree, or a run queued behind something that will never move; a run that never terminates, or that parks instead of ending; a wall that stops being recognised, or a run that waits hours for money that will not arrive; a blip that ends a run holding a live session, or three billed re-spawns into a wall that will refuse every one; a cycle billed to say `DONE` twice, or one that restates a task already half done; a window that rolls over while the provider is still counting it, or that reopens after it closed; a file list that shifts by one at the first rename, or a diff that is quietly a third of the change; a merge into a dirty tree or onto a branch the work does not belong on; a conflicting file dropped from the list because a message did not parse, or a markdown heading rendered as a clash; a billed resolution bought for a merge that was going to be refused anyway, or ten identical refusals where one was the answer; a saved configuration that widens what an agent may do, or that can never be started; a credential block git discards whole because its count disagrees with its pairs; a guard read off a model's suggestion instead of off the guard set a person wrote, or an agent handed a heading with no instructions above it, or an agent ordered to commit by a flag that forbids committing, or an agent that ends the server supervising it — and every run in flight with it — by matching a process name that describes two processes, or a refusal that leaves a run looking like it chose to do nothing, or a chat turn billed without the thread it is answering, or issues read out of a stranger's repository because a remote URL was parsed loosely, or a mid-cycle spending limit reading a figure that cannot move because the run was never told to report one; or one run's leftovers committed onto the branch of whichever run took its checkout slot next, or a branch destroyed by a request that was aimed at a different one, or a work cycle's report filed under the cycle before it, or a run cut off by its cycle cap picked up with the prompt written for one that said it was finished; or a run eight minutes into its first cycle displayed exactly like one that was marked running and never started, or a dead run still claiming a cycle in flight). Three are renderings rather than functions — `Meter.test.tsx`, `LiveTelemetry.test.tsx` and `Markdown.test.tsx` — and they clear the same bar by the same argument: what they pin is *something the reader would act on*, wrong in a way that throws nothing and typechecks (a solid green bar that means "we don't know"; a first-party figure that reads as an addend to the transcript-derived meter beside it; a report that ends in silence because the cycle was killed with a code fence still open). Two are neither a function nor a rendering, and each earns it its own way. `chatTurn.test.ts` is the only test here that opens the database: it drives `sendChatMessage` through a failed pre-spawn setup, because what it pins is a *state transition* rather than a return value (a chat thread stranded at `thinking` for ever by one failed `writeFileSync`, unusable until the server restarts). It sets `DATA_DIR`/`CLAUDE_HOME` into a temp directory before the module graph loads, which is why it is a second file rather than a case in `chat.test.ts`, and it refuses to run if `config.ts` was already loaded. `deployment.test.ts` pins `Dockerfile` and `docker-compose.yml` against each other, that the directory compose sets `DATA_DIR` to is `chmod`ed writable by any uid in the image, because `/data` is a *named volume* and Docker copies that directory's mode onto a fresh volume's root: left at the default, the database belongs to uid 1000 and a container run under any other `UF_UID` cannot create it. It clears the bar for the same reason — nothing else here notices. It typechecks, it builds, and it passes on macOS, where Docker Desktop's bind-mount remapping makes 1000 right whatever the host uid is. That is the bar for adding another, not a general testing convention to follow. `npm run typecheck` plus a `docker compose up --build` smoke test is still the real verification loop, and the README's "Verified" section records what was checked by hand — including a "Not yet verified" list, which must stay honest.

Note that `npm run dev` on the host reads the host's **real** `~/.claude` transcripts and can spawn **real, billed** `claude` processes. Runs default to `acceptEdits`, so an agent started from the UI writes files.

## Environment gotchas

- The app reads `WORKSPACE_ROOTS` (multiple mounts, `Label=/path` entries joined by `|`) and falls back to the single `WORKSPACE_ROOT` when it is unset. `.env` / `.env.example` define `UF_WORKSPACE`, `UF_WORKSPACE_N` and `UF_WORKSPACE_N_NAME`, which are **only** consumed by `docker-compose.yml` — to pick the host mounts and to compose `WORKSPACE_ROOTS`. Running `npm run dev` without either set falls back to `~/workspace`, so `/api/folders` will look empty even though `.env` names a directory.
- An entry in `WORKSPACE_ROOTS` with an *explicitly empty* label (`=/workspace2`) is **skipped**, while a bare path (`/workspace2`) is labelled from its basename. That asymmetry is load-bearing: compose cannot omit a volume conditionally, so all four slots are always mounted and an unset `UF_WORKSPACE_N_NAME` is what switches a slot off. Adding a workspace must stay an `.env` edit, not a compose edit.
- `CLAUDE_HOME` (default `~/.claude`) determines which transcripts are parsed; `DATA_DIR` (default `./.data`) holds the SQLite file.
- `UF_AUTH_TOKEN` blank disables auth entirely. `ANTHROPIC_ADMIN_KEY` blank leaves the API-account page in an explicit "not configured" state rather than showing zeros.
- `UF_GITHUB_TOKEN` blank means runs cannot use GitHub at all, and the Settings header says so — the failure otherwise arrives mid-run, inside a tool call nothing here reads. The `UF_` prefix is load-bearing rather than cosmetic: `gitEnv()` and `reviewEnv()` strip that namespace, so the token is withheld from every child except the one `githubEnv()` hands it to.
- All process-level config is centralised in `src/lib/config.ts` and fixed at boot. User-editable values belong in the settings table (`src/lib/settings.ts`), not here.
- `UF_WORKSPACE` and `HOME` use compose's `${VAR:?message}` form, so a missing one aborts `docker compose up` instead of substituting. Both previously had defaults, and both failure modes were silent: Docker *creates* a bind source it is handed, so a wrong path yields an empty folder picker and a dashboard of zeros — indistinguishable from a quiet week. Do not restore a default to either. `UF_WORKSPACE_2..4` still fall back to `UF_WORKSPACE`, which is what keeps all four slots mountable.
- `user: "${UF_UID:-1000}:${UF_GID:-1000}"` in compose exists because the container writes to both bind mounts. macOS Docker Desktop remaps bind-mount ownership onto the container user, which is why uid 1000 was never questioned; Linux preserves the host uid and a mismatch breaks `/login`, transcript writes, and `.uf-worktrees` creation. The image still sets `HOME`, `DATA_DIR`, `CLAUDE_HOME` and `CLAUDE_CONFIG_DIR` explicitly — required, because a uid with no `/etc/passwd` entry makes `os.homedir()` unreliable.
- The image carries `gh` (`ARG GH_CLI_VERSION`, checksum-verified release tarball rather than an apt source) for the same reason it carries a compiler: an agent asked to open a pull request finds out `gh` is missing halfway through a cycle, inside a tool call, and works around it badly. It is credentialed only by `githubEnv()`, never by a config file in the image — nothing about the image knows a token.
- The image pins `@anthropic-ai/claude-code` (`ARG CLAUDE_CLI_VERSION`) and sets a system-wide git identity. The pin protects a reverse-engineered contract: the `stream-json` parser and the OTLP shapes were captured from one build, and both degrade *quietly* when it moves — an unparsed line becomes a log entry, a missing `result` event understates spend. The identity is not cosmetic: a container hostname has no domain, so git rejects its own auto-detected address under the strict ident every commit uses, and an isolated run — whose preamble orders it to commit — ends with an empty branch.

## Architecture

**Three** data sources now, still **never summed or mixed in the UI**. The third is Claude Code's own OTLP export (`otlp.ts` → `otlp_requests`), gated on `settings.telemetryForRuns` with one exception below, covering only runs this app spawns. It is first-party per-request cost — no price table, no dedupe key, no file polling — and it is the only way to account for a work cycle killed before the CLI's `result` event. It renders as its own card on the run page and its own card on the dashboard, and must never reach `buildSnapshot()` or `runs.spent_usd`. It reaches `evaluateBudget()` through exactly one door — `telemetrySpendSince` → `RunProgress.spentGuardUSD`, for a live run's own spending limit, described under the enforcement modes below — and that door is narrow on purpose: one run, one cycle, the guard half of a split whose display half stays transcript- and `result`-derived. It cannot replace transcripts: no backfill, no `cwd`, and `cache_creation_tokens` collapses the 5m/1h split. Wire details were captured from a live CLI, not read from the docs — the docs' `claude_code.api_request` is the record *body*, while `event.name` is the bare `api_request`, and `OTEL_RESOURCE_ATTRIBUTES` lands on both the resource and each record. The payload carries `user.email` and account UUIDs; the parser drops them and the schema has no column for them. `request_id` is the primary key because OTLP delivery is at-least-once, and the ingest route always answers 200 — a batch exporter retries failures, so rejecting a malformed record would cost that batch on a loop.

The two original sources:

| | Subscription view | API-account view |
|---|---|---|
| Source | `~/.claude/projects/**/*.jsonl` | Anthropic Admin API |
| Code | `transcripts.ts` → `windows.ts` | `adminApi.ts` |
| Route | `/api/usage`, `/api/calibrate` | `/api/account` |
| Nature | exact volumes, **estimated** percentages | authoritative |

The subscription pipeline:

```
transcripts.ts  scan + dedupe → UsageEntry[]      (incremental byte-offset reads)
pricing.ts      per-model rates, cache multipliers → costUSD per entry
settings.ts     limitConfig() applies reserved headroom → LimitConfig
windows.ts      buildSnapshot() → 5-hour blocks, weekly rollup, burn, projection
budget.ts       evaluateBudget(policy, snapshot, progress) → allow / block + code
orchestrator.ts the run loop: guard → spawn claude → parse stream-json → repeat
git.ts          the one way this app runs git — argv only, env scrubbed
diff.ts         <base>...<branch> as a rendered, budgeted file list + patches
review.ts       one-shot Claude calls outside the loop: review, conflict resolve
land.ts         merge preview, AI conflict resolution, landing, deletion, inventory
templates.ts    saved run configurations — form input, never a run
chat.ts         the orchestrator chat: a conversation that proposes runs
workspace.ts    the folder walk, shared by /api/folders and the chat's tools
cycles.ts       the event stream segmented into work cycles — client-safe, and
                the only reader of where one cycle's output ends
db.ts           SQLite: runs, run_events, run_reviews, run_templates, settings,
                chat_sessions, chat_messages, chat_proposals
```

**Four kinds of child process, from four modules, and no more.** `git.ts` holds the git primitives (`gitSync` for the admission decision, `git` for everything else); `orchestrator.ts` spawns the agent; `review.ts` spawns the one-shot invocations that are not work cycles — a review, or a conflict resolution (`run_reviews.kind`); `chat.ts` spawns the orchestrator chat. All go through an argv array and never a shell. The review spawn was the deliberate third and differs from the agent in every way that matters: it is never automatic, it runs `--permission-mode plan` so it cannot write, its cost lands in `run_reviews` and never in `runs.spent_usd`, and it gets no telemetry env even when `telemetryForRuns` is on — `otlp_requests.run_id` is compared against the run's own spend, and a review's requests in that comparison would make an accounted-for run look unaccounted-for. Adding a fifth kind is a decision, not a detail.

`orchestrator.ts`'s loop calls `currentSnapshot()` (a fresh transcript scan) *before every iteration*, evaluates the budget, then spawns one `claude -p … --output-format stream-json --verbose` child in the run's working directory. Iteration 2+ uses `settings.continuationPrompt` and `--resume <sessionId>`; the run ends on `DONE`, the iteration cap, a guard, or a non-zero exit.

Several runs can be in flight at once. `createRun` admits a run or leaves it `queued`; `promoteQueued()` starts whatever is startable, and is called after creation and again in `startRun`'s `finally`. A run on a git repository defaults to its own worktree (`work_dir` ≠ `folder`), which is what lets two runs share a project; a run anywhere else takes the folder exclusively.

Events flow: `emit()` writes to `run_events` **and** publishes on a `globalThis` EventEmitter → `/api/runs/[id]/stream` replays persisted history first (honouring `Last-Event-ID`), then tails live. Persist-then-publish is what makes reconnect and late page loads lossless — keep that order.

## Invariants — these encode the product's reasoning, not style preferences

**Unknown must not render as zero.** Anthropic publishes no numeric value for a Pro/Max limit, so ceilings default to `null`. A `null` fraction renders as a hatched indeterminate meter ("no ceiling set"), never an empty 0% bar. Do not add default numeric ceilings to `DEFAULTS` in `settings.ts`.

**A fraction guard with no ceiling is refused, not ignored.** `evaluateBudget` returns `code: "no_ceiling"` when `maxWeeklyFraction`/`maxSessionFraction` is set but the window has no ceiling. Silently passing would leave the user believing a guard is active.

**Cost is the primary metric; raw tokens are the fallback.** A Claude Code workload is ~98% cache reads at 0.1×, so a token-denominated ceiling tracks conversation length rather than work. `WindowState` exposes both `costFraction` and `tokenFraction`, but `fraction`/`limitMetric` prefer cost whenever a cost ceiling exists.

**Unpriced models contribute $0 to everything displayed, and are named.** `resolvePrice` returns `null` for unknown models rather than guessing; `costOf(t, null)` is `0`; `scanUsage` collects `unpricedModels` and the dashboard banners them. Dollar totals are a documented floor.

**…but the guard charges them a fallback rate, because a floor is not a guard.** A window made entirely of an unpriced model has `costUSD === 0`, so `costFraction` is exactly `0` and no threshold can ever be crossed — the guard would silently stop existing the week a new model ships. `guardCostOf()` charges `UNKNOWN_MODEL_PRICE` ($10/$50, the priciest *current-generation* rate, so an unknown can never look cheaper than a known model), which flows through `Aggregate.costGuardUSD` → `WindowState.guardFraction` → the threshold comparisons in `evaluateBudget`. Keep the split absolute: `costUSD`/`fraction` are what the user is shown, `costGuardUSD`/`guardFraction` are what the guard acts on, and the two are identical whenever every model is priced. `Meter`'s `upperFraction` renders the gap as a hatched band — do not drop it, or a run gets refused at a threshold the visible bar has not reached. The `no_ceiling` refusal still reads `fraction`: a missing ceiling is a configuration fact, not a pricing one.

**Canonicalise model IDs, never truncate them.** `canonicalModelId()` strips region and vendor prefixes (`us.anthropic.`) and normalises `@date` to `-date`, so Bedrock and Agent Platform IDs resolve to the same rates as first-party ones. Do **not** add short catch-all keys like `claude-opus-4` — a future `claude-opus-4-9` would then be priced at a confident wrong number instead of surfacing as unknown, turning a loud failure into a quiet one.

**Naming the plan is not setting a ceiling.** `account.ts` reads Claude Code's own `.credentials.json` / `.claude.json` to *name* the subscription ("Claude Max 20x"). A tier maps to no published number, so this must never become a ceiling, never populate `DEFAULTS`, and never suppress the indeterminate meter. Both files are undocumented internals of another program — written lazily, mode 0600, possibly replaced by the macOS Keychain — so every read is try/catch to `null`, misses are cached only briefly, and the profile is projected to plan strings before it reaches `apiTypes.ts` (the source objects carry email, display name, and UUIDs). The legacy `~/.claude.json` is consulted only while `CLAUDE_CONFIG_DIR` is still the default: once it is redirected, that file describes whoever is logged in on the host rather than the account whose transcripts are being scanned, and a confident wrong plan name is worse than none.

**A block opens at its first turn, and nothing rounds that off.** The provider issues the reset instant itself — Claude Code reads `anthropic-ratelimit-unified-reset` off each response, and its own renderer prints the minutes whenever they are non-zero, so windows plainly do not begin on the hour. Nothing writes that instant to disk: it is on no transcript record, in no config file, and in none of the OTLP metrics the CLI exports, which is why this stays derived. `buildSessionBlocks` therefore anchors on the entry, and the error left is the opening turn's latency (seconds — the block is anchored on the response we can see, not the request that opened the window). Flooring to the hour, which this used to do, was not a rounding error: each block opens where the last one closed, so the offset carried down the entire chain, and a window rolled over up to an hour early reads as a *fresh, empty* session while the provider is still counting the old one — which is what the meter shows and what `evaluateBudget` acts on. There is deliberately no separate idle-gap rule: `blockStart <= lastActivityAt` always holds, so five quiet hours have already carried the next entry past the window, and reinstating one would assert that going quiet ends a window early, which the provider does not do.

**The 5-hour window is derived, except when the provider resets it.** `settings.sessionResetOverrideAt` is the one number a user supplies about a window rather than about a ceiling, because a tier change restarts the window with no trace in any transcript. `buildSessionBlocks` **splits** at `resetAt - 5h` rather than filtering: the pre-reset block is closed there (so it stops being active) and the next one starts at the reset instead of at its own first entry, which keeps that work in history where it did happen and did count. It is inert once `now >= resetAt` — a stale value keeps splitting history but must never re-open a finished window — and it never touches the weekly rollup. `PUT /api/settings` refuses a value more than 5h in the future with a 400, not a clamp: no window can reset that late, so it is a typo that would blank the session meter when its anchor arrived.

**Reserved headroom is applied in exactly one place.** `limitConfig()` subtracts it so meters, guards, and the exhaustion projection all agree. Raw configured values stay on `Settings` for display. Capped at 0.95.

**Per-iteration spend comes from the CLI's own `result` event** (`total_cost_usd`), not re-derived from tokens. The transcript-derived cost math in `pricing.ts` serves the dashboard; the two are independent on purpose.

**A killed cycle's spend is reconciled, into its own column.** A cycle interrupted mid-flight never emits `result`, so it contributes $0 to `spent_usd`. `reconcileKilledCycle` recovers an estimate from the transcript pipeline — same dedupe key, same price table, same cache-TTL weighting — bounded by session id *and* the cycle's time range, because a resumed session copies earlier turns forward with their original timestamps. It lands in `spent_usd_est`/`spent_tokens_est` and **never** in `spent_usd`, which stays a floor of what the CLI itself measured; `RunProgress.spentGuardUSD` is the sum, and only the guard reads it. This is the same display-vs-guard split `costUSD`/`costGuardUSD` already makes for windows. The kill ladder tries `SIGINT` first for the same reason — a CLI that handles it may still print `result`, which is the difference between measured and estimated.

**The cycle in flight is on the row, in its own column, and it is not a count.** `iterations` is written only when a cycle *returns*, because that is what the guard counts — so for the whole of cycle 1, routinely tens of minutes, a working run read `0/N` and `$0.00`, which is bit-for-bit what a run that was marked running and never started reads. `runs.active_iteration` is the same number one tick earlier: stamped beside the `iteration` event at the spawn, cleared in the post-cycle UPDATE and again in `startRun`'s `finally`, so between cycles it is null rather than naming one that has already returned. It is display only — nothing derives a limit from it and `evaluateBudget` is passed exactly what it was before, including the live guard's deliberate `iterations - 1`. `fmtCycleInFlight` is the single reader and it refuses the column on any status but `running`, because nothing clears the row when the container dies mid-cycle and a finished run claiming an open cycle is the same lie pointing the other way. The wording is "cycle N of M **in flight**" for the reason `spent_usd_est` is a separate column: a reading that could be added to the completed count would be worse than no reading. `spent_usd` is untouched by this — it stays a floor of what the CLI measured, and the figure that moves during a cycle is still telemetry's.

**Attribution comes from the transcript, not from telemetry.** `effort`, `attributionAgent`, and `attributionSkill` are on the assistant record already, so `byEffort`/`byAgent`/`bySkill` cover full history with no collector, no config, and no second source to reconcile. Before adding a breakdown, check whether the field is already on the record — `agentId`, `gitBranch`, `usage.server_tool_use`, and `message.stop_reason` are all still unread. All five rollups go through one `groupBy()` in `windows.ts`, and every turn must land in a bucket (`(main thread)`, `(no skill)`, `(unspecified)`) so each column reconciles to the window total rather than silently omitting a remainder.

**What a run is spending *now* is a third reading on the dashboard, never a correction to the meters.** A cycle's spend lands on `runs.spent_usd` only when the CLI emits `result`, so a cycle in flight contributes $0 there for its whole duration and the page can say nothing about which run is responsible or what it has cost so far. `telemetryWindow(since)` groups `otlp_requests` by `run_id` over the *snapshot's own* `session.startsAt`, so the card covers the same five hours as the meter above it — and the two are still never added, because one is Claude Code's per-request cost for agents this app spawned and the other is our price table over every transcript on the machine, covering overlapping work. Rows with a null `run_id` are excluded: the orchestrator stamps one onto every agent it spawns, so an unattributed record is something else pointed at the ingest route, and the card claims to describe runs. The listed runs are capped at the heaviest few while `runCount` reports the whole set, for the same reason a shortened diff says so. The poll drops from 10s to 5s **only** while `workingRunCount > 0` — `buildSnapshot` re-aggregates the full history on every request and the agent is competing for the same CPU, so a permanently faster dashboard would be paid for by the run it is watching.

**Transcript parsing details that materially change the numbers:**
- Dedupe key is `${message.id}:${requestId}`, applied across files (a resumed session copies earlier turns forward). Naive summing over-reports by ~3×.
- Files are read from a cached byte offset; the bytes after the final `\n` are left unconsumed so a partially-flushed line is re-read next pass. A shrinking file means rotation → re-parse from 0.
- `cache_creation` splits into 5m (1.25×) and 1h (2×). Unsplit legacy records are attributed to the **cheaper** 5m bucket so ambiguity understates rather than overstates.
- Pricing changes over time: `resolvePrice(model, {at, speed})` is date- and speed-aware (Sonnet 5 intro pricing has an end date; `speed: "fast"` has its own table). Keep new rates in that shape rather than flattening them.

**How guards are enforced is the operator's choice, and none of the three modes is a hard cap.** `BudgetPolicy.enforcement` selects it per run.

- `between-cycles` (the default) reads the guards only before each iteration. Overshoot is bounded by one iteration **per run active at the time**, and this is the only mode whose accounting is exact — every cycle reports its own cost.
- `live` also reads them on a global ticker (`liveGuardTick`, `settings.liveGuardIntervalSeconds`, floor 15s) while a child is in flight, and interrupts it. That bounds overshoot to *one model turn plus one interval plus the kill* instead, and costs the in-flight cycle's work. Every input moves per tick, but from three different places: `duration` off the wall clock, the two window fractions off a fresh `currentSnapshot()`, and the run's own spend off telemetry (see below — the locals cannot supply it). Neither usage source is instant: window usage comes from transcripts Claude Code flushes as each turn completes, and telemetry from a batch exporter a second or so behind. Tighter, not exact — say so in every piece of copy.
- `live-resume` is `live`, except the 5-hour window parks the run instead of ending it.

`LIVE_ENFORCEABLE_CODES` is the whitelist. `iterations` is excluded because the loop increments before it spawns — a live check must be passed `iterations - 1` or it kills the cycle the pre-cycle guard just authorised. `no_ceiling`/`no_terminus` are excluded because re-reading configuration mid-flight means a Settings edit in another tab kills a running agent. The ticker deliberately emits **no** `run_events` row per tick; only an interrupt is recorded.

**`run_cost`/`run_tokens` are live only because telemetry makes them live — this is the one place OTLP feeds a budget decision.** The ticker's `progress()` closes over `startRun`'s locals, and `spentUSD`/`spentTokens` only move when the CLI's `result` event is folded in *after* `runIteration` returns — by which point the `finally` has already removed the `liveGuards` entry. Those locals are therefore the *completed cycles'* total and nothing else, which made `maxRunCostUSD` overshoot by one full cycle under `live` exactly as under `between-cycles`: a between-cycles guard wearing a live label. `telemetrySpendSince(runId, cycleStartedAt)` supplies the missing half, bounded by the cycle start so the cycles that already reported through `result` are not counted twice, and added to `spentGuardUSD`/`spentGuardTokens` — **never** to `spentUSD`, so `runs.spent_usd` stays a floor of what Claude Code itself measured. Same display-vs-guard split as `costUSD`/`costGuardUSD`. The window fractions were never part of this: they move on every tick already, off a fresh snapshot, and a run's own turns land in that scan — but that is the whole machine's counter, not this run's, which is why it does not substitute.

**A guard whose input is optional is not a guard, so the input stops being optional.** `settings.telemetryForRuns` opts into *reporting* — the dashboard card and the run card. A run whose policy needs telemetry to be enforceable (`needsLiveSpendTelemetry`: live enforcement, plus a run cost or token limit) gets `telemetryEnv(runId, required)` regardless of that setting, because a guard that silently stops guarding when an unrelated toggle is off is the failure `guardCostOf()` exists to prevent for unpriced models. Refusing such a run at the door would have been the consistent alternative and was rejected: it refuses a policy that works today. `/api/usage` still gates its card on the setting, so nothing about the dashboard changes. What is *not* covered is an export that is configured and does not arrive — so the loop compares the CLI's own figure for each finished cycle against what telemetry reported for it, and logs a `run_events` line naming the cost when a paid cycle reported nothing. The alternative is a guard reading zero, which refuses nothing and looks exactly like a guard that was never reached.

**A cycle cut short by a pause is refunded to the counter.** The loop increments before it spawns, so a live interrupt — and a provider refusal, which does no work at all — lands on a cycle that has already been charged. Left charged, `live-resume` with `maxIterations: 1` can only park and then stop at `cycles` without ever finishing: the pre-cycle guard checks cycles before the session window. `MAX_PAUSES_PER_RUN` bounds the refund, so one work cycle is at most four billed invocations. The refund is applied at the post-cycle interrupt site only — `applyInterrupt`'s two other call sites run *before* the increment and would discount a cycle that completed. It also means `iterations` can no longer be read as "has this run worked before": the prompt/`--resume` choice keys on `sessionId === null`, and `ensureWorktree`'s orphaned-branch guard keys on `pause_count`.

Concurrency multiplies overshoot — `maxRunCostUSD` is per run, so N runs at $5 is a $25 worst case — and `maxConcurrentRuns` (default `null`, no limit) is what bounds N. The cap is enforced in `promoteQueued`, counting **running** rows only: it is a limit on work in flight, so a run over it waits rather than being refused, and queued *or paused* rows — which cost nothing — must never consume it.

**Only the 5-hour window can be waited out.** It is the sole quantity that refills on its own, on a schedule, with no configuration. The weekly window does not qualify: with `weeklyAnchor` unset (the default) `weekly.endsAt === now`, so there is no reset instant at all — the trailing total merely decays over days. `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume` and for nothing else, as a discriminated union so `resumeAt` is unreachable without narrowing. The check order — terminus, cycles, duration, run spend, weekly, *then* session — is load-bearing: a run that is out of time **and** out of window must end, not park, or the clock stops being a terminus.

**A run parks on two triggers, and only one of them needs configuring.** Our own guard is the first: `evaluateBudget` returns `disposition: "pause"` for `session_fraction` under `live-resume`, which needs both a per-run fraction *and* a numeric 5-hour ceiling — and ceilings default to `null` by design, so on a stock install that trigger never fires. The provider's own refusal is the second, and it needs neither. Claude Code reports API-level refusals as an assistant turn whose `message.model` is the literal `<synthetic>` (the marker `transcripts.ts` already keys on to keep an all-zero record out of the unpriced warning); `isUsageLimit()` decides whether that refusal is an exhausted allowance. Nothing parses a reset instant out of the message: the CLI renders a *formatted local time*, and the `usage limit reached|<epoch>` form every community wrapper keys on appears nowhere in the shipped binary. The refusal test sits **before** the exit-code test *and* before the `DONE` test — a refusal exits non-zero, so the exit code would file the provider's decision as the agent crashing, and a refusal that exits 0 would otherwise match nothing and re-spawn straight back into the wall.

**A refused run backs off; it does not trust the window boundary.** `refusalResumeAt` reads the end of the last block with real spend in it — not `session.endsAt`, because the refusal's own zero-token `<synthetic>` record opens a block of its own that reads as a window five hours out. Even that boundary is approximate in both directions: it runs late by the opening turn's latency, and early whenever the window was really opened by work this app cannot see — claude.ai, Desktop and Cowork spend the same allowance and write no local transcript. A boundary still in the future is waited for; one already passed falls through to a 20/40/60-minute backoff, floored so nothing re-spawns immediately and capped at six hours. `MAX_PAUSES_PER_RUN` bounds the whole thing, because unlike the guard path — where wall clock is checked ahead of the window and terminates the run — a refusal is someone else's claim about someone else's counter, and a misread one must not park forever.

**A `<synthetic>` turn is not by itself a refusal — the cycle's own outcome decides.** When a stream drops after some blocks have been yielded, Claude Code finalises the partial response with an ordinary `end_turn` and carries the cycle on (`tengu_streaming_partial_finalized`, and the watchdog/stale-connection retries beside it). The `API Error: Connection closed mid-response` turn it leaves behind is then a warning *about a completed cycle*, followed by a clean `result` and exit 0 — but `apiError` latches on first sight, so the marker alone was ending runs whose work cycle had finished. `recovered` requires the CLI's own verdict (a `result` event, a success subtype, a zero exit) — never anything inferred from the text — and excludes an allowance refusal by name, because a wall that exits 0 must still stop the run rather than re-spawn into itself, which is the reason this whole test sits ahead of the exit-code test.

**A refusal has three answers, not two, and the third one is not a park.** A cycle can also die because the connection dropped mid-response or the upstream was briefly overloaded — `isTransientApiError`, matched on the five stream-truncation sentences read out of the shipped binary, on the statuses and `error.type` names the provider documents as retryable, and on the socket errors that never reach a status. That is neither the wall nor the agent failing, so the loop retries it in place: 5/20/60 seconds of backoff and another spawn into the same session. Retried rather than parked because `resume_at` exists to wait out a five-hour window and a run that parks yields its folder — for a fault measured in seconds, on a run whose session is intact. `MAX_TRANSIENT_RETRIES` is **consecutive**, reset by any cycle that gets through and held in `startRun`'s frame rather than on the row (a restart hours later is not "in a row"), so a long run meeting one blip an hour is never terminated by the total while a dead upstream ends the run in ~85s and names the attempt count. The retried cycle is refunded to `iterations` *and* to `cyclesThisSegment` — the first for the reason a parked cycle is, the second because that counter means "no cycle in this segment has completed yet", which is what lets `looksLikeResumeFailure` still recognise a retry that cannot resume the truncated session. The order of the three tests is load-bearing: `isUsageLimit` first, because a wall can arrive as a 429 and no backoff refills an allowance. `refusalInStderr` deliberately does **not** consult this — an agent's own build output says "connection error" constantly, and a run must not re-spawn because its test suite could not reach a registry.

**A paused run is reconsidered, not trusted.** `resume_at` decides *when to look*; `evaluateBudget` decides *whether to run*. `sweepPaused` (60s, lazily started and stopped) re-evaluates from a fresh snapshot and re-queues through `promoteQueued` rather than calling `startRun` directly — that is what keeps FIFO order, folder reservation and the concurrency cap in one place. A verdict that can never clear ends the run instead of leaving it holding a folder. A cleared verdict is still not enough on its own: a run whose folder was taken while it waited stays `paused` and re-checks next tick, because the alternative is a `queued` row that a restart would close out.

**Reopening a finished run is an operator decision, not a resume.** `reopenRun` (`failed`/`stopped`/`completed` — `REOPENABLE`) puts a terminal row back in the queue keeping its folder, checkout, branch, session id and spend, so `startRun` continues the same conversation. It takes a **budget**, because the usual reason a run needs picking up is that its own limits ended it, and re-queueing under the limits that stopped it just reproduces the stop; the three carried-forward guards (`iterations`, run spend, run tokens) are therefore checked at the door rather than left to the pre-cycle check, which would refuse seconds later with the row already flickering queued → stopped and nothing said about what to change. `started_at` is **cleared**, and that is the one deliberate divergence from a pause: a parked run keeps its original start so wall clock stays a terminus it cannot wait out, while a run picked up by hand days later would otherwise be refused by its own time limit before it spawned. `permissionMode` is not accepted from the wire — the stored value carries forward, so reopening adds no second route to `--permission-mode`. An isolated run whose slot an active run has since taken is refused by name, because `allocateSlotPath` only avoids slots held by *active* rows and a terminal row is not one.

**A template is form input, and the two settings that decide what an agent may do are applied but announced.** `run_templates` holds a task, guards, and optionally a target; it takes no folder claim, consumes no concurrency slot, and nothing derived from `activeRuns()` can see it. `permissionMode` is narrowed three times — on save, on read, and again by `POST /api/runs` — because a template is the *second* route to `--permission-mode`, the flag `reopenRun` deliberately refuses to become a third route to. Only the last narrowing guards anything; the first puts the mistake where it was made, and the second (unknown → `plan`, the only mode that cannot write) is what stops a row from a build this one does not understand from ever *widening* what it permits. Never invert that fallback. `enforcement` is the other one: there is no `settings.defaultEnforcement` precisely so that no single edit turns every run into a cycle-killing run, and a template that quietly carried `live` would reintroduce exactly that — so a carried non-default mode, and a carried `bypassPermissions`, each raise a banner above the form with a one-click way back to the safe value, and the banner clears the moment the control is touched. `normalizeTemplateInput` also refuses the `no_terminus` pair at the door rather than leaving it to `POST /api/runs`: a template that can be saved but never instantiated fails weeks away from the form that caused it. `folder` is nullable and `""` is *not* the null — the empty string is the mount root, the one selection that blocks every other run in the tree. The template holds no model: `settings.defaultModel` is the single place for that.

**The orchestrator chat picks what work to do; something a person wrote picks what an agent may do; a person decides whether it happens.** `chat.ts` is a conversation with a read-mostly tool surface, and the two tools that write anything add a `chat_proposals` row or a template's *prompt* — both inert, holding no folder claim and no concurrency slot. `planProposal` is where a proposal becomes a run, and the branch that matters is the one that is *not* in it: no value off a proposal sets a budget, a permission mode or an isolation choice. Those come from the named template, or from `settings.chatDefaultGuards` when it names none — the second one exists because requiring a template made the chat useless on a stock install, and it is a *person's* configuration either way, which is the property that matters. A proposal that names a template that has since been deleted is refused by name rather than falling back to the defaults: the operator approved the card that said "Fix a bug", and a run under different rules than the card stated is what this gate exists to prevent. `--permission-mode` is not something a model should be able to reach for — the same reason `reopenRun` refuses to become a third route to that flag. The approval route takes an explicit list of ids the page displayed, so a proposal the chat added between render and click is not swept into an approval nobody saw, and it approves in one synchronous pass because `createRun`'s folder claim is only atomic inside an event-loop turn. There is deliberately no setting that approves automatically.

**Prompt text is the one half of a run a model may write, and it is written down as an exception rather than absorbed.** `chat_proposals.prompt_override` replaces the template's prompt for one run, and `save_template` writes a name and a prompt back for reuse — taking `chatGuards()` for a new template and the row's existing guards for an update, so no argument on that tool can move one. The distinction is not cosmetic: guards decide what an agent *may* do and prompts decide what it is *asked* to do, and a chat that cannot adapt a prompt just restates its objections inside the task, which puts the same text in the run with nothing recording that it happened. `composeTask` keeps the two halves in order and separated by a heading, and emits the task alone when there is nothing standing above it — a section marker for a section that is not there is worse than no marker. Every proposal card says which guard set applies, spelling out the untemplated one, and marks a rewritten prompt.

**The chat's tools run in this process, and that is a correctness requirement rather than a convenience.** `/api/mcp` speaks MCP over HTTP by hand — `initialize`, `tools/list`, `tools/call` — and the handlers call `createRun`, `listTemplates` and `scanWorkspace` directly. A stdio MCP server would be a second process doing check-then-insert against the same SQLite file, which silently permits the two-agents-in-one-directory collision the folder claim exists to prevent. `workspace.ts` exists for the same reason in miniature: the picker and the chat must not be able to disagree about which folders exist or which are busy.

**The chat's child authenticates with a capability, never with `UF_AUTH_TOKEN`.** `middleware.ts` exempts `/api/mcp` because the edge runtime cannot reach SQLite to check a per-chat credential, so the route checks it itself — the exemption and the check must stay together, or the tool surface is public. The capability is minted per turn, written to a 0600 file rather than into argv (where `ps` would show it), and revoked when the child exits. `telemetryEnv` does hand a child `UF_AUTH_TOKEN`, and that precedent was deliberately not followed: that token opens every route for as long as it is set, where this one opens a read-mostly tool surface — the two things it can write are a proposal and a template's prompt, neither of which does anything until a person acts on it — and dies with the turn.

**The chat runs with no tool allowlist, so the system prompt is the boundary.** It runs `--permission-mode bypassPermissions` with no `--allowedTools` and no `--disallowedTools`: an orchestrator's whole job is to find out enough to propose good work, and the allowlist this replaced — this app's tools, `Read`/`Glob`/`Grep`, read-only `gh`, `git log`/`status`/`branch`, `cd` — refused every question it had not anticipated (a build log, `gh api`, `git -C <path> log`, anything compound), which is a bad proposal an operator then approves believing it was researched. Not `plan`, which refuses MCP tool calls outright (measured: `Cannot call mcp__uf__list_templates while in plan mode`) and would leave the chat able to read GitHub and not this app; not `acceptEdits`, which holds mutating shell for an approval a `-p` child has nobody to give — the same failure `ISOLATED_GIT_TOOLS` exists to fix — so it would reproduce the refusals less predictably. What replaces the allowlist is `systemPrompt()`, which states the role rather than a list of forbidden tools: look, do not build; do not edit, commit, push, or act on GitHub; a task small enough to just fix is a proposal that says it is small. Everything that bounds this child is elsewhere and unchanged — nothing it can call starts a run, `--strict-mcp-config` keeps the mounted `~/.claude`'s MCP servers out, the capability token dies with the turn, `chatTurnBudgetUSD` caps the spend, and `--add-dir` still names only the mounts. The costs are real and are written down rather than absorbed: the chat can write into a checkout the operator also works in, and `githubEnv()`'s token now authenticates writes as well as reads. `permission_denials` is still read and shown in the thread — now because it should be *empty*, so an entry is the CLI declining something on its own.

**A chat turn is spend with no `evaluateBudget` behind it.** It passes the same gate a review does — `assistRefusal()`, the operator's own configured ceiling already spent — and nothing else, because there is no per-chat fraction and inventing one would be a threshold nobody set. `settings.chatTurnBudgetUSD` (default $2, null disables) is therefore the only other bound besides the ten-minute timeout, and it is enforced *inside* the CLI via `--max-budget-usd` rather than between cycles. `chat_sessions.cost_usd` is displayed on the chat page only: never added to `runs.spent_usd`, never to the meters. `githubEnv()` reaching this child is a real widening of "GitHub credentials reach a work cycle and nothing else" — a chat asked to read issues cannot without it — and is written down rather than absorbed quietly.

**A reopened run carries one message, resolved at the door and consumed at the spawn.** `reopenRun` writes the literal first-cycle prompt into `runs.follow_up`; `nextPrompt` prefers it over the continuation, and the loop clears the column the moment it hands it to a spawn — not after the cycle returns, because a run that parks or is killed from there on has already had it delivered and replaying it would say the same thing twice. Resolving to *text* rather than to a flag is what lets `completed` be reopenable at all: the substitution depends on the status the row is being picked up **from**, which a queued row no longer records. With no operator note, a run whose agent replied `DONE` gets `donePushbackPrompt` — the continuation prompt asks for `DONE` when the work is complete, so replying to a `DONE` with it is the same billed spin `continueAfterDone` already avoids — while `failed`/`stopped` get the continuation as before. **`completed` is not that reply**: it is also what a run that used up `maxIterations` is written as, and `maxIterations` defaults to 1, so keying the substitution on the status told the ordinary interrupted run that it had reported the task complete and then forbade it from starting new work. `runs.reported_done` records what the agent actually said, at the moment the cycle ends and the answer still exists — the stop reasons differ, but they are user-visible prose and not something to parse — and `reopenPrompt` is the one branch that reads it. Rows written before that column read as not-done, which is the cheaper error: a continuation into a finished session buys one billed cycle that says `DONE` again, where the pushback costs the work the run was reopened for. A note with no session to resume into is **appended** to the original task rather than sent alone: the run is starting over, and a reply-shaped note would read as the whole job. `nextPrompt` and `reopenPrompt` are pure and unit-tested for exactly these branches; every one of them is billed.

**Whether a run can be continued is decided by `session_id`, so it is recorded the moment the stream names it — not when the cycle returns.** `handleStreamLine` calls back on the first `session_id` it sees and on any change; `adoptSession` sets the loop's own variable *and* writes the column. Writing it only in the post-cycle UPDATE meant every failure that stopped a first cycle *returning* — a spawn failure, a container restart mid-cycle — left it null however far the cycle had actually got, and reopening that run re-sent the original task. That is a literal restart with the previous attempt's commits still on the branch, which is the one outcome the whole reopen path exists to avoid. The empty-string guard in that callback is load-bearing for the same reason the null check is: `nextPrompt` and `--resume` both key on *having* a session.

**A resume that comes back under a different id is logged, never treated as a failure.** `if (res.sessionId) sessionId = res.sessionId` used to adopt whatever arrived with no comparison against what `--resume` was given. Which id Claude Code reports for a resumed conversation is its business and has never been checked here against a real CLI, so the mismatch is recorded rather than acted on — but adopting it silently means every later cycle continues a conversation nobody chose, which from outside is indistinguishable from a restart.

**The first cycle of a resumed segment is the one that can fail without doing anything.** `looksLikeResumeFailure` is `usedResume && cyclesThisSegment === 1 && !sawResult && finalText === ""`: no cycle in this segment has completed, so the id can only have come off the row, which makes those two conditions exactly "this segment opened by resuming a session an earlier one left behind". It deliberately does **not** also require `pause_count > 0` — a session truncated mid-turn is truncated whether a guard parked the run or a crash ended it, and a run picked up by hand has `pause_count === 0`, so that condition excluded the single case an operator is watching. The one retry re-resumes `resumeTarget` rather than anything the failed attempt named, because a cycle that passes this test did no work at all and an empty session the CLI opened before giving up is worth less than the conversation being retried for.

**A restart on top of existing work says so in the prompt.** `nextPrompt` takes `priorCycles` (read *before* the loop's increment) and, when it has to open with the task text on a run that has already been charged for cycles, prepends a notice naming the branch for an isolated run and the folder otherwise. Nothing else in that prompt refers to the earlier attempt — the conversation that held it is gone by definition — and an agent handed a bare task does the first thing it says, which is the work it is standing on. This is the floor under a restart, not a replacement for resuming: `DEFAULT_CONTINUATION_PROMPT` still restates nothing, because on a conversation that really is intact a restatement is spend for no information.

**`cancelled` is checked twice per cycle, and both matter.** Once before committing to a cycle (the top-of-loop check is separated from the spawn by a transcript scan that takes seconds, and `stopRun` has already promised no further cycle will start), and once after the child returns, *before* the exit-code test — a SIGTERM'd child closes with a null code that reads as `-1`, so testing the code first files every deliberate stop as `failed`. Likewise `runIteration` resolves on `exit` with a grace period, not on `close` alone: `close` waits for inherited pipes, and an agent that leaves a grandchild behind would otherwise hold its folder until the next restart.

**One writing run per folder subtree, unless the run is isolated.** A **paused** run holds two claims and yields one of them. Its **worktree slot** is absolute — it resumes onto the same branch carrying its own commits, so `activeRuns()` still selects `('queued','running','paused')` and `allocateSlotPath` still skips it. Its **folder** is not: `selectPromotable` reserves for `running` rows only, so a run submitted afterwards takes the folder and works while the parked one waits. Nothing is in the directory twice, because the parked run cannot come back until the folder is free — `sweepPaused` refuses to un-park it while a run is in there, and says so in its stop reason rather than leaving "waiting for the next 5-hour window" standing after that window cleared. It stays `paused` while it waits, deliberately: `paused` is what `reconcileOnBoot`'s grace exception keys on, and joining the queue instead would make a restart close it out. The cost is that a younger queued run can be promoted ahead of it in the ≤60s before the next sweep — accepted, because a parked run losing priority to work that is ready now is the point. `/api/folders` reports the two separately (`busyRunId` blocks, `parkedRunId` is a note), and a parked run has never consumed a concurrency slot. "Folder" means `(physical tree, path within it)` — `conflictKey()` — compared segment-wise and case-folded by `overlaps()`. Path equality is wrong three ways, all reachable from shipped config: the picker offers the mount root, which contains every folder under it; two mounts can be one host directory (compose defaults `UF_WORKSPACE_2..4` to `${UF_WORKSPACE}`); and macOS is case-insensitive. Mount identity is resolved once, at first use, because `/api/folders` annotates up to 400 folders per request and because a per-check `stat` that throws would fail **open**, permitting exactly the collision this prevents.

**The folder claim is a synchronous check-then-insert.** `createRun` runs from entry to INSERT with **no `await`**, so one event-loop turn covers deciding a folder is free and recording that it was taken. Adding a single `await` to that path silently reintroduces two agents in one directory; the `db().transaction()` wrapper does not save you, because better-sqlite3 is synchronous either way. Never key occupancy on `isRunning()` — `procs` is emptied at the end of every iteration, so it reads false while a running run sits in its pre-iteration scan.

**A restart must close out its own runs, except a recent pause.** `reconcileOnBoot()` (via `src/instrumentation.ts`) marks stale `running` rows failed and `queued` rows stopped. Without it one crash blocks a folder permanently. It **never signals a pid**: the DB outlives the container, so a recorded pid names something else after a restart — plausibly this server. Queued rows are stopped rather than resumed, because auto-starting a days-old prompt as an unattended `acceptEdits` agent is the one thing a queue must not do by itself. A `paused` row within `settings.resumeGraceHours` (default 24) is the deliberate exception: it is not an unreviewed prompt but a run the operator started in a mode chosen precisely so it would carry on across windows, and the sweeper re-evaluates its budget from scratch before anything spawns. Past the grace period it is closed out like any other stale row — that boundary is what keeps the exception from becoming the rule it exempts. A `running` row stays `failed` even under `live-resume`: the child is gone with unknown state, and mapping that to `paused` would be guessing.

**An isolated run is granted the two git commands it is ordered to use.** `acceptEdits` — the default the run form and `chatDefaultGuards` both start from — auto-approves file edits and read-only shell, and holds mutating git for a human: `git add` and `git commit` each come back `This command requires approval`, and a `-p` child has nobody to give it. So the isolation preamble told the agent to commit as it went and the permission mode made that impossible. Measured, not reasoned: four runs finished `completed`, on their own branches, each having tried to commit and been refused, with the whole change left uncommitted in a worktree that `landState` then read as a branch with nothing on it. `buildArgs` therefore passes `--allowedTools Bash(git add:*) Bash(git commit:*)` for `isolation === "worktree"` only — additive, so everything else still follows the mode, and verified against the real CLI along with the fact that `--allowedTools` does not restrict what it does not name. Not `bypassPermissions`, which would also hand the run the network and `rm`; and not for a run in the operator's own checkout, which is told nothing about committing.

**A refused tool call is reported, because the alternative is a run that looks like it chose not to.** The `result` event carries `permission_denials` (confirmed on the wire for `stream-json`, not only for the `--output-format json` that `chat.ts` reads), and `permissionDenials()` groups it by tool *and command* — every entry's `tool_name` is the bare `Bash`, so "Bash ×7" would say nothing. This is the line that turns the failure above from a transcript-archaeology exercise into a log entry.

**An isolated run works on a branch, and a worktree contains committed work only.** `seedWorktree` copies the gitignored config files named in `settings.isolationCopyGlobs` and nothing else — dependencies are the agent's job, and slot reuse is what makes that cheap. The handoff card withholds the `git merge` command entirely while the operator's own checkout is dirty rather than showing it with a caveat, because a copyable command gets copied.

**The tool does now merge, and every protection the old "never merges" rule bought is a check in `land.ts` rather than a caveat.** The operator's checkout must be clean (unreadable counts as dirty, same rule as `emitHandoff`) *and* standing on the recorded target branch — landing onto the wrong branch is the one mistake here with no undo, so it is refused by name rather than caveated. An active run's branch is never landable: `running`/`queued`/`paused` can commit again, and the base that merges cleanly now will not be the base in ten minutes. A failed merge is aborted immediately and the conflicting files reported, so a half-merged index never survives the request. `landRefusal` is pure and unit-tested for exactly these branches, because it is the decision that writes into a directory a person also works in.

**Finding out whether a merge works must cost the operator nothing.** `merge-tree --write-tree` does the three-way merge in memory — no checkout, no index, only unreferenced objects in the object store — so the preview is honest *before* any decision. It needs git ≥ 2.38; an older git reports `unknown`, never "clean". `parseMergeTree` treats every exit code other than 0 and 1 as undetermined for that reason. Those unreferenced objects are also what makes the conflicting *content* free: the tree it writes holds each file as a real merge would leave it, so `withRegions` reads the `<<<<<<<` blocks straight out of it — capped at `MAX_CONTENT_FILES`, since this runs on every load of the land card. A file past that cap keeps `regionsRead: false` rather than an empty list, because "not looked at" and "nothing there" are different sentences and a modify/delete really does leave no markers.

**What conflicts comes from the stage records; why comes from the messages, and only the first is trusted.** `-z` is what makes the conflict type readable at all — the plain output states it only in prose, and finding the path in "CONFLICT (content): Merge conflict in f.txt" means parsing a filename out of a sentence, which is the mistake `splitPatches` exists to avoid. But the informational section's field layout was captured from git 2.50 and the container ships 2.39, so it is parsed defensively and contributes nothing but annotation: an unreadable one loses the type and the explanation and still lists every conflicting file. A message naming a path the stage records did not is **ignored**, never added — what counts as conflicting is what `landRefusal` counts, and that must not shift with a prose format.

**A resolution is shown as what it did, not only as what it said.** `run_reviews.resolved_commit` is read off the isolated checkout the moment the merge commits, because that checkout is removed seconds later and the commit is the only handle on the work afterwards; `resolved_paths` is recorded at the same time so the display is the resolution rather than everything the merge brought across. `resolutionChange` diffs that commit against its **first** parent — the branch as it stood — which is the one framing that never comes back empty: a `--cc` combined diff shows nothing at all for a clash settled by taking one side whole, and "the resolution changed nothing" is exactly the wrong thing to tell someone about to land it.

**Several branches are a queue, never a batch, and the queue re-decides at every turn.** `mergeQueue.ts` reverses the "one button per run" rule, and earns it by keeping what that rule protected: one merge in flight (a single sequential worker, one per process), and `landRun` re-deriving the whole `LandState` for every item at *its* turn rather than trusting the answer the page had — each landing changes the base for the one behind it, so a preview taken when the queue was made is worthless by the second item. `position` is the operator's order and the only thing that decides what runs next; `created_at` would silently reorder two rows queued in the same millisecond.

**A queue tells a branch's problem apart from the checkout's.** `planItem` returns `fail` for the first — the branch behind it is unaffected — and `halt` for the second, which marks every remaining row *in that repository* skipped with one reason instead of scrolling ten identical refusals past. It therefore tests the checkout **before** the conflict, the one place it deliberately disagrees with `landRefusal`'s ordering: that function answers "why can this not be landed", where the conflict is the fact about this branch; this one answers "what should happen next", and paying a model to reconcile a branch into a checkout that will refuse the merge anyway is money spent on nothing.

**Auto-resolution is authorised per batch and recorded per row.** `review.ts` says nothing automatic may reach it, because spend nobody asked for is spend nobody authorised — queueing with the toggle on *is* that authorisation, which is why `auto_resolve` lands on every `merge_queue` row rather than in `settings`, where it could change under a queue already running. `POST` reads it as `=== true` for the same reason `continueAfterDone` does. A refusal that is about the operator's *window* rather than about the branch stops later resolutions being attempted at all: it will refuse every one of them identically, and each attempt costs a full transcript scan to find that out again.

**A queued merge is cancelled on boot, never resumed.** Same rule as a queued run, for a stronger reason: this one writes into the operator's own checkout, and a server coming back up and merging four branches into the tree someone is working in is the one thing a queue must not do by itself. A row caught mid-merge is failed without a guess about what happened — `landState` will say, from git, the next time anyone asks. Cancelling a batch leaves the row *in flight* alone: a merge is a multi-step write and a resolution is a child holding a checkout, and interrupting either part-way is worse than the second it takes to finish.

**The merge target is recorded, never assumed.** `worktree_base` is a *commit*: it says where a branch started, not where it belongs. `probeIsolation` now also records `worktree_base_branch`, and a detached HEAD stores null rather than the literal `HEAD`. Rows written before that column existed fall back to the branch currently checked out — but only after proving the run's base commit is an ancestor of it, which makes it a deduction, and `targetInferred` says so in the UI.

**A squash is landed work that git cannot see.** Squashing rewrites the commits, so the branch is never an ancestor of its target and `merged` is false for ever — which would both offer it for landing a second time and leave it undeletable. `landed_tip` records the branch tip at land time; `landedUnchanged` (tip unmoved) is what stands in for ancestry, and it stops being true the moment the branch gains a commit, which is exactly when deleting would lose something. Branch deletion uses `-d` wherever git can see the merge itself and `-D` only in this case.

**Work an agent left uncommitted goes onto its own branch, and nowhere else.** `commitPending` exists because that state is reachable and its symptoms point the wrong way: before `buildArgs` granted `git add`/`git commit` to an isolated run, every such run ended `completed` with a full checkout and an empty branch, which the land card reported as "this branch has no commits of its own" — a run that looks like it did nothing. It is also what frees the slot, since `ensureWorktree` refuses to reuse a checkout with work in it. The decision is `commitRefusal`, and the branch that earns the unit test is the slot one: a slot is reused, so what is uncommitted in it is only this run's while it still has this run's branch checked out — otherwise the commit lands one run's work on another run's branch, authored by nobody. `add -A` rather than the listed paths, because gitignored files stay ignored and a file written since the page loaded belongs to the same work. A failed commit is left **staged** rather than reset: a `pre-commit` hook is the likely refusal, and the agent may have staged part of it itself. `git status --porcelain` is the one output in this app that must not be trimmed — `" M path"` opens with a space that means "unstaged", and `git()` takes `trim: false` for it alone.

**Getting rid of a branch is two doors, and only the careful one is called Delete.** `deleteBranch` still refuses anything git cannot see as merged — that refusal is all that stands between a stray click and work that exists nowhere else — and `purgeBranch` is the deliberate other one, for the attempt that went nowhere and the slot it is holding hostage. It destroys committed work by design, so the caller has to **name the branch back**: that echo is not authentication and never selects anything (the row still decides what is deleted), it is what stops a request aimed at one branch from landing on another, and what forces the interface to spell out what goes. It force-removes the checkout, which `deleteBranch` will not do, and counts the commits and the uncommitted paths *before* anything is removed so the sentence afterwards says what was lost. Neither door is offered for an active run, and the UI never shows both at once.

**A conflict is resolved on the run's branch, never in the operator's checkout.** `resolveConflicts` merges the *target into the branch* — the opposite direction from landing — inside the run's own checkout when it still holds that branch, and otherwise a throwaway `<slug>-resolve` slot that is removed either way. A resolution that goes badly therefore costs a branch nobody has landed yet. The agent resolves **text only**: it runs `acceptEdits` (not `bypassPermissions`) and is told not to run git, because the app stages and commits *after* checking that no marker survived. `unresolvedFiles` treats an unreadable file as unresolved, and any failure ends in `merge --abort` with the branch exactly as it was — an agent that reports success having left `<<<<<<<` in a file is the specific failure this ordering exists to catch. When it succeeds the branch contains the target, so landing becomes a fast-forward and still goes through every check above. `hasConflictMarkers` matches only the two labelled markers, never a bare `=======`, which is a markdown heading underline.

**Reviewing a diff is not a work cycle and is never automatic.** `startReview` exists only behind a POST; nothing in the run loop reaches it. It refuses when the operator's *own* configured ceiling is already spent (`guardFraction >= 1` on either window) rather than going through `evaluateBudget` — there is no per-run fraction for a review and inventing a threshold would be a limit nobody set. The reviewer is given the diff, the run's task and how the run ended, but **not** the event log: the log is the process rather than the outcome, and a reviewer that reads how the agent got there reviews the journey. A large diff is cut at a file boundary and the omitted files are *named* in the prompt, because a reviewer handed a third of a change with no marker writes a confident review of a change that did not happen.

**GitHub credentials reach a work cycle and nothing else.** The container has no other way to authenticate — the `~/.claude` mount carries Claude's login and neither `~/.gitconfig`, `~/.ssh` nor `~/.config/gh` — so `git push`, `gh pr create` and `gh issue view` all fail, and they fail *inside a tool call the run loop never inspects*: the cycle simply ends without the pull request. `githubEnv()` is where the token is turned into an environment, mirroring `telemetryEnv()`, and it sets three things because the failure arrives three ways: `GH_TOKEN`/`GITHUB_TOKEN` for the CLI, a credential helper for `https://github.com` for plain git, and `url.…insteadOf` rewriting `git@github.com:` to HTTPS because no key and no agent reach this container — that last one is the likeliest reason this fails on *some* repositories and not others. It travels as `GIT_CONFIG_*` rather than a config file, so it applies to every git the agent runs and dies with the process instead of outliving the run in a mounted tree; the helper list is **reset** first, because a repository cloned on the host can name `osxkeychain` in its own config and git consults helpers in order. The helper reads `$GH_TOKEN` at call time rather than embedding the token, so `git config --list` does not print it. `GIT_CONFIG_COUNT` must equal the number of key/value pairs — git discards the entire block otherwise, silently, which looks exactly like the unauthenticated container this exists to fix. Withholding is by namespace, not by remembering: `gitEnv()` and `reviewEnv()` strip `UF_*`, so the reviewer (which cannot write) and this app's own git (whose children run repository-controlled hooks, and which never touches the network) are excluded by construction.

**Diffing runs repository-controlled code unless it is told not to.** Every `git diff` here carries `--no-ext-diff --no-textconv`: `diff.external` and a `diff.<driver>.textconv` reached through `.gitattributes` are both *commands git runs*, configured by the repository being rendered. Same class as the `core.fsmonitor` clearing that already applies to every call. Paths that come back from git and go out again as pathspecs are pinned with `:(top,literal)`, or a filename containing `*` would be read as a glob.

**A diff that was shortened says so.** The file *list* is always complete; patch bodies are budgeted (`selectForPatch`), and what the budget leaves out is counted and rendered as "N files listed without contents" rather than dropped. `splitPatches` matches chunks to files **by position**, never by parsing the header path — git re-quotes odd filenames there — and a count mismatch yields no patches at all rather than hunks filed under the wrong name.

**The UI says "work cycle", the code says "iteration".** User-facing copy names the unit a first-time user must reason about; `Settings`, `BudgetPolicy`, the API payloads, and the `runs` table keep `iteration`/`maxIterations`. Don't rename the internals to match the copy, and don't reintroduce "iteration" into the UI.

**Every budget rule can be switched off, but the loop must always have a monotone terminus.** `null` means "no limit" for cost, tokens, duration, and both fractions — `normalizePolicy` maps `null`/`""`/`0` to `null` rather than to a default, so a blank field disables a guard instead of quietly restoring one. `maxIterations` is nullable too, but only alongside `maxDurationMinutes`: those two are the only quantities that move one way and keep moving. This run's own spend stops accruing the moment a cycle is killed before it reports, and both window fractions can *fall*. The pair is enforced in `POST /api/runs` (which has an error channel) and refused again as `no_terminus` in `evaluateBudget`; `normalizePolicy` must stay total and idempotent, so it never rejects — and never coerces the illegal pair into a limit the user did not ask for. Only an explicit `null` asks for an uncapped loop; blank, zero, negative and missing all still mean one cycle.

**`continueAfterDone` sends the agent back in after `DONE`, with a different prompt.** It must be `settings.donePushbackPrompt`, never `continuationPrompt` — that one says "if it is fully complete, reply with exactly DONE", so feeding it back after a DONE produces an immediate second DONE and a tight, billed spin loop. The flag is read as `=== true`, not `Boolean(...)`: it makes a run refuse to stop, so a string `"false"` off the wire must fail safe.

## Security-critical paths

- `resolveInMount()` (`orchestrator.ts`) checks containment on the lexically resolved path **before** touching the filesystem, then **again** after `realpathSync` — a symlink inside the root can still point out of it. Both checks are load-bearing. `resolveWorkspaceFolder()` runs that pair against **one mount at a time**; multiple mounts widen which roots are legal, never what counts as contained. A run is confined to the mount it started in.
- Containment stays **per mount**, while collision detection is deliberately **cross-mount**: `conflictKey`/`overlaps` see two mounts onto one directory as one folder. Widening what counts as a collision never widens what a run is permitted to touch.
- Worktrees live at `<mountRoot>/.uf-worktrees/<repo>-<slot>` so the unmodified `resolveInMount` validates the agent's cwd. `ensureWorktree` `lstat`s that directory and refuses a symlink **before** git writes — validating afterwards would mean a full checkout had already landed wherever the link pointed.
- The agent is spawned with an argument array and `stdio: ["ignore", "pipe", "pipe"]`, **never a shell**, so prompt metacharacters are inert. `gitSync` does the same, and additionally strips `ANTHROPIC_*`/`UF_*` from the child environment and clears `core.fsmonitor`: both `worktree add` (via `post-checkout`) and `status` (via fsmonitor) can execute repository-controlled commands.
- `gitArgs` also passes `safe.directory=*`, and the image sets it system-wide for the agent's own git. This is a deliberate waiver, not an oversight: a bind mount carries the *host* uid, and git's ownership refusal reaches `probeIsolation` as an unreadable repository — indistinguishable from "not a repository", so isolation would switch itself off and say the wrong thing about why. The check guards against repositories encountered by surprise on a shared host; every path that reaches `gitSync` has already been proved inside a configured mount by `resolveInMount`, which is the containment guarantee that actually matters here. Keep it paired with `UF_UID`/`UF_GID` in compose — the waiver makes git *work* against a foreign-uid mount, it does not make the mount *writable*.
- `UF_GITHUB_TOKEN` is scoped twice over. It reaches only the agent's work cycles (`githubEnv()`), and the credential helper it installs is keyed to `https://github.com`, so a repository whose submodule or remote points at another host asks for credentials and gets none — with `GIT_TERMINAL_PROMPT=0` alongside it, that fails in a second rather than hanging until the run's duration limit.
- `permissionMode` is narrowed against the four literals in `POST /api/runs` before it reaches `--permission-mode`.
- **An agent cannot select processes by name to signal them.** `buildArgs` passes `--disallowedTools Bash(pkill:*) Bash(killall:*)` on every spawn — a deny rejects the whole Bash call, so a `pkill` buried in a `;`-chain takes the chain with it, which is the form the incident arrived in — and `--append-system-prompt` carries the reason *and the safe recipe*. The deny alone buys one turn, since `kill $(pgrep -f next-server)` is not `pkill` and is exactly as fatal; a bare prohibition buys the opposite failure, a dev server nobody can stop holding its port for the life of the container. So the notice spells out pid capture, the `pgrep -P` child form, and selecting on the port rather than the title. Next renames this server's process to `next-server (v…)`, which is *also* the title of any dev server an agent starts to check its work, so a name match cannot tell the two apart and reaches whichever was there first. One `pkill -f "next-server|next dev"` ended the container (`restart: unless-stopped` brought it back) and `reconcileOnBoot` marked fourteen runs failed 690ms later, including the run that issued it. There is no ownership boundary to enforce this with instead: compose runs a single uid. Plain `kill` stays permitted — a pid is a handle on a process the agent started, a pattern is a guess about the machine — and denial survives `bypassPermissions`, which is the only reason the argv is worth anything here.
- `src/middleware.ts` runs in the **edge runtime**: it reads `process.env.UF_AUTH_TOKEN` directly and must not import `lib/config` (which pulls in `node:os`/`node:path`). Comparison is constant-time; API paths get 401, page paths redirect to `/login`. `/api/mcp` is the one exempted path, and it authenticates itself — removing the check there makes the chat's whole tool surface public.
- The chat's capability token is compared constant-time against every live token in `chatForCapability`, rather than looked up by key: a `Map.get` on a secret leaks its prefix through timing. The live set is the number of turns in flight, which is one.
- `bypassPermissions` is offered in the new-run form with a warning; the default stays `acceptEdits`.

## Conventions

- **Server-only vs client.** `src/lib/apiTypes.ts` holds the DTO mirror of the server types so client components never transitively import `node:fs`. `src/lib/format.ts` is likewise client-safe. Don't import `windows.ts`/`transcripts.ts` types into a `"use client"` file — add to `apiTypes.ts` instead.
- **Route handlers** that touch SQLite or the filesystem need `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`. Every existing data route has both.
- **Module state survives dev hot reload** via `globalThis` singletons: `__ufDb`, `__ufBus`, `__ufProcs`, `__ufCancelled`, `__ufTranscriptCache`. New long-lived state must follow the same pattern or it silently resets on every request in dev.
- **Schema changes** go in `migrate()` in `db.ts` as idempotent `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements — there is no migration framework or version table.
- **Pages are client components** that poll their API route (dashboard 10s, run detail 3s for the row while SSE carries the log). There is no server-side data fetching or React Server Component data layer.
- **Styling** is Tailwind v4, CSS-first — no `tailwind.config.js`, no CSS modules, no third-party component library. Primitives live in `src/components/ui/`. Four things in `src/app/globals.css` are load-bearing and were each arrived at by measurement, not preference:
  - **The `@layer theme, base, legacy, components, utilities` statement.** Layer precedence is declared, never inferred: `next dev` and `next build` emit the blocks in *different* orders, so an inferred order means the legacy sheet beats utilities in the browser and loses to them in the shipped image.
  - **`@import "tailwindcss" source(none)` plus an explicit `@source`.** Automatic content detection respects `.gitignore`, and `.dockerignore` hides `.gitignore` from the build context — so the container would scan `CLAUDE.md` and `tsconfig.tsbuildinfo` and emit a different stylesheet than the host. A class would work in `next dev` and be missing from the image.
  - **Tokens keep their existing semantic names** (`--bg-raised`, `--fg-muted`, `--warn`) and `@theme inline` maps them to utilities. `inline` is mandatory — without it a utility freezes one theme's value at the definition site. Three theme states come from `color-scheme` + `light-dark()`: absent `[data-theme]` follows the OS, the two explicit values override it. Do not put `font-size` back on `html`; it redefines `rem` and silently shrinks every spacing and type utility by 12.5%.
  - **Variants are typed props with `Record<Union, string>` lookup maps, never `data-[…]` Tailwind variants.** Three reasons, all silent: React renders `data-x={false}` as the string `"false"`, which a bare `data-x:` variant matches on presence; Tailwind scans source as text, so an interpolated `text-${tone}` emits nothing; and `Meter` carries both `data-sev="ok"` and `data-unknown="true"` for an unknown reading (`severityFor(null)` is `"ok"`), where losing the tiebreak paints a solid green 100% bar instead of the hatched indeterminate one. `src/components/Meter.test.tsx` pins that last one. Shared tone unions live in `src/lib/format.ts`, not beside the components, because `src/lib` is what `tsconfig.test.json` compiles.
  - The `@layer legacy { … }` block is the migration's remaining surface and shrinks as pages move onto the kit. It still beats Preflight and still loses to utilities. When it is empty, delete it — and with it `--radius`, `--mono` and `--sans`, which exist only for its sake.
- `better-sqlite3` is a native addon — it must stay in `serverExternalPackages` in `next.config.ts`, and the Dockerfile's `deps` stage carries the build toolchain for it.
- Comments in this codebase explain *why* a decision was made (usually a correctness or safety trade-off), not what the code does. Match that when editing.
