# The orchestrator chat

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/chat.ts, src/app/api/mcp/.**

**The orchestrator chat picks what work to do; something a person wrote picks what an agent may do; a person decides whether it happens.** `chat.ts` is a conversation with a read-mostly tool surface, and the two tools that write anything add a `chat_proposals` row or a template's *prompt* — both inert, holding no folder claim and no concurrency slot. `planProposal` is where a proposal becomes a run, and the branch that matters is the one that is *not* in it: no value off a proposal sets a budget, a permission mode or an isolation choice. Those come from the named template, or from `settings.chatDefaultGuards` when it names none — the second one exists because requiring a template made the chat useless on a stock install, and it is a *person's* configuration either way, which is the property that matters. A proposal that names a template that has since been deleted is refused by name rather than falling back to the defaults: the operator approved the card that said "Fix a bug", and a run under different rules than the card stated is what this gate exists to prevent. `--permission-mode` is not something a model should be able to reach for — the same reason `reopenRun` refuses to become a third route to that flag. The approval route takes an explicit list of ids the page displayed, so a proposal the chat added between render and click is not swept into an approval nobody saw, and it approves in one synchronous pass because `createRun`'s folder claim is only atomic inside an event-loop turn. An id that is not pending in *that* chat is dropped rather than approved — and `decisionNote` then has to say which of the two things it was, because "already decided" is a sentence about this thread's proposals and a selection carried over from another one is not. A batch where every id is dropped is a 400 for the same reason an empty list is: a 200 with nothing started is indistinguishable from a batch that worked, and the page clears the selection on `res.ok`. **There is deliberately no setting that approves a proposal automatically, and the chat itself starts nothing — but auto-start does exist, in one place, and the approval it needs is a different one.** A workflow's orchestrator block starts its runs with nobody clicking anything, because a person saved a graph that had already named that block's folder, its guard set and the most runs it may ever start. The approval moved from the run to the graph; it did not disappear, and everything that made this paragraph's gate worth having survives the move unchanged — see the orchestrator-block invariant below.

**Prompt text is the one half of a run a model may write, and it is written down as an exception rather than absorbed.** `chat_proposals.prompt_override` replaces the template's prompt for one run, and `save_template` writes a name and a prompt back for reuse — taking `chatGuards()` for a new template and the row's existing guards for an update, so no argument on that tool can move one. The distinction is not cosmetic: guards decide what an agent *may* do and prompts decide what it is *asked* to do, and a chat that cannot adapt a prompt just restates its objections inside the task, which puts the same text in the run with nothing recording that it happened. `composeTask` keeps the two halves in order and separated by a heading, and emits the task alone when there is nothing standing above it — a section marker for a section that is not there is worse than no marker. Every proposal card says which guard set applies, spelling out the untemplated one, and marks a rewritten prompt.

**Who does the work is the third half a model may write, and it is the same act as writing the task.** `chat_proposals.agent_id` and a proposed graph's `agentId` name the saved agent a proposed run would be started as, and neither is an exception to the paragraph above: an agent is a description and a prompt, the registry refuses a tool list at the door and has no column for a permission mode, so `planProposal` and `planNode` gain no branch that reads a guard off either. It is an **id** rather than the frozen copy `runs.agent` holds, which is `run_templates`' rule and for its reason — a proposal is form input a person decides on, so it should name the agent as it stands at the click rather than as it stood when the model wrote the card, and the copy is taken where it always is, by `createRun`. A deleted or decayed one is refused **by name** through the same `agentRefusal` at both moments the template is checked at: when the tool records the proposal, where a model can act on the sentence, and again at approval, where the operator can. `list_agents` is what a turn reads first, and it is on the **shared** tool list rather than the chat's: a block names one too, and the alternative is a deciding turn guessing at names out of its system prompt. It grants neither subject anything — the same reason naming one is allowed at all — and it declares the ambient definitions beside the registry, because those reach every run whatever is named and cannot be named at all. The card carries the agent in the line that already carries the folder and the guard set, and *outside* the guard mark: a phrase under the shield would claim it bounds something, which is the one thing about it that is not true however large a fact it is otherwise. `summarizeProposedGraph` says it per block for the same reason it says the fan-out cap.

**The chat's own turn is not started as one, and the asymmetry with an orchestrator block is the whole reason.** `runOrchestratorChild` takes one `agent` and a block hands it the one its node names; `runTurn` deliberately hands it none. **The old reason for that is gone, measured, and is replaced rather than kept** — this is exactly the paragraph the singular flag was expected to overturn and did not. It used to rest on a doubt: a `--agents` member carries a system prompt of its own, and whether `--append-system-prompt` also reached the turn it was delegated was not verified against the pin, so this child — the only one in the app whose boundary is *prose* — could not absorb the question the way the others could. That is now measured, and it went the other way: an agent asked to answer with a secret word stated only in the appended text answered with it, so the appended prompt reaches a `--agent` session alongside the agent's own. What stands in its place is the stronger half of the same argument, and it is not a doubt. This child is bounded by `bypassPermissions`, no allowlist, and `systemPrompt()`'s look-do-not-build paragraph carried by `--append-system-prompt`. Selecting an agent here would make some saved prompt the orchestrator's own role — reachable from a registry a chat proposal can name — which is precisely the thing that paragraph exists to fix, and no measurement can make that safe. The second half is unchanged: there is no work here for one to do, since a chat turn looks and proposes, so what an agent would change is how the orchestrator *thinks*. The `@`-mention in the composer is what an operator actually wants from this — it names the agent the proposed *run* will be started as. Nothing in this app parses it back out of the message: it is text, read by a model that has `list_agents`, which is why a name with a space in it is inserted as it stands rather than quoted into a syntax nothing else here speaks. The popover takes **Tab**, the arrows and Esc and never Enter or ⌘↩, because this composer sends on Enter and a list that accepted a completion with it would swallow the send exactly when the operator had finished typing a name.

**Order is the other half of the work a model may write, and it is a label until a person approves it.** `chat_proposals.spec_id` is the chat's own name for a proposal and `depends_on` is what it says that proposal starts after — labels rather than ids, because the model writes several proposals in one turn and has to point one at another before either has an id. They resolve to *run* ids at approval and nowhere else: `planApprovalBatch` is that decision, pure and unit-tested for `planProposal`'s reason with `releasableRuns`' failure modes. A label naming a sibling in the same click resolves to the run this pass is about to create; one naming a proposal of this chat that already became a run resolves to it; anything else **fails that one proposal by name**, and everything behind it fails too with its own sentence naming the one in front of it. Dropping the edge instead is the failure this exists to have none of — a run told to wait and started immediately is bit-for-bit a run that was never told, and the two agents then work in the same checkout in whatever order the queue felt like. The batch is created in `topologicalOrder`, which moved to `orchestrator.ts` beside `dependencyCycle` for that function's reason: three callers now create runs in one synchronous pass and "every one after what it waits for" has to mean one thing. Without it the order is whatever the page displayed, and a proposal is refused as naming a missing run — an artefact of a render, reported as a fact about the work. Everything `admitDependencies` already decides is deliberately *not* re-decided here — one branch handed over, both ends isolated, no rival continuation, no loop against the live graph — because those need rows and a second copy would be a second set of rules to keep in step; what `propose_run` does check at the door is the subset it can, for the reason it validates everything else there.

**The chat can write a workflow, and approving one saves it rather than starting it.** That asymmetry with `propose_run` is the whole design. An orchestrator block's runs start with nobody looking *because a person fixed its folder, its guard set and its fan-out cap when they saved the graph* — and a graph a model wrote has no such person in it. Saving rather than starting puts one back: the operator reads a card that spells out every guard-shaped fact a canvas would show (`summarizeProposedGraph` — which template supplies each block's guards or the untemplated set written out, where each block runs, how many runs a deciding block may start, whether a merge block may pay to reconcile), then opens the graph, then presses Run. Two separate human decisions stand behind every number in it before an agent exists. `planWorkflowProposal` re-normalizes through the *same* `normalizeWorkflowInput` and the same `folderRefusal` the save route and the validate route call, with the same `currentKnowledge()`, so a template deleted between the proposal and the click is refused by name exactly as `planProposal` refuses one — a second set of rules about what a workflow may be would be confidently wrong about what Approve does the day one of them changed. The **instance budget is not carried**, and there is nothing on the wire that could carry it: no field on the tool, no column on the row, no argument on the plan. That is `startWorkflow`'s "there is nothing to raise it *with*" applied one level up, and its cost is stated rather than absorbed — a proposed workflow runs by hand and `scheduleRefusal` will not let it be scheduled until the operator sets one, which the card says in words. `propose_workflow` requires a `folder` on every non-merge block even though `normalizeWorkflowInput` accepts `""`: the empty string is a real answer from the editor's picker and an *omitted* field is not that answer, and reading one as the other would silently put a block on the mount root — the one selection that blocks every other run in the tree.

**The chat's tools run in this process, and that is a correctness requirement rather than a convenience.** `/api/mcp` speaks MCP over HTTP by hand — `initialize`, `tools/list`, `tools/call` — and the handlers call `createRun`, `listTemplates` and `scanWorkspace` directly. A stdio MCP server would be a second process doing check-then-insert against the same SQLite file, which silently permits the two-agents-in-one-directory collision the folder claim exists to prevent. `workspace.ts` exists for the same reason in miniature: the picker and the chat must not be able to disagree about which folders exist or which are busy.

**The chat's child authenticates with a capability, never with `UF_AUTH_TOKEN`.** `middleware.ts` exempts `/api/mcp` because the edge runtime cannot reach SQLite to check a per-turn credential, so the route checks it itself — the exemption and the check must stay together, or the tool surface is public. That check also has to stand **outside** `auditMutation`, and for a reason about the audit log rather than about this route: it *is* the authentication for the whole tool surface, so a request that fails it has passed nothing at all, and auditing that refusal made `request_log`'s 20,000-row cap a lever anyone who could reach the path could pull — twenty thousand refusals and every line naming a run that was started or a sign-in that failed is evicted. Only the handler that already holds a subject is wrapped, which keeps the line the table exists for (a real capability whose tool call was refused, which is the burst somebody comes looking for afterwards); `DELETE` is not audited at all, being a 405 answered before any credential is read; and the refusal goes to stdout, which nothing caps. The capability is minted per turn, written to a 0600 file rather than into argv (where `ps` would show it), and revoked when the child exits. That file is in a per-turn directory of its own under a base the *server* owns, never in `os.tmpdir()`: `/tmp` is 1777, so `ls /tmp/uf-mcp-*.json` found a live capability without guessing its random name and any of the concurrent agents could run it — the name was never the protection, the directory was the leak. Both are removed on every settle path, including the partial-write one inside `writeMcpConfig`, since a directory left behind is a leak in a path nothing else sweeps. The directory closed enumeration and nothing else, and what closes the rest is a **group**: `--mcp-config <path>` is an argv element and `/proc/<pid>/cmdline` is world-readable, so a work-cycle agent read the path off a sibling's command line and opened a file its own uid owned. Under `UF_CHAT_GID` the per-turn directory and file are handed to a group the chat and block child is in and no work cycle is — 0710 and 0040, so a thief fails the owner check, fails the group check, and is left with the "other" bits, which are zero. A gid rather than a second uid because the chat child must stay the uid that owns the mounted `~/.claude`: that credential is what it authenticates and bills with, and a second uid would need a second Claude account. `chatChildCredentials()` is the one place that differs from `childCredentials()`, and `mcpConfigOwnership()` returning null — no `UF_CHAT_GID`, or no privilege separation at all — falls back to the previous arrangement whole rather than half-applying it, because a config the child cannot read is a turn with no tools, which reads as a model that chose not to call any. It names a **subject** rather than a chat id, and that is a discriminated union rather than two optional ids on purpose: the subject is what decides which tool list the caller is offered, and a shape where both ids can be absent is a shape where the route can forget to check which it has. The subject also *scopes* one tool: `get_run_diff` answers for the runs a chat proposed (`chatOwnsRun`) or the runs of a block's own instance (`instanceOwnsRun`), and refuses the rest with a sentence naming what to use instead. That is the one place blast radius is bounded rather than the theft prevented — a token is its holder's identity, so a stolen one is indistinguishable from the turn that minted it, and patch text was the one thing on this surface a work cycle could not otherwise reach from the folder it was started in. `list_runs` and `get_run` stay install-wide deliberately: "what is already in flight" is the question the orchestrator exists to answer, and a file list is not a patch. `telemetryEnv` used to hand a child `UF_AUTH_TOKEN`, and that precedent was deliberately not followed: that token opens every route for as long as it is set, where this one opens a read-mostly tool surface — the two things it can write are a proposal and a template's prompt, neither of which does anything until a person acts on it — and dies with the turn. That reasoning was an argument for fixing the exception rather than for keeping it, and the exception is gone: the exporter now carries a capability of the same shape, minted per run by `ingestTokenFor`, opening one thing (writes to that run's own telemetry) and revoked when the run's loop ends.

**The chat runs with no tool allowlist that bounds anything, so the system prompt is the boundary.** It runs `--permission-mode bypassPermissions` with no `--disallowedTools` and one `--allowedTools` that grants nothing — `SEARCH_TOOLS`, which is `Grep` and `Glob`, named because the pinned CLI otherwise does not offer them at all and an orchestrator with `Read` and no way to find what to read proposes badly for exactly the reason below. Under `bypassPermissions` there is no prompt for a named tool to skip, so it moves no boundary; what it moves is the tool list. An orchestrator's whole job is to find out enough to propose good work, and the allowlist this replaced — this app's tools, `Read`/`Glob`/`Grep`, read-only `gh`, `git log`/`status`/`branch`, `cd` — refused every question it had not anticipated (a build log, `gh api`, `git -C <path> log`, anything compound), which is a bad proposal an operator then approves believing it was researched. Not `plan`, which refuses MCP tool calls outright (measured: `Cannot call mcp__uf__list_templates while in plan mode`) and would leave the chat able to read GitHub and not this app; not `acceptEdits`, which holds mutating shell for an approval a `-p` child has nobody to give — the same failure `ISOLATED_GIT_TOOLS` exists to fix — so it would reproduce the refusals less predictably. What replaces the allowlist is `systemPrompt()`, which states the role rather than a list of forbidden tools: look, do not build; do not edit, commit, push, or act on GitHub; a task small enough to just fix is a proposal that says it is small. Everything that bounds this child is elsewhere and unchanged — nothing it can call starts a run, `--strict-mcp-config` keeps the mounted `~/.claude`'s MCP servers out, the capability token dies with the turn, `chatTurnBudgetUSD` caps the spend, and `--add-dir` still names only the mounts. The costs are real and are written down rather than absorbed: the chat can write into a checkout the operator also works in, and `githubEnv()`'s token now authenticates writes as well as reads. `permission_denials` is still read and shown in the thread — now because it should be *empty*, so an entry is the CLI declining something on its own.

**A chat turn is spend with no `evaluateBudget` behind it.** It passes the same gate a review does — `assistRefusal()`, the operator's own configured ceiling already spent — and nothing else, because there is no per-chat fraction and inventing one would be a threshold nobody set. `settings.chatTurnBudgetUSD` (default $2, null disables) is therefore the only other bound besides the ten-minute timeout, and it is enforced *inside* the CLI via `--max-budget-usd` rather than between cycles. `chat_sessions.cost_usd` is displayed on the chat page only: never added to `runs.spent_usd`, never to the meters. The same money also lands as **one dated row per settled turn** in `chat_turn_spend`, and the two are both needed because neither is derivable from the other: the running total answers *what has this thread cost*, which is what the page shows, and the rows answer *what did this install spend on chat inside the window*, which is what the install-wide ceiling reads. Summing the running total bounded on `updated_at` charged a fortnight of conversation to whichever day one four-cent message landed in, closing every door in the app and stopping the runs already in flight. The row is written inside `finishTurn`'s existing latch and after it, so a late settle that moved no total adds none. `githubEnv()` reaching this child is a real widening of "GitHub credentials reach a work cycle and nothing else" — a chat asked to read issues cannot without it — and is written down rather than absorbed quietly.
