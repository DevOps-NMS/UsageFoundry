# What the test suite covers, and what earns a test

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing any src/**/*.test.ts, or when deciding whether a change needs one.**

or twenty-five unattended agents holding the server's own uid under a container that reads, from every page and every log line, exactly like one that separated them; or two mounts onto one host directory reported as two repositories with half the money each, or a repository's bill quietly missing every run that was not in a git checkout; or a second server that has correctly worked out it owns nothing and admits a run anyway, so two processes each decide one folder is free inside their own event loop and two agents start work in one checkout, or an owner that stalled for one git call, lost the directory, restamped the file over whoever took it and went on writing to a database two processes now believe is theirs). Three of them are not pure functions, and each earns the exception on its own terms. `settleOnExit` spawns a real child, which is what the fault requires: an inherited pipe held open past the exit is the entire mechanism, and a stubbed emitter would only pin the wiring back to whatever it was written against. `sendChatMessage`'s claim on a chat is the second, driven against a temporary database with `spawn` replaced by a counter — what it decides is not a value but whether a second billed child joins a conversation that already has one, and the only assertion that says so is the number of children. `jsonRequest` is the third, and it is the one that makes the request: what it pins is that it *returns*, whatever happens, because an unguarded `fetch` rejecting out of a handler reports nothing at all — the chat page's flag disabling the composer, Approve, Reject and Select-all stayed set with no way back but a reload; the branches page's Land, Purge and Delete re-enabled their button and left the table exactly as it was, which is what a press that did nothing also looks like; and the land card's poll went on rendering a conflict resolution as in flight long after it had finished. The status it carries is the other half — `null` is nobody answered and a number is somebody refused, which is the split between `pollFailureMessage` on a poll and `actionFailureMessage` beside a press that may or may not have landed. `chatRequest` is a caller of it and keeps its own test, because the chat page reads a thread off the answer and that shape is its own. Three are renderings rather than functions — `Meter.test.tsx`, `LiveTelemetry.test.tsx` and `Markdown.test.tsx` — and they clear the same bar by the same argument: what they pin is *something the reader would act on*, wrong in a way that throws nothing and typechecks (a solid green bar that means "we don't know"; a first-party figure that reads as an addend to the transcript-derived meter beside it; a report that ends in silence because the cycle was killed with a code fence still open). Twenty-one are neither a function nor a rendering, and each earns it its own way. `src/app/api/chat/[id]/route.test.ts`, `chatOrder.test.ts`, `chatTurn.test.ts`, `haltedMembers.test.ts`, `mergeQueueOrder.test.ts`, `mergeQueueView.test.ts`, `bootBlocks.test.ts`, `assistBudget.test.ts`, `cycleDeadline.test.ts`, `slotProbes.test.ts`, `snapshotCoalesce.test.ts`, `fleet.test.ts`, `src/app/api/agents/route.test.ts`, `src/app/api/health/route.test.ts`, `src/app/api/status/route.test.ts`, `runOrigin.test.ts`, `requestLog.test.ts`, `dataDirClaim.test.ts` and `shutdown.test.ts` are the nineteen that open the database, and what they pin is different in kind. The first names a throwaway `DATA_DIR` and calls the handler, because what it pins is a *payload key*: the chat page polls that one route, so a list left out of its answer is frozen on screen until a reload, which is exactly what it did for as long as a comment claimed otherwise. The second is in the SQL itself: a thread ordered by a random UUID puts a denial note above the reply it is a footnote to, which reverses what the operator is being told. The third drives `sendChatMessage` through a failed pre-spawn setup, because what it pins is a *state transition* rather than a return value (a chat thread stranded at `thinking` for ever by one failed `writeFileSync`, unusable until the server restarts). The fourth halts a real instance through `stopInstance` and then asks `reopenRun` and `reviveBlockedDependents` about its members, and drives the same pick-up against a graph's deferred nodes to pin `reviveBlockedBlocks` — the two halves of one question, because what it pins is a *join*: a halted member is an ordinary `blocked` row with a null `work_dir`, indistinguishable from the one the revive exists to rescue except by `workflow_instance_runs`, so every way of getting this wrong typechecks, throws nothing and reads identically on the page — the only evidence is a billed agent working under a workflow the page says is stopped. Its three control cases are half the test, and the half more easily broken: a chain outside any workflow, and one inside an instance still `started`, must still wake exactly as before. The fifth is in the SQL as well, `chatOrder.test.ts`'s grounds one table over: `nextQueuedIn`'s ORDER BY is the whole of what decides which branch is merged next, and reading the per-batch `position` first sorted a batch queued while the worker was still draining an earlier one into the middle of it. It also pins the repository term beside it — that a branch in one repository stays eligible while another repository's is in flight, and that within one repository nothing does — because those are one question and the way to get the first is to drop the second. Nothing crashes — every item is still re-previewed against git at its own turn — so all that is lost is the operator's sequence, in merge commits in a directory they own, with nothing afterwards to say that was not the order they chose. It drives the selector the way the worker does, settling each row and asking again, because a comparator beside the query would be a second copy of the rule and the copy is the one that would stay right. The sixth is that same table once more, and its decision is in the SQL too: `selectQueueBatches` is the rule and is tested pure, but the query that fed it never consulted a rule at all — it took the newest `batch_id` — so what `mergeQueueView.test.ts` pins is that the answer the page is handed covers every batch the worker can still act on, and that Cancel reaches one that is not the newest. The seventh drives a whole boot — `reconcileOnBoot` then `reconcileBlocksOnBoot`, in `src/instrumentation.ts`'s order — because what it pins is neither a value nor a row but an *ordering between two reconcilers*: `bootBlockPlan` beside it decides which instances are spared, and this is what says the survivors it is handed are the ones the run reconciler had already decided to keep. Its own controls are again half of it, and one of them is the halt bound: a stale pause, a run the boot failed, and an instance already `stopping` must all still lose their blocks. The eighth is a *count over three tables*, which is what `assistBudgetRefusal` beside it cannot be tested on: the rule is pure and the defect was never in the rule — it was that the cap read one kind of child and three others consulted nothing, so a `run_reviews` row, a `chat_sessions` row and a `workflow_instance_blocks` row are written and the count asked about each. Its two negative cases carry the same weight as its positives and one of them is not obvious: a **merge** block takes the identical `thinking` status from the identical `claimBlock` and spawns no child at all, so counting it refuses an operator's chat turn to make room for a process that does not exist. Both directions were seen to fail before this landed. The ninth is `settleOnExit`'s argument in its strongest form: what `cycleDeadline.test.ts` pins is that `runIteration` *returns at all* against a child that prints nothing and does not exit, so the subject has to be a real process — a stubbed emitter would pin the wiring rather than the fault, and the fault is the child. It is the one file in the suite that points `CLAUDE_BIN` at a binary that exists (`process.execPath`, running an inline script, so it can reach nothing and spend nothing), which is exactly why it cannot be a case in `orchestrator.test.ts`, whose own harness pins that variable at a path that does not exist so a regression reaching a spawn is a failed test rather than a billed one. Its control is half of it and is what says the clock is *silence*: a child printing every 100ms must survive a one-second deadline, which a wall-clock deadline would fail while passing every assertion in the case beside it. The bound is the test's own `timeout`, because without one the only failure available is a test that never returns, and that is not a failure anything reports. The tenth is a count as well, and of a third thing again — not rows in tables and not children, but *subprocesses*: `slotProbes.test.ts` wraps `spawnSync` module-wide and asks what one `createRun` spends on choosing a checkout slot, against two real repositories that differ only in how many of their slots were left dirty. `createRun` runs from entry to INSERT with no `await`, which is what makes its folder claim atomic and also what makes every subprocess it spawns a hold on the one event loop that drains every agent's stdout, feeds every SSE stream and beats the server lock's heartbeat — and nothing bounded that walk: dirty slots are left behind deliberately, they are never `taken`, so every admission re-ran `git status --porcelain` over every one of them, for ever. Nothing about that is visible from a value, a status or a page; the app stays correct and stops answering, for longer the older the repository is, so the only assertion that says so is the number of subprocesses. Its own file for three reasons at once — it needs a real git repository inside the mount, where `orchestrator.test.ts`'s mounts are fixed at a layout that file's collision cases depend on; a wrapped `spawnSync`, which would otherwise count every other case beside it; and a cold slot memo, since the whole question is what a *first* admission on a repository costs. Its two controls are half of it: the run must still come back isolated, because a walk that bounded itself by giving up would pass the count and quietly serialise every run on the repository, and a store whose settled slots have all been seen once must cost no git at all. The eleventh is a count as well, one function over: `snapshotCoalesce.test.ts` wraps `buildSnapshot` module-wide and asks how many times it runs for 25 callers that arrive together. It is a count and never a wall clock because the defect is invisible from any value the app produces — all 25 of those aggregations return the same answer — so a timing assertion would be the only other way to see it, and a timing assertion in CI is a flake. Its own file for one reason: the question is what a *cold* process does with N simultaneous callers, and any case in the same process that reached `currentSnapshot()` first would already have answered it. Its two other cases are the halves a cache would put at risk — a caller arriving after the aggregation settled must read the transcripts again rather than be served the reading already given out, and a failed aggregation must not stay in the slot, since a latched rejection would refuse every budget evaluation for the life of the process off one transient failure. The twelfth is `fleet.test.ts`, and it is two subjects that are one file because both are about *whether anything is running*. The stop half pins an ordering, `bootBlocks.test.ts`'s kind of fact: a dependent still `waiting` when the run it waits on is stopped is released, promoted and spawned — a run starting *because* the fleet was stopped — so the waiting rows are blocked first, and the only evidence otherwise is a billed agent under a page saying everything stopped. It pins the third halt cause beside it, since `fleet` versus `operator` on the instance row is the only thing that afterwards tells a workflow somebody stopped from one that went down with everything else. The hold half is a case per call site, and that shape is the point: four separate places start work and a fix that misses one is silent, so each case drives the real entry point — `promoteQueued`, `releaseDependents`, `emitBlockRuns`, `tickSchedules` — and proves the *difference* by running the same call with the hold clear. Two of them need that second run to be legible rather than merely different: the emission is refused for a malformed payload once the hold is gone, and the schedule tick is refused by `scheduleRefusal` instead, which is what separates a tick that never looked from one that did. `tickSchedules` is exported for that case and for nothing else. The thirteenth is the first one's argument at another door: `/agents` is a form now, and `normalizeAgentInput` spends a paragraph on each of its refusals precisely because they are *shown* — so what that test pins is the payload those sentences travel in (`error` on a 400, `agent` on the way back), since a route that answered `{ message: … }` instead would leave the page saying "Could not save the agent" with the reason thrown away, and nothing about that throws or typechecks differently. The duplicate-name refusal is the half that cannot be reached any other way: `withNameConflict` turns the unique index into that sentence, so it is only a sentence at all once there is a database with a row already in it. `src/app/api/health/route.test.ts` is the fourteenth and drives that route in both directions against a throwaway database: the unhealthy one is the case worth having, because a probe that always answers 200 is indistinguishable from a working one right up to the day the database goes read-only — which is exactly when Docker is reporting the container as fine. It also asserts what the payload does *not* carry, because the middleware exemption above is justified by that and by nothing else. `src/app/api/status/route.test.ts` is the fifteenth and pins the same thing one route over, for a reader that is not a person: that the counts match the rows it seeded (a monitor thresholding a queue depth that never moves is bit-for-bit a queue that never backs up), that a prompt, a folder path and both tokens are absent from a payload something else will retain and forward, and that the read-only credential is checked here — since `middleware.ts` exempts that path only while `UF_STATUS_TOKEN` is set, the two have to be asserted together exactly as `/api/mcp`'s are. It names `WORKSPACE_ROOTS` as well as the other three, because the report walks the checkout store for a byte count and any container this ships in has that variable set. `runOrigin.test.ts` is the sixteenth and drives all five creation paths *through the gates* rather than asserting about them — a `createRun({origin: "chat"})` written in a test would pin the test's own argument and nothing about `approveProposal` — plus the pick-up that must not rewrite what it finds. Every way of being wrong here typechecks, throws nothing and produces a run that works: the only symptom is a row claiming a person filled in a form when a model decided it, read months later by somebody scoping what a stolen token did. `settleBlock` is exported for `sweepPaused`'s reason and no other, being the only door to `createEmitted` whose other end is a real child exiting. `requestLog.test.ts` is the seventeenth and its second case is the one it exists for: the wrapper is handed a body holding a token, a query string holding the same token and a session cookie, and the row must contain none of them — adding a field is the dangerous direction here, and a leak would typecheck, pass everything else and be found by whoever reads the logs. `dataDirClaim.test.ts` is the eighteenth and it opens the database in order to be *refused* by it twice, in the two ways ownership ends: with the lock held by a live pid that is not ours, `createRun` has to throw, leave no row and spawn no child. What it pins is the wiring rather than a value — `lockVerdict` was always right and nothing asked it, so a second replica served traffic, admitted runs and spawned billed agents having correctly reported that it owned nothing, and the collision that follows is silent in every table. Its control is half of it, for `haltedMembers.test.ts`'s reason: the same call, with the lock removed and the directory claimed, must still come back with a run, or a refusal that fired for every caller would pass this test and break the app. Its second case is the other ending — the directory taken while this server is up — and it drives the real `heartbeat`, because the fault is that the beat *wrote* rather than that it decided wrongly: the assertions are that the stranger's `ownerId` is still in the file afterwards and that the writer gates have flipped, neither of which any pure function can be asked about. `shutdown.test.ts` is the nineteenth and the only one here whose subject is a *promise the process makes on the way out*: it drives a real run to `running` against a child that stays alive until it is signalled, calls the real `shutdownRuns`, and reads the row. Nothing short of that says what it needs to say — `reconcileKilledCycle` was always correct and was reachable from exactly one place, inside `startRun`'s loop, which a `process.exit(0)` two lines after `killAllAgents` meant no suspended frame ever reached. So a test that the function exists would have passed against the defect; what is pinned is that the handler *awaits* it, that the columns claiming an open cycle are cleared, and that the second work cycle the run's budget still allowed is not spawned on the way out. Its second case is the mop-up for a loop that did not finish inside the grace, including that a second pass charges nothing twice, and its third is `reconcileOnBoot` clearing those columns for the endings no handler reaches at all. All nineteen point `DATA_DIR` at a temp directory before the module graph loads — `chatTurn.test.ts`, `haltedMembers.test.ts`, `mergeQueueOrder.test.ts`, `bootBlocks.test.ts`, `assistBudget.test.ts`, `cycleDeadline.test.ts`, `slotProbes.test.ts`, `snapshotCoalesce.test.ts`, `fleet.test.ts`, `dataDirClaim.test.ts`, `shutdown.test.ts` and the agents route `CLAUDE_HOME` as well, the last of those `CLAUDE_CONFIG_DIR` too (it only *falls back* to `CLAUDE_HOME`, so an environment that sets it sends the ambient walk into the machine's own `~/.claude` and answers differently per machine), and all twelve refuse to run if `config.ts` was already loaded, the same guard `chat.test.ts` needs for the turn claim, which is why all twenty set that environment before requiring anything. Each is its own file rather than a case in the pure suite beside it because `node --test` gives each file its own process and the harnesses want opposite things: `chat.test.ts` replaces `spawn` module-wide so it can count children and `mergeQueue.test.ts` must never bind `DATA_DIR` to the repository's own `.data`, where these nineteen need the real database, the real `writeFileSync` failure, a real git repository and, for two of them, a real child that outlives the call. `bootBlocks.test.ts` is not a case in `haltedMembers.test.ts` for a further reason of its own — both reconcilers it calls act on *every* row in the database, so they would close that file's fixtures out from under it. `fleet.test.ts` is separate for that same reason turned up one further: `stopFleet` acts on every live row *and* every started instance, so it would take down any other file's fixtures mid-test. `deployment.test.ts` pins `Dockerfile` and `docker-compose.yml` against each other, that the directory compose sets `DATA_DIR` to is `chmod`ed 0700 in the image and reclaimed by the entrypoint on every boot, because `/data` is a *named volume*: Docker copies that directory's mode onto a fresh volume's root and never revisits it, so the mode is the whole of what keeps the database, the settings every guard reads and the server lock away from the children — and an *existing* volume, which is what every deployment with data in it has, keeps the old `node:node 0777` through any number of image pulls. That file asserted the opposite until the uid split landed and it was deliberately inverted: the old rule was sound on its own premise, that one uid ran the server and the agents and a fresh volume had to be writable by whatever `${UF_UID}` was. And, since the two files now express a uid boundary rather than one uid, that compose runs the server as root while handing the operator's own uid to the children through `UF_AGENT_UID`/`UF_AGENT_GID`, and that no `USER` line in the runner stage takes back the privilege the drop needs. Dropping either half is silent in its own direction: no root and the server cannot switch uids at all, no agent uid and every child runs as root, which is worse than the shared arrangement the split replaced. It clears the bar for the same reason — nothing else here notices. It typechecks, it builds, and it passes on macOS, where Docker Desktop's bind-mount remapping makes 1000 right whatever the host uid is. It pins a second agreement of the same kind, the `HEALTHCHECK` against the route it probes: a directive pointed at a path that has gone reports every container unhealthy for ever, and one pointed at `/` reports a server that cannot open its database as *healthy*, because under `UF_AUTH_TOKEN` that path is a 307 to `/login` and `curl -f` accepts a redirect. It carries a third group of the same kind, about the one thing in this deployment with no second copy: that the image ships `scripts/backup-db.mjs` and `scripts/restore-db.mjs`, that `sqlite3` is in the runtime apt list — tokenised rather than matched as a substring, because `better-sqlite3` in the comments beside it satisfies any looser test — and that the backup destination compose mounts is *not* inside `DATA_DIR`, since a snapshot kept in the named volume dies with the one command it exists to survive. It carries a fourth of the same kind, this one wholly inside compose: that `NODE_OPTIONS`' heap ceiling leaves room inside `mem_limit` for the children the container exists to supervise, and that `memswap_limit` matches `mem_limit` so the stated ceiling is the ceiling — Docker defaults the swap limit to *twice* the memory one, and a server permitted to fill the cgroup by itself never throws V8's own heap error, it gets the container OOM-killed and restarted with every run in flight failed. `backupRestore.test.ts` is the twenty-first, and it is the behaviour that pinning cannot reach: it drives those two scripts as an operator does, against a real migrated database with a second connection holding a write transaction open, and compares the restored file against the quiesced source object for object and row for row. Its grounds are that every other check passes on a bad backup — a `cp` of a WAL database opens cleanly, reports `integrity_check ok`, and is silently missing every transaction since the last checkpoint (measured: 25 runs against the snapshot's 386, both files `ok`), and nobody looks at a backup until the volume is already gone. The refusals beside it are the ones that turn a restore into a second incident: restoring under a live server (which corrupts rather than replaces, and is decided by watching `server.lock` for a beat, because a restore runs in another container where a pid means nothing), deleting the database being replaced or leaving its `-wal` behind for SQLite to replay into the new file, restoring some other SQLite file, and a prune that reaches a file this script did not write. That is the bar for adding another, not a general testing convention to follow. `npm run typecheck` plus a `docker compose up --build` smoke test is still the real verification loop, and the README's "Verified" section records what was checked by hand — including a "Not yet verified" list, which must stay honest.
