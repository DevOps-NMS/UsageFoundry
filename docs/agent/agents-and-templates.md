# Saved agents and run templates

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/agents.ts, agentRegistry.ts, templates.ts.**

**A template is form input, and the two settings that decide what an agent may do are applied but announced.** `run_templates` holds a task, guards, and optionally a target; it takes no folder claim, consumes no concurrency slot, and nothing derived from `activeRuns()` can see it. `permissionMode` is narrowed three times — on save, on read, and again by `POST /api/runs` — because a template is the *second* route to `--permission-mode`, the flag `reopenRun` deliberately refuses to become a third route to. Only the last narrowing guards anything; the first puts the mistake where it was made, and the second (unknown → `plan`, the only mode that cannot write) is what stops a row from a build this one does not understand from ever *widening* what it permits. Never invert that fallback. `enforcement` is the other one: there is no `settings.defaultEnforcement` precisely so that no single edit turns every run into a cycle-killing run, and a template that quietly carried `live` would reintroduce exactly that — so a carried non-default mode, and a carried `bypassPermissions`, each raise a banner above the form with a one-click way back to the safe value, and the banner clears the moment the control is touched. `normalizeTemplateInput` also refuses the `no_terminus` pair at the door rather than leaving it to `POST /api/runs`: a template that can be saved but never instantiated fails weeks away from the form that caused it. `folder` is nullable and `""` is *not* the null — the empty string is the mount root, the one selection that blocks every other run in the tree. The template holds no model: `settings.defaultModel` is the single place for that. It *does* hold an `agent_id`, which is not a second place for one and not a fourth route to `--permission-mode` — an agent carries a role and no capability, and the model on it is only ever reached where the run itself named none, an explicit `--model` outranking it on the pin. See the agent invariant above for why that one is a reference where `runs.agent` is a copy.

**A saved agent is the fourth thing here that is form input, and it carries a role rather than a capability.** `agents` holds a name, a description — what a *person* reads on a picker when they choose it — a prompt, and optionally a model; it takes no folder claim, consumes no concurrency slot, nothing derived from `activeRuns()` can see it, and deleting one cannot reach a child that has already been spawned, because every spawn writes the whole definition onto its own argv rather than a reference to the row. **It reaches a child as two flags, and the pair is the whole feature.** `sessionAgentArgs` emits `--agents <json>` through `agentsFlagValue` *and* `--agent <name>` beside it, so the definition travels and the session is then started as it — the saved prompt is the run's own, not a role inside it. This app was built the other way round, on the plural flag alone, and that reading is recorded here rather than deleted because the next person to read this file will otherwise re-open the question. `--agents` on its own *offers* a definition to the session's main agent as a specialist it may hand a subtask to; the `description` was then what the delegating model read when it chose, and this paragraph said in as many words that the singular flag was a different feature answering a different question. It is — and the question this app is for turned out to be the singular one, which is why every place the plural reasoning was embedded was re-decided rather than patched around. The pair is not redundant, and that is measured rather than assumed: `--agent` resolves a name against the built-ins, whatever is on disk, and whatever this argv defined, so sending only the name would select an agent this app never wrote down anywhere the CLI can see. On the pin (`@anthropic-ai/claude-code@2.1.226`), `claude --agents '{"uf-probe-agent":{…}}' --agent uf-probe-typo -p hi` refused with `Available agents: claude, Explore, general-purpose, Plan, statusline-setup, typescript, uf-probe-agent` — the built-ins, an ambient definition on that machine, and the member supplied on the same argv, in one set. `spawnAssist` is the one caller left on the plural flag alone, for the reason the child-process paragraph above gives. **A `tools` field is refused at save, and the refusal is the decision.** `--agents` members accept one and this app will not store one, because capability in this app comes from a guard set a person wrote — the permission mode, `ISOLATED_GIT_TOOLS`, `PROCESS_KILLERS` — reached through exactly two routes and re-narrowed at every one; an agent record is a third kind of thing that would carry it, and the surfaces that pick one put it within reach of a model, where `planProposal`'s rule is that prompt text is the one half of a run a model may write and capability is the other. **The singular flag strengthens that refusal rather than weakening it**, and the opposite reading is available enough to be worth closing off: under `--agents` alone a `tools` list would have bounded one delegated subtask inside a run whose own mode and lists still stood over it, which is at least arguably contained. Selected with `--agent` the run *is* this agent, so a list on it would be a statement about what the whole session may do — precisely the third route to that decision the two-routes-to-`--permission-mode` rule exists to prevent, arriving through a record a chat proposal or a workflow block can name. There is no reading of the new semantics under which the field becomes safer to store. There is also a concrete hazard behind it: `PROCESS_KILLERS` is a `--disallowedTools` entry and deny is *verified* to beat `--permission-mode`, but whether it also beats a member's own `tools: ["Bash"]` — offered as a delegate or selected as the session — is **not** verified, and the incident behind that list is one `pkill` that restarted the container and failed fourteen runs. Refused by name rather than dropped, for `normalizeTemplateInput`'s reason: an operator who typed a tool list and got a saved agent that ignored it would believe their agent was narrowed when it was not. **A model is the one field `run_templates` refuses that this holds, and it is the one field whose *meaning* the singular flag changed.** Under `--agents` alone it was the model a delegated sub-turn ran on — a thing nothing else here can express, and the whole reason this file departs from `run_templates`' "`settings.defaultModel` is the single place" rule at all. Selected with `--agent` it is the **session's** model, which is exactly the second place to set the run's model that a template's would have been. What keeps it from becoming that is measured off the `system`/`init` event, before any request is made: an explicit `--model` outranks it, and `buildArgs` passes one whenever the run has one. `--agents '{"uf-m":{…,"model":"sonnet"}}'` alone reported `claude-opus-5[1m]`; adding `--agent uf-m` reported `claude-sonnet-5`; `--model opus … --agent uf-m` reported `claude-opus-5`. So the agent's model fills a gap the run left rather than overriding a choice the operator made — a run with no model of its own, started as an agent that names one, runs on the agent's — and it still moves cost and not capability, since the run's spend lands on its own `result` event and in its telemetry whatever model produced it. It is free-form for `settings.defaultModel`'s reason: a list this build knows would refuse whatever ships next week. **The registry is written from `/agents` and nowhere else.** `GET /api/agents` is read by five surfaces — the run form, Settings, the workflow canvas, the chat's mention popover and that page — and for as long as the page did not exist, `POST`/`PUT`/`DELETE` were reachable by hand and by nothing else, so every picker in this app was empty on every install and the run form's Agent row, gated on `agents.length > 0`, never appeared at all. What that page may hold is the same absence this paragraph is about: a name, a description, a prompt and a model, and no control for a tool list, a permission mode, a budget, a folder or an isolation choice — `agentPayload` is a named projection rather than a spread so that adding one is a decision somebody makes in front of the test that counts the keys, and the singular flag is what makes that absence load-bearing rather than tidy, since a field on this form is now a statement about what a whole run may do. It decides nothing else: `normalizeAgentInput` lives beside a database and a filesystem so a client cannot import it, and the refusals below are written to be *shown*, so the draft goes to the server and the page renders the sentence that comes back — `/api/workflows/validate`'s rule and its reason. The ambient collision the next paragraph leaves unresolved is annotated there rather than refused (`ambientClash`, case-folded as `idx_agents_name` is), and the same page lists the ambient set beside the registry, which is the "a surface that lists both" that sentence asks for.

**The CLI will not register a malformed agent, so this app refuses one at the door — and the singular flag changed how loudly that fails, not whether it does.** Measured against the pin (`@anthropic-ai/claude-code@2.1.226`), not read from the docs: a `--agents` member with no `description` is dropped, one with no `prompt` is dropped, one whose `model` is JSON `null` is dropped, an empty name registers as an empty entry, and a `--agents` value that is not JSON at all is ignored outright — exit 0 in every case, nothing on stderr, no line in the stream. That silence was the whole argument for validating here, and it is worth being exact about what "dropped" now means. It is dropped from the set `--agent` resolves against, which was invisible while the member was only being offered and is a hard start failure when it is being selected. Re-measured on the pin for the first three: `claude --agents '{"uf-nodesc":{"prompt":"p"}}' --agent uf-nodesc -p hi` answered `--agent 'uf-nodesc' not found. Available agents: claude, Explore, general-purpose, Plan, statusline-setup, typescript` and exited **1**, before any API call, and identically for a missing `prompt` and for `"model": null`. The other two — the empty name and the non-JSON payload — have **not** been re-measured under the singular flag and are still on the *Not yet verified* list by name. So the class of fault now has two shapes rather than one, and both are worth refusing where the person is: a run that was given a specialist and does not have it (the old one, still exactly what `spawnAssist`'s offered member would produce, and bit-for-bit a run that was never given one — nothing downstream can tell them apart, not the event log, not the cost, not the transcript's own `attributionAgent`, which simply never names it), and a run whose every work cycle dies at the spawn with a message only the CLI's stderr carries. Louder is better, and it is still not a substitute for refusing at the form. The five are answered in three places rather than one, because they are not one kind of fault. `normalizeAgentInput` refuses the three a person can type — a missing description, a missing prompt, an empty name — where they were typed; the description stays required on a *stronger* ground than the one it lost, since nothing chooses on it any more but the CLI will not register a member without one. `rowToAgent` reports a row that has *decayed* into one as `usable: false` rather than repairing it with a placeholder, and every door reads that flag. And the last two are the encoder's, because they are shapes rather than values: `agentsFlagValue` **omits** `model` instead of nulling it — the only spelling of "inherit" that survives — and it is the one thing that writes the JSON, so there is no second place for a payload to stop being JSON. It is that one encoder for every caller that can carry the flag (`buildArgs` and `runOrchestratorChild` through `sessionAgentArgs`, `spawnAssist` through `agentsArgs`) precisely because a second copy of a shape whose violations are unreported would drift with nothing reporting it. A name that collides with one the CLI already answers to (`claude`, `Explore`, `general-purpose`, `Plan`, `statusline-setup`) is refused too, and the reason **narrows** rather than disappearing: `claude --agents '{"Explore":{…}}' --agent uf-typo -p hi` still lists one `Explore` and not two, so `--agent Explore` selects *an* Explore with no way to tell from outside whether it is the operator's prompt or the built-in — which is now the difference between a run that is the agent the operator wrote and a run that is something else entirely, under a name they chose. That list can go stale when the pin moves, in the direction that costs a shadow rather than a crash; note also that `typescript` appears in the CLI's own "Available agents" line on the probe machine and is *not* on it, being an ambient definition — which is what that line looks like when a name comes off disk rather than out of the binary.

**The agents this app did not write are left in play and declared, never silently mixed.** `docker-compose.yml` bind-mounts the operator's `~/.claude`, so `$CLAUDE_CONFIG_DIR/agents/**` already reaches every child this app spawns — runs, chat turns, orchestrator blocks and reviews — and an isolated run's worktree carries the repository's own `.claude/agents/` for the same reason. `--agents` **merges** with that set rather than replacing it, verified — and `--agent` resolves its name against the merged set, which the pin's own refusal line shows directly: the `Available agents` it printed beside a typo carried the built-ins, `typescript` off that machine's disk, and the member supplied on the argv, all together. So starting a run *as* a saved agent withdraws nothing; the ambient definitions are still in play inside it, and are still the thing a picker cannot name. Excluding them is what `--strict-mcp-config` does one door over, and it was rejected on the mechanism rather than the principle: agent discovery is governed by `--setting-sources`, where `user` keeps the user scope, `project` keeps the repository's, and only the empty value drops both — and that flag governs settings *whole*, so passing it to exclude agents would silently drop the operator's own `settings.json`, hooks, permissions and environment from every child. There is no agent-scoped exclusion in 2.1.226, and a change that large made in passing for a feature nobody has switched on yet is worse than the thing it fixes. The second reason is that these are not new: a repository's `.claude/agents/` is part of the repository the agent was pointed at, and withholding it would make a run behave differently from the same checkout opened in a terminal. So the registry is a *part* of the set and the app has to say so wherever an agent is chosen. `listAmbientAgents` is what that sentence is built from, `GET /api/agents` returns it as `ambient` beside `agents` so no two surfaces can say it differently, and `parseAgentFile` reads a definition the way the CLI does — the name off the frontmatter `name:` key and never off the filename, a file with no `name:` key not registered at all, subdirectories walked. Only the **user** scope is on that payload, being the half that holds whatever a child's cwd turns out to be; `listAmbientAgents` takes a directory for a caller that has already resolved one, and resolving an arbitrary one on the wire would be a containment surface this does not need. A saved agent whose name collides with an ambient one is *not* refused — the ambient set is per-cwd and a pure validator cannot see it — so which definition wins is unverified and a surface that lists both is what makes the collision visible.

**The mounted `settings.json` can name a session agent too, and that one is measured and *not* declared.** `--agent`'s own help says it overrides "the `agent` setting", and on the pin that setting exists: an `agent` key in `$CLAUDE_CONFIG_DIR/settings.json` starts the session as that agent with no flag at all, which is the same class of fact as the ambient definitions — the registry is not the whole set — arriving through the same bind mount and reaching every child this app spawns. Four probes against 2.1.226, a definition whose entire prompt was "reply with exactly BANANA": the key set answered `BANANA` where the key absent answered an ordinary greeting; `--agent` naming a second definition answered that second one, so the flag wins as documented; `--agents` **alone** answered `BANANA`, so the plural flag does not override it; and a key naming an agent that does not exist answered an ordinary greeting at exit 0, where the same name on `--agent` exits 1 before any API call — silently ignored where the flag is loud, which is the opposite direction from every refusal `agents.ts` makes. What follows bounds how much this matters: every door that names an agent emits `--agent` and therefore outranks the key, so a run, block or turn started *as* something is unaffected. What the key reaches is everything this app starts as **nobody** — an agentless run, every chat turn (`runTurn` withholds one deliberately, and this is the one door that can put a saved prompt under `systemPrompt()`'s boundary without asking), every orchestrator block whose node names none, and every review (`spawnAssist` is on the plural flag, which the third probe shows does not override it). It is **not declared**, and that is a decision with a stated cost rather than an oversight: `describeAmbientAgents` is one sentence four pickers share, so carrying this would be a new read of `settings.json`, a new field on `GET /api/agents`, a second argument threaded through that sentence and its four call sites — and the sentence would be *false* on the surface carrying it, since picking an agent there is precisely what overrides the key, while the two children where it bites hardest (a chat turn, a review) have no picker at all. Recorded in `docs/verification.md` and in the README rather than built.

**A run records the agent it was started as; a template records the one it names; and the difference between a copy and a reference is the whole of it.** `runs.agent` holds the entire definition as JSON, the treatment `runs.budget` already gives `permissionMode` and the reason deleting a template cannot reach a run started from one. An id there would be wrong twice, and the singular flag makes it wrong harder: a run spawns a child per work cycle, so an agent deleted between cycle 3 and cycle 4 would leave cycle 4 selecting a name nothing on its argv defines, which the CLI refuses at the spawn — a run that silently stopped being what it was started as, part-way through, and then stopped running at all — and a run picked up by hand days later would lose it the same way. `startRun` therefore reads `parseRunAgent(run.agent)` and never the registry. `run_templates.agent_id` is a reference for the opposite reason: a template is applied again and again, so an operator who fixes their reviewer's prompt expects the next run from it to use the fixed one. **What that reference reaches is the new-run form and nothing else** — it is a seed for a field, the treatment the template's mount and folder already get, and it is *not* inherited by the two paths that read a template on the server. `planProposal` takes the agent off the proposal and `planNode` takes it off the node, both deliberately (the workflow invariant below argues that one out), so a template supplies a proposal its prompt and its guards and never its agent. Which is the honest reading of "carries onto the run exactly as the guards do": true where a person applied the template to a form, and false everywhere a model named the template instead. **A deleted agent is refused by name at every door and never falls back to none**, which is `planProposal`'s rule for a deleted template and the same reasoning — the operator started the run that said "as the reviewer". `agentRefusal` is that one wording for every door handed an **id**, pure and unit-tested: `POST /api/runs` through `resolveAgentForRun` (which takes an id off the wire and never a definition, since a definition would be a route to an agent nobody saved), `normalizeTemplateInput` through the `TemplateKnowledge` it is handed — `normalizeWorkflowInput`'s argument-rather-than-read shape, for that function's reason, and the `no_terminus` rule applied to a second field so a template cannot be saveable and never startable — `PUT /api/settings` for the form default, `propose_run` and `approveProposal` for a chat proposal, `normalizeWorkflowInput` at save and at `/api/workflows/validate`, `planNode` at both moments a block becomes a run, and `startBlockTurn` for a deciding turn's own. The two doors that were shown a **name** rather than an id — `planEmission` for a spec and `createEmitted` when that spec becomes a run — refuse in their own words for that reason and no other; the answer is the same refusal, and the sentence has to name what the turn typed. An agent that exists but has decayed into something the CLI would drop is refused the same way and *named*, because `rowToAgent` reports rather than repairs. `reopenRun` carries the column forward by not touching it: there is no argument on the function and no field on the reopen route that could reach it, which is `permissionMode`'s rule one field over and also what lets a run whose agent has since been deleted still be picked up as the agent it ran as. **What the surfaces say is bounded by what the flag does, and that placement was re-decided under the singular flag rather than carried over.** The obvious reading is that a run which *is* its agent has had its agent promoted into the guard group, and it is wrong: `--agent` sets the session's system prompt and, where the run named no model, its model — the permission mode, `ISOLATED_GIT_TOOLS`, `PROCESS_KILLERS` and `--append-system-prompt` are argued at the spawn sites and are untouched by it, which `orchestrator.test.ts` asserts again with an agent selected. A row inside the guard group would claim it bounds something, and it bounds strictly nothing; it is a bigger fact than it was and still not that kind of fact. So the run page keeps it beside the guards and never among them, and the form's picker declares the ambient set beside itself, because the registry is a part of the set and not the whole of it.
