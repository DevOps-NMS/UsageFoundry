# Retention: what is evidence and what is permanent

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/retention.ts.**

**Three stores, one retention decision, and the decision is what a run's row is for.** `run_events` in the named volume, `.uf-worktrees` on the workspace bind mount, `~/.claude/projects` in the operator's own home — three media, three growth rates, and for a long time not one `DELETE` between them. They were filed as three findings because each sweep found the store in front of it, and they are **one** design because they share one question: what is safe to discard, and what does this app promise about history it has already shown somebody. The answer is a single sentence. **A run's row is permanent; everything behind it is evidence, and evidence has a horizon.** Nothing in `retention.ts` deletes a `runs` row, a `run_reviews` row, a `workflow_instance_*` row or a settings key, so every figure this app has ever put on the dashboard, the runs list or a run's own state card keeps reading true for ever — the spend columns, the cycle count, the stop reason, the branch, the landing record. What each sweep removes is the *working material* those figures were derived from: the event log's payloads, the checkout on disk, the session transcript. Each is bounded by its own horizon in Settings (`eventRetentionDays` 30, `checkoutRetentionDays` 7, `transcriptRetentionDays` 30; `null` on any of them means keep for ever, the reading every switchable rule here takes), and each horizon is separate because the media are — a checkout is hundreds of megabytes and is rebuilt by `worktree add` in seconds, where a transcript is the only thing `--resume` can continue.

Four properties are shared by all three sweeps and none of them is optional. **Nothing in flight is touched**: a non-terminal run keeps its whole event log, a checkout an active run holds is skipped by name, and a transcript whose session id belongs to a live run or to any chat is never a candidate — which is why each sweep asks the *database* what is live rather than inferring it from a file's age. **The decision is pure and the syscall is not**: `reclaimableCheckouts` and `expiredTranscripts` are the two functions that decide what goes, and both are unit-tested against fixtures, for `releasableRuns`' reason — every way of being wrong here is silent, lands on somebody's disk, and throws nothing. **A removal is recorded where the operator would look for it**: a reclaimed checkout emits a `land` event on its own run, and every sweep's counts are stored under `retention.lastSweep` and shown on the Settings page beside the sizes. And **a sweep never destroys the only copy of anything**: it removes no branch and no commit (`worktree remove` without `--force`, so git gets a second veto), it never touches the operator's own checkout, and a transcript it removes is one whose spend is already recorded in `runs.spent_usd` and in the `run_events` row that reported it.

Two consequences are written down rather than absorbed. **A pruned transcript takes its session with it**, so the sweep clears `runs.session_id` on the terminal runs it belonged to: `--resume` against a file that is gone fails the first cycle of a pick-up outright, where a null session id is already the documented restart — `nextPrompt` writes the task with `priorWorkNotice` naming the branch. Clearing is what turns a silent failure into the path this app already has. **And it shortens the dashboard's own history**, which is the one place the promise above is genuinely at risk: `buildPeriods` offers twelve months and a 30-day horizon empties eleven of them. Making the horizon a year would defeat the retention, so the card says so instead — `PeriodSeries.completeFrom` carries the cutoff, `/api/usage` fills it from the same setting the sweep reads, and any bucket that starts before it is marked as covering transcripts that have since been pruned. `buildPeriods` already drops buckets that closed before the first entry, so the effect is a *shorter* history rather than a wrong one; the sentence exists for the one bucket the cutoff falls inside. Nothing here reaches `evaluateBudget`: a guard reads the 5-hour and weekly windows, both far inside every horizon.

What the sweep deliberately does **not** do is `VACUUM`. SQLite reuses freed pages, so the retention bounds the database's growth to a steady state, and only a `VACUUM` returns the space to the filesystem — which rewrites the whole file and blocks the single writer for as long as that takes, on a process that is also carrying live guards. So the file size is *reported* rather than silently shrunk, and `README.md` gives the one-line command beside the backup procedure.

The transcript sweep is the one whose protection cannot come from a file's age, so it comes from the database: `expiredTranscripts` takes a horizon and a `keepSessions` set built from every non-terminal run and **every** chat thread — a chat has no terminal state to key on, since an operator may type into one at any moment, and a *parked* run's transcript is old precisely because it is the one about to be resumed. The session id is the file's own basename, which is how the pinned CLI names one; that is verified against the shipped layout rather than assumed, and if it ever stops holding the cost is the extra protection rather than the age test, which is on the README's *Not yet verified* list by name. The cache is told about exactly the files that went (`forgetTranscriptFiles`) rather than invalidated — invalidating the whole of it makes the next scan re-read every file from byte 0, which is the pass the byte-offset cache exists to avoid, and there is deliberately no function that does it: `337f355` deleted `invalidateTranscriptCache` "rather than left reading as an eviction path that exists", the eviction the cache actually has being `TRANSCRIPT_CACHE_MAX_ENTRIES`, which drops a file whole and coldest-first. A removed file's parsed entries would otherwise be held for the life of the process, leaving the dashboard showing spend from transcripts that are gone and disagreeing with the cutoff the period card had just been handed.

The checkout sweep is the one whose store is somebody else's directory, so what it may touch is narrower than the other two and is worth stating outright. It removes a *directory* and never a ref: `worktree remove` without `--force`, which leaves the branch and every commit on it exactly where they were and gives git a second veto over the cleanliness `planCheckoutReclaim` already checked. Six clauses have to hold, and each of them is a keep — `slotIsDirty`'s rule that an unreadable status counts as dirty is one of them, unchanged and not to be weakened, since `git status` cannot see the gitignored trees that are most of the bytes. It never removes a checkout an active run holds, one the newest run recorded in it has not finished with, one a run that has not started yet is set to carry the branch on from, or one whose branch carries commits its target does not have — where "does not have" is `landed_tip` unmoved for a squash and `rev-list --count target..branch` for everything else, because a squash rewrites the commits and git's own ancestry test can never call such a branch merged. What it costs when it does fire is the installed dependency tree the next run in that slot would have reused, which is the whole of why the horizon is a week: slot reuse is what makes isolation practical, and a horizon short enough to break it would trade disk for an install per run.
