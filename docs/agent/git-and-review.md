# Reviews, GitHub credentials and diffs

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing src/lib/review.ts, git.ts, diff.ts, patch.ts.**

**Reviewing a diff is not a work cycle and is never automatic.** `startReview` exists only behind a POST; nothing in the run loop reaches it. It refuses when the operator's *own* configured ceiling is already spent (`guardFraction >= 1` on either window) rather than going through `evaluateBudget` — there is no per-run fraction for a review and inventing a threshold would be a limit nobody set. The reviewer is given the diff, the run's task and how the run ended, but **not** the event log: the log is the process rather than the outcome, and a reviewer that reads how the agent got there reviews the journey. A large diff is cut at a file boundary and the omitted files are *named* in the prompt, because a reviewer handed a third of a change with no marker writes a confident review of a change that did not happen.

**A conflict resolution may check its own merge only where a toolchain can exist, and only where an operator named the command.** `resolveConflicts` pins `acceptEdits`, which auto-approves file edits and read-only shell and holds everything else for a human — and a `-p` child has nobody to ask. So the resolver could edit the conflicted files and could not run one command against the result: 19 of 58 completed resolutions, $109.94 of $233.85, say in their own report text that they could not compile or test what they had merged, across the whole recorded window. `AssistRequest.allowedTools` is the same door `ISOLATED_GIT_TOOLS` opens for a work cycle and the same flag — additive, so everything not named still follows the mode. **The reviewer passes no command and must keep passing none**: it is `--permission-mode plan` precisely so that nothing it does can write, and a command granted through that field would be the one hole in that. What the flag now always carries underneath the operator's list is `SEARCH_TOOLS` — `Grep` and `Glob`, which is why the emptiness guard is gone, since the list can no longer be empty. That is a bound by capability rather than by count, and the difference is the whole of what makes it not a hole: the pinned CLI drops both tools from the tool list whenever `Bash` is present unless something names one of them, so naming them buys their existence and not a permission. Measured on this install — zero of 469 recorded `system:init` events ever carried `Grep`, and every one of the five `Grep`/`Glob` calls an agent attempted came back "No such tool available" — and measured the other way on the pin, where adding the two to `--allowedTools` puts them back and changes nothing else in the list. `settings.resolveVerifyTools` is **empty by default and that is not timidity** — this app runs against whatever repository is mounted, so there is no command it could ship that is right for one, and `npm run typecheck` means nothing in a Go or Python tree. It is granted only on `resolveCheckout`'s **reuse** branch, where the run's own worktree was clean and standing on the branch and therefore has a dependency tree; the other branch cuts a fresh `git worktree add` with none, where a check fails for a reason that is not the merge and an agent reading a missing-module error as its own bad resolution will "fix" code that was right. `resolvePrompt` takes the granted list rather than assuming one, so the prompt cannot ask for a command the argv did not allow — an agent told to verify and then refused reports the refusal as a finding about the merge, which is how nineteen reports came to carry a limitation instead of a result.

**GitHub credentials reach a work cycle and nothing else.** The container has no other way to authenticate — the `~/.claude` mount carries Claude's login and neither `~/.gitconfig`, `~/.ssh` nor `~/.config/gh` — so `git push`, `gh pr create` and `gh issue view` all fail, and they fail *inside a tool call the run loop never inspects*: the cycle simply ends without the pull request. `githubEnv()` is where the token is turned into an environment, mirroring `telemetryEnv()`, and it sets three things because the failure arrives three ways: `GH_TOKEN`/`GITHUB_TOKEN` for the CLI, a credential helper for `https://github.com` for plain git, and `url.…insteadOf` rewriting `git@github.com:` to HTTPS because no key and no agent reach this container — that last one is the likeliest reason this fails on *some* repositories and not others. It travels as `GIT_CONFIG_*` rather than a config file, so it applies to every git the agent runs and dies with the process instead of outliving the run in a mounted tree; the helper list is **reset** first, because a repository cloned on the host can name `osxkeychain` in its own config and git consults helpers in order. The helper reads `$GH_TOKEN` at call time rather than embedding the token, so `git config --list` does not print it. `GIT_CONFIG_COUNT` must equal the number of key/value pairs — git discards the entire block otherwise, silently, which looks exactly like the unauthenticated container this exists to fix. Withholding is by namespace, not by remembering: `gitEnv()` and `reviewEnv()` strip `UF_*`, so the reviewer (which cannot write) and this app's own git (whose children run repository-controlled hooks, and which never touches the network) are excluded by construction — and `UF_GITHUB_TOKENS` is covered by that same rule with no second exclusion.

**…and *which* credential a work cycle gets is the repository's, not the install's.** One token for the whole install is one token for the whole fleet: `.env.example`'s own advice — a token limited to the repositories you run agents against — yields a one-repository token at one repository and a fifteen-repository token at fifteen, at which point an unattended agent asked to fix a test in one of them holds a credential that can force-push to the other fourteen. `selectGithubToken` is that choice, pure and unit-tested for `githubEnv`'s reason one function over: nothing downstream can see it go wrong, because the wrong token *works* — the push succeeds and the only evidence is a commit in somebody else's history. It is keyed by folder through the same `matchFolderKey` `copyGlobsFor` uses, longest key winning, absolute or relative to any mount; a folder no entry names still takes `UF_GITHUB_TOKEN`, which is what keeps an existing install's behaviour exactly what it was, so narrowing a whole install is leaving that blank and naming the repositories that should have one. An entry with an **empty** token is an answer rather than a typo — this repository gets none — because the narrowest thing an operator can write must not be the widest thing it does. The run resolves it once from `runs.repo_root ?? runs.folder` and hands it to `runIteration` as a **required** parameter, `buildArgs`' rule for the run-cost ceiling: a credential an unattended agent holds is not something a call site should widen by omission, and `cwd` cannot supply it, since an isolated run's cwd is its checkout under `.uf-worktrees` rather than the repository the token is about. What this does *not* do is narrow the helper, which still answers for `github.com` as a whole — how far the token reaches on GitHub's side is still GitHub's answer, and this only decides which token is handed over. The chat is the one child that keeps the install-wide one, and the asymmetry is the argument: an orchestrator turn looks across every mount *before* it knows which repository it is proposing work in, so narrowing it to a cwd would withhold the credential from every question about a repository it had not been pointed at yet — which is the failure `chatEnv` was widened to remove.

**Diffing runs repository-controlled code unless it is told not to.** Every `git diff` here carries `--no-ext-diff --no-textconv`: `diff.external` and a `diff.<driver>.textconv` reached through `.gitattributes` are both *commands git runs*, configured by the repository being rendered. Same class as the `core.fsmonitor` clearing that already applies to every call. Paths that come back from git and go out again as pathspecs are pinned with `:(top,literal)`, or a filename containing `*` would be read as a glob.

**A diff that was shortened says so.** The file *list* is always complete; patch bodies are budgeted (`selectForPatch`), and what the budget leaves out is counted and rendered as "N files listed without contents" rather than dropped. `splitPatches` matches chunks to files **by position**, never by parsing the header path — git re-quotes odd filenames there — and a count mismatch yields no patches at all rather than hunks filed under the wrong name.
