# Conventions and design language

> Extracted verbatim from `CLAUDE.md`, which grew past the size Claude Code will
> load into a session. Each paragraph records a correctness or safety decision
> whose violation is silent — nothing throws, nothing fails to typecheck.
> **Read before editing any component in src/components/, any route handler, any CSS.**

## Conventions

- **Server-only vs client.** `src/lib/apiTypes.ts` holds the DTO mirror of the server types so client components never transitively import `node:fs`. `src/lib/format.ts` is likewise client-safe. Don't import `windows.ts`/`transcripts.ts` types into a `"use client"` file — add to `apiTypes.ts` instead.
- **Route handlers** that touch SQLite or the filesystem need `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`. Every existing data route has both.
- **Module state survives dev hot reload** via `globalThis` singletons: `__ufDb`, `__ufBus`, `__ufProcs`, `__ufInterrupts`, `__ufTranscriptCache`. Those are examples rather than the roster — there are thirty-odd such keys and `grep -rn "globalThis as unknown" src/` finds every one. New long-lived state must follow the same pattern or it silently resets on every request in dev. Take a **new** key whenever the shape at an old one changes rather than reusing it, which is what `__ufInterrupts` did to the former `__ufCancelled` (`orchestrator.ts:373`): `??=` only initialises when the key is absent, so a pre-upgrade value survives the reload and every call on it throws.
- **Schema changes** go in `migrate()` in `db.ts` as idempotent `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` statements, or as an `addColumn` that reads the live schema — there is no migration framework, and `PRAGMA user_version` is a record rather than one: nothing keys a step on it. **A destructive change is the exception and it is one transaction.** `db.exec` maps to `sqlite3_exec`, which runs each statement in autocommit, so `relaxProposalTemplate`'s four statements used to commit independently — and a kill after the first left every proposal in `chat_proposals_old`, which no query here reads. The next boot then recreated `chat_proposals` empty from the same `CREATE TABLE IF NOT EXISTS` and the rebuild's own guard (`template_id` is already nullable, return) made the loss permanent: the guard that makes a migration idempotent is what stops it noticing a half-applied one. So the rebuild runs inside `db.transaction`, `recoverStrandedProposals` completes a leftover from a build that predates that (`INSERT OR IGNORE`, so a boot interrupted between the INSERT and the DROP is a no-op rather than a primary-key failure, and the index is recreated because the rename took it and the drop took it away), and any other `*_old` table is named on stdout and left alone — a table this build cannot read is not one it may drop, and refusing to boot over it would strand the whole install rather than one table. `SCHEMA_VERSION` records what a live-schema read cannot: that a *rebuild* completed, and that the file was last written by a newer build, which is what a rollback after a failed deploy produces. It is stamped after `migrate()` returns, so it means finished rather than started. Keying the ~50 `addColumn` calls on it would be fifty numbers or an ordering nobody can change, which is why those still read the schema. **And `migrate()` is gated on the data-directory claim**: `open()` runs on the first `db()` call in *any* process, which is how a second server — an agent's `next dev` pointed at the live database by an inherited `DATA_DIR` — was entitled to rebuild a table under the server that owns it. `heldByAnotherProcess()` is the synchronous half of `serverLock.ts` that answers it, and it reads an undecided lock as free. The exception is a file with no `settings` table: a process that owns nothing and finds no schema has nothing to destroy, and refusing there would leave it with no tables and every query throwing.
- **A Save stores only what differs from `DEFAULTS`, and that is a correctness decision rather than a size one.** `getSettings()` is `{...DEFAULTS, ...stored}` and the settings page PUTs the whole *effective* object, so writing it verbatim materialised all thirty-three keys into the blob the first time anybody pressed the button — and from that moment every `DEFAULT_*` in `settings.ts` was dead for that install. There is no versioning, no migration, and nothing surfaces the divergence: a shipped default and a running install disagree silently and permanently. Measured, not reasoned. `8651bcd` raised `maxConcurrentRuns` from `null` to 4 at 20:28 on 2026-08-14 to bound exactly the failure that happened two minutes later — sixteen concurrent runs meeting the provider's 5-hour wall inside a 44-second span, every one of them with its first cycle amputated — and the stored row carried an explicit `"maxConcurrentRuns": null` that put itself back over the 4 on every read, so the fix was never in force on the install it was written for. The four prompt strings are the same trap one door over, which is why `COMPLETION_NOTICE`, `SHARED_CHECKOUT_NOTICE` and `RESTART_KILLED_NOTICE` are generated in `orchestrator.ts` instead of living in `Settings`. **The trade is real and it is the one being chosen:** a value an operator set *to today's default* is now indistinguishable from one they never set, so a later change to that default moves it — which is precisely what lets a shipped number reach an existing install, and the effective object is identical either way until that day comes. If pinning ever needs to be sayable, the answer is a stored marker, never a return to writing the whole blob. The comparison is structural rather than `!==` because five keys hold an object or an array and every one of them arrives off the wire as a fresh instance, and it is not `JSON.stringify` because that is key-order sensitive and a reordered `chatDefaultGuards` would read as an edit and be stored forever — the original failure arriving through its own fix. `src/lib/settings.test.ts` asserts on the stored blob rather than the round trip, because a test that only checks `getSettings()` after `saveSettings()` passes either way, which is why this survived as long as it did.
- **Pages are client components** that poll their API route (dashboard 120s, run detail 3s for the row while SSE carries the log). There is no server-side data fetching or React Server Component data layer.
- **A run's page is a split view, and the pane shows one thing at a time.** The inspector on the right holds what the run *is* — state and the one control that acts on it, spend, work cycles, guards, telemetry, its checkout, its task — and is `lg:sticky` with its own scroll region, so it stays put while the pane scrolls. Column and row are placed explicitly rather than left to source order, because on a narrow window there is one column and the state is what the reader came for. The pane holds what the run *produced*, behind a `SegmentedControl`: log, report, changes, review, land. Three rules on it. **The log leads and nothing switches tabs on its own** — a run that finishes while you are reading one pane must not move you to another, which is the same reasoning that freezes the old log's open/closed state at the first status seen. **A tab is offered only when there is something behind it**, which is why `cycleOutputs` runs on the page rather than inside `RunOutput`: the bar has to know whether the agent said anything before it offers a Report tab, and two walks of the same event stream per paint is what the alternative costs. **Only the active tab is mounted**, so Changes re-reads the repository each time it is opened — the same cost as loading the page, against four polling cards alive behind the one being looked at. The guard block draws each configured limit as a `Meter`, and the spend one keeps the display-versus-guard split the windows already make: `runs.spent_usd` is the solid fill and the killed-cycle estimate is the hatched band past it, never one summed fill, so the bar shows the threshold that will actually stop the run without presenting the estimate as a correction to what the CLI measured. The time bar reads `finished_at` where there is one, since the clock only ticks while a run can still move. On the runs list, the cycle in flight is a **column of its own** on the in-flight list and nowhere else, and `fmtCycleInFlight` is the only thing that decides it, wording included — for the reason that function documents, and separated from the completed count for the reason the wording says "in flight". That list's box is deliberately not a scroll container: the sticky header then pins to the content pane as the page scrolls, where a wrapper of its own would pin it to a box that never moves.
- **The chat's transcript says who is speaking with structure, never with colour.** The answer is the pane: plain prose at a readable measure with nothing drawn round it, because it is what the reader came for. The operator's own words are a bezelled block pulled right — the raised chip every secondary control here wears — and were an accent-tinted bubble, which is the web-chat idiom and which spent the app's one accent saying "a human typed this", a fact the position and the speaker label already carry. A `system` turn is this app speaking and keeps its own treatment, because a sentence about what the app did, rendered as though the model said it, is one the operator will later attribute to the wrong party. Proposals are rows of one grouped box and selection is a `--selection` wash rather than a border, since a row that gained a border would shift the two beside it; the action row puts the one default action at the right edge, where every `Sheet` here already puts it, and Select-all at the other end because it is not a decision about the work. Everything that makes a proposal card approvable is unchanged and must stay: the guard set spelled out (including the untemplated one), a rewritten prompt marked, the dependency order named, what the click starts counted in words, and the **explicit list of the ids the page displayed** on the wire. The composer is pinned to the foot of the pane and takes **⌘↩** as well as Enter — ⌘↩ is the chord the run form already commits with and the one the shell's keyboard layer deliberately binds to nothing; the `isComposing` guard is tested *after* it, because an IME composition can only be ended by a bare Enter. The waiting state stays legible frozen (`@layer base` flattens the spinner to a still, and the word and the clock beside it never moved), and it claims no progress it does not have: elapsed time is the only real measure of a turn.
- **The shell is a window, not a page.** `src/components/shell/` holds all of it — `AppShell` (the frame, and the app's one keyboard listener), `Sidebar`, `Toolbar`, `QuickOpen`, `panes.ts`, `shortcuts.ts` — and `layout.tsx` does nothing but the theme script, the skip link and `<AppShell>`. There is no centred column: the source list is fixed-width and full height, and the content pane owns its own scroll region, which is what makes a `sticky bottom-0` bar inside a page stick to the pane rather than to the document. A `fixed` bar is still positioned against the viewport and has to step around the sidebar itself — the branches page's selection bar does, with `left-[var(--sidebar-w)]`. `panes.ts` is the single list of destinations because four things read it: the source list draws them, the toolbar titles from them, ⌘1…⌘8 navigates to them and quick open searches them, and a pane added to one and missed in the others is a row you can reach and cannot get back from. Its `activePane` matches on a path *segment*, not a prefix — `startsWith("/runs")` is what the top nav did, and it also matches a future `/runsheet`. The toolbar's title and action are derived from the **route** rather than published by the page: the pages still carry their own `<h1>`, so the strip renders a plain `<div>` and not a second heading, and the action is only ever a *destination* — Start, Run, Approve and Land all need page state, and a toolbar button wired to one would be the shell reaching into a body it does not own.
- **A box inside the pane is never sized in viewport units, because the pane is not the viewport.** It is the window less the toolbar less the pane's own `pt-5`/`pb-12` less whatever heading the page puts above the box — so `62vh`, `68vh` and `calc(100dvh - var(--toolbar-h))` all named a box taller than the space it had, and every one of them hung past the bottom edge and gave the pane a scrollbar whose whole travel was empty: a screen-deep band under a 62vh log that the inspector beside it had already stretched the row past, a composer under the fold behind a thread that was scrolling itself. What replaces the figure is a mechanism rather than a better figure — `main`'s wrapper is a **flex column of `min-h-full`**, so `flex-1` means "fill what is left" and `min-h-full` rather than `h-full` keeps a page longer than the pane growing exactly as before. A box that fills that way must not also report its *content* as its intrinsic height, or the row is sized by the transcript instead of by the pane: the run log fills by being taken out of flow (`lg:absolute lg:inset-0` in a `relative` parent that has the height), which contributes nothing to the measurement. The fill is `lg:`-only on both split pages — stacked at one column there is a second column of content below the fold and the page is *meant* to scroll, so the box stays bounded there. `--pane-h` (`100dvh` less `--toolbar-actual`, which is the `max()` the toolbar and the sidebar's brand strip already compute inline) is for the one case a flex parent cannot reach: a `sticky` inspector's own cap. And a `sticky bottom-0` bar is never pushed *past* where it sits in flow, so the pane's `pb-12` stayed underneath it as a band of nothing — the three pane footers pair `-mb-12` with it exactly as they already pair `-mx-4` with `px-4`.
- **A table must not be the reason the pane scrolls sideways.** A truncating line is `white-space: nowrap`, so its min-content width is the whole sentence — a `max-w-[56ch]` cap on it is therefore a *floor* under the column, and the runs list stayed 916px wide however narrow the window got, scrolling sideways into empty canvas beside cards that had stopped at the pane's own edge. `w-full max-w-0` on the cell is what makes it the column that gives: zero as its max content contribution, 100% as its preference, so the fixed columns keep their widths and this one takes what is left, which is what the ellipsis was for. The `56ch` stays as an upper bound on a wide window. The list view is deliberately not wrapped in `overflow-x-auto` — that would pin its sticky header to a box that never scrolls — so the column that gives is the whole of what keeps that decision affordable. Below the mobile breakpoint the same cell **releases** the cap with a `max-md:max-w-none`, and it has to: there is no column left to give to there, so a zero max-width is a zero-width block with the task hanging out of it.
- **`Table`'s `stack` is the narrow-window answer, and the label on each `Td` is the other half of it.** `TableWrap`'s sideways scroll is right where a row is a set of readings a reader compares; it is not a presentation of a *record*. At 390px a run's status and its spend are never on screen together, and the row tint `Tr` exists for — the thing that holds a label and a figure on one line as the eye crosses — does not exist on touch at all. So `stack` makes the whole grid one block per row below `md`, `THead` takes the column heads off the screen, the hairline moves from the cells to the row, and each `Td` carries the `label` that names its own field. **The two are one decision and neither works alone**: with the heads gone, a table switched on without labels is a column of unnamed figures, which is worse than the scroll it replaced — which is exactly why this is opt-in per table rather than a change to what `Table` does everywhere. Seventeen of the app's twenty carry it. The three that do not are a list, not a backlog: the settings page's **calibration suggestion table** (`Ceiling` / `Set now` / `Observed peak`, under *Where a ceiling can come from*) and `RunAgentCost` were out of the scope this landed under — the storage report this sentence used to name is no longer a table at all, it is a `ListGroup` of `ListRow`s, which is why the count is right and the name was not — and `/account`'s daily cost has **no `<thead>` at all**, so there is no column name for `THead` to take away and a date beside a dollar figure is already two short columns that fit — stacking it would spend two lines naming what a date and a dollar sign say on their own. That last one is the shape to check for before reaching for `stack`, rather than a table it was forgotten on. A cell left deliberately without a label is the headline the record is identified by (a status, a task, a branch), never a figure; `labelPlacement="above"` is for a value that is prose or a list, which in the right half of a 390px row is a four-word column. **The explicit ARIA roles are not decoration.** `display: block` strips a table element's implicit role in every engine, and the row and column relationships go with the layout — so `Table`/`THead`/`TBody`/`Tr`/`Td` state theirs whenever `stack` is on, and above the breakpoint each is exactly the role the element already had. The value is wrapped in a `block md:contents` span so the flex row has one item to place: several cells hold two children, and `contents` is what makes that wrapper generate no box at all in the flat table. Only `display` may be switched on it — an inherited property stated there would reach the children *through* `contents` and change the desktop.
- **A capped scroll region is released below the breakpoint, not kept.** `ListView`'s `capped` box pairs `max-h-80` with `overflow-auto` so the sticky head has a box to stick inside. Below `md` there is no head — `THead` hid it — and the rows are blocks, so what is left is a 320px nested scroller inside a scrolling pane with nothing pinned to the top of it: a trap on touch, where the only way past a list is through it. `max-md:max-h-none max-md:overflow-visible`, and it lives in `ListView` because it was written out by hand five times: three copies carried it, one box is uncapped and one is not a scroll container at all. Only the last of those is a difference anybody recorded a reason for — the missing cap, and the one sticky head drawn without its hairline, are open questions the typed `box` preserves rather than answers, which is the difference between a variant and a copy that drifted.
- **The collapse is a document state, and it is settled before the first paint.** The rail is 168px narrower than the list, so a state read after hydration would shove the whole content pane sideways one frame into every page load — a louder version of the flash the theme script exists to prevent, which is why it rides in the same script. `[data-sidebar="collapsed"]` on `:root` swaps `--sidebar-w` and hides the row labels (kept in the accessibility tree, since the glyph is then the only thing naming the destination), and that is the whole of what it changes. The attribute is the source of truth; React mirrors it so the toggle can announce `aria-expanded`, and `writeCollapsed` writes the attribute and `localStorage` together. Storage failing costs the next page load, not this one.
- **The shell is installable, and the toolbar knows it.** `src/app/manifest.ts` declares `display: "standalone"` with `window-controls-overlay` first in `display_override`, which is what makes a browser hand the whole title bar to the page and publish `env(titlebar-area-x/y/width/height)`. The toolbar's height is a *floor* — `max(--toolbar-h, env(titlebar-area-height, 0px))` — and its left padding steps around the traffic lights by however much the sidebar has not already absorbed; every one of those env values is zero in an ordinary tab, so nothing anywhere branches on which case it is in. The empty part of the strip is `app-drag` and every control on it is `app-no-drag`, because a drag region swallows the pointer press; the sidebar's brand strip is deliberately not a link home so the whole of it can be drag space. `apple-mobile-web-app-capable` is declared through `metadata.other` **alongside** Next's own `mobile-web-app-capable`: Next emits only the standardised name because Chromium deprecated the Apple one, and WebKit reads only the Apple one, so Safari's Add to Dock needs both present. Icons are generated from `public/icon.svg`'s own geometry by `scripts/make-icons.py` rather than hand-drawn — an SVG covers a tab and Chromium's install criteria, but not `apple-touch-icon`, which Safari will not read as SVG, or a maskable icon, which is separate artwork (full bleed, mark inside the safe zone) rather than the rounded one relabelled. The manifest route sits inside `middleware.ts`'s matcher like every page, so installing behind `UF_AUTH_TOKEN` means signing in first; the exemption list is **not** widened for it — see the note beside the one entry it already has.
- **⌘ and nothing beside it, and never over a text field.** `AppShell` registers one `keydown` listener; `shortcuts.ts` holds the two rules it obeys, separately, because both are easy to get wrong in a way nothing reports — a layer that swallows a keystroke in a field looks like a dropped character, and one that claims a chord the browser owns looks like the browser broke. `isPlainCommandChord` refuses Ctrl as an alias for ⌘ (on Windows and Linux, Ctrl+1…8 switches browser tab and Ctrl+K is the address bar) and refuses ⌥ and ⇧, which make other people's chords. `isTextEntry` lists the input types that are *not* text entry, so a type this app has never seen is assumed to be text and left alone — the direction that costs a shortcut rather than a keystroke. ⌘↩ is the one carve-out from that exclusion and the shell binds it to nothing: the rule is stated where the exclusion is, so this layer can never become the reason a form's own commit chord stops working. Bound: ⌘1…⌘8 and ⌘K. Never bound: ⌘R, ⌘L, ⌘T, ⌘W — and Esc, because the quick-open sheet and the mobile drawer are both `<dialog>`s and the browser already routes Esc through whichever one is open, so a second handler would be two things closing one of them — and with two in play, two things closing the wrong one. The two never stack: ⌘K closes the drawer before it opens the sheet, for the same reason ⌘1…⌘8 closes both before it navigates. Every binding is announced with `aria-keyshortcuts` on the control it belongs to. **Quick open navigates and does nothing else.** That is a constraint on what the component may be rather than a feature not yet written: a keystroke away from spending money is what every approval gate in this app exists to prevent, and a palette is exactly where such a thing would look convenient. It reads `/api/runs` and `/api/workflows` through `jsonRequest`, only while it is open, so a failed read is a notice above a list that still offers the panes.
- **The mobile boundary is `md` (768px), the sidebar is a drawer below it, the touch target is 44px, and every mobile rule is additive.** Four facts, and they are a contract rather than a description: the shell was made usable on a phone first and the tables, the forms, the canvas and the run detail split view follow it, so a run that picks a different number puts two boundaries in one window.
  - **`md`, 48rem, and the same line everywhere.** At or above it the source list is a docked column; below it, a drawer. `sm` was rejected because a 640px window still hands 224px of 640 to a list, and `lg` because a tablet in portrait is 768px *exactly* and has the room — losing the list there would be a worse window than the one being fixed. The two split pages keep their own `lg:`: that is a decision about a *page's* columns and this one is about the window, and they are allowed to differ. The figure is written in CSS as Tailwind's `md` and once in JS as `SIDEBAR_DOCKED` in `AppShell.tsx`, because a media query is the one thing a Tailwind class cannot be read back from — that listener is what closes the drawer when a phone is turned to landscape and crosses 768px with it still open. Keep the two in step.
  - **The drawer is a native `<dialog>` and obeys `Sheet`'s three rules.** `Sheet` itself is not reused — it is a top-anchored panel with a title, one default action and Cancel, and a nav drawer has none of the three — but `showModal()` is, for the same reason: the top layer, the inert background, the focus trap and Esc come from the browser and a hand-rolled overlay is a hand-rolled focus trap. So: always rendered and never conditionally mounted; nothing sets `display` on it, which is also why it is **not** hidden above the breakpoint with a `md:hidden` (`display: none` on an element in the top layer hides it without taking it out of the top layer — an inert page with nothing on screen explaining why, which is what the `matchMedia` close exists to prevent); and `cancel` is prevented so Esc routes through `onDismiss`. The backdrop dismiss is a click whose target is the dialog element rather than the panel, because `inset-0` makes the element the whole viewport and `::backdrop` is behind it and unreachable. **`[data-sidebar="collapsed"]` is a desktop state and must not reach the drawer**: it is written before first paint and swaps `--sidebar-w`, and a drawer is closed on every page load and has nothing to settle — so the drawer reads `--sidebar-w-list`, which nothing swaps, and carries neither `uf-sidebar-row` nor `uf-sidebar-label`, so the two rail rules in `globals.css` have nothing to match. Both halves are needed; the variable alone leaves the labels `sr-only`. And a drawer **absorbs none of the window's left edge**, which is what `--sidebar-w-absorbed` exists to say: the toolbar subtracts it from `env(titlebar-area-x)` to find the part of the traffic lights it still has to clear, and an installed window narrowed past the breakpoint would otherwise put the first button on the strip underneath them — silently, because the subtraction merely stays negative and the `max()` keeps picking the 12px padding. Anything else that does titlebar arithmetic owes the same distinction.
  - **44px is the hit target below the breakpoint**, against `--control-h`'s 32px above it, and it is `max-md:min-h-11` rather than a change to the token — `--control-h` is the pointer's floor and the whole kit is built on it. Where a control's *visual* box must stay 32px, the extra comes from a stretched `::after` overlay the layout never sees, which is the recipe `Switch` already uses. It lives in the kit rather than at call sites: `Button`'s `SIZE` map and `SegmentedControl`'s segment each state it in the same entry as the pointer's height, so a size reads as one decision. That co-location is legibility and **not** the `Record` map's own rule — as `Button`'s comment says, a base utility and a `max-md:` one are ordered by Tailwind whichever string they are written in, and co-location is load-bearing only where both candidates carry the *same* variant, which is what `Table`'s `STACKED_CELL` has and this does not. `Switch` is the recipe's own case and states both figures where it sits: the pill stays 38×22, the pointer's overlay is 38×32, and below the breakpoint it is 44×44 — the one control that has to grow *sideways* as well, because 22px is short enough that height alone leaves it under the floor in the axis a thumb misses in, and the 3px of bleed per side is inside the 8px `gap` a `ListRow` puts between two trailing controls, so no two targets can touch. `SegmentedControl`'s segment takes a `max-md:min-w-11` beside its height, and the width is not redundant: a `labels="hidden"` group is a 16px glyph in 10px of padding, so the theme picker's three segments cleared the floor vertically and were 38px wide. It is a `min-w` and so a floor rather than a size: the only *labelled* segment it reaches is the runs list's "All" at ~37px, and it is the same figure in both states, so no selected segment can change size. `Switch`'s `::after` recipe is not available here — segments sit 2px apart, so any bleed would take the tap aimed at the neighbour — and the width is not free: `ThemeToggle` is three of these on the toolbar, so the strip's right-hand group grows ~20px below the breakpoint and the title beside it, the one item there that shrinks, truncates that much sooner. That title is derived from the route and the page under it carries its own `<h1>`, so what gives way is a duplicate. Everything else takes the plain `max-md:min-h-11`: `Field`'s `CONTROL_LINE` (so every `Input`, `Select` and `LimitField` control), `Toggle`, `ListRow`, `QuickOpen`'s result rows — which navigate on the click, so the row *is* the control — the settings page's section chips, and the run form's one button drawn as a link, because the hit target does not depend on what a control looks like. Two things still do not take it and both say why where they sit. A `<summary>`, whose `list-item` display is what draws the disclosure triangle, buys the target with `max-md:py-3.5` instead — a min-height on a list-item leaves the word and its triangle at the top of a box the finger is aiming at the middle of. **That figure is stated once, in `ui/Disclosure`, which is what a `<details>` in this app is written as.** The recipe lived at seven hand-rolled call sites and three of them carried it, which is how a missing hit target survives every review it is read in: it is invisible from each of the files that has one, and the file that does not looks exactly like the file that does. The component states the target and the interaction states and stops there — the desktop box stays the caller's, because those call sites disagree on it (`py-2` on the runs list, nothing on the branches and chat folds, `--control-h` on the diff file row) and that disagreement is each surface's own rhythm rather than drift. It also states no ARIA at all, which is the other half of using the element rather than imitating it: a `role` or an `aria-expanded` on a native disclosure is redundant in one engine and wrong in another. And the chat's proposal checkbox, which is 16px inside a `<label>` wrapping the whole card, so the row is the target a finger actually finds and an `::after` would not render on an `<input>` anyway.
  - **A control that cannot wrap is a control that pushes the pane sideways.** `SegmentedControl` is an `inline-flex`, and a five-option group is about 330px of segments against the ~358px a 390px phone has once the pane's gutter is off — so it carries `max-md:flex-wrap`, in the component rather than at the two call sites that are near the line, because the next five-option group will not know it is near it. Nothing above the breakpoint comes close to the width, so the rule changes nothing there.
  - **A `fixed` bar is outside `AppShell`'s box, so it owes both edges itself.** The branches page's selection bar is positioned against the viewport, so it steps around the source list with `left-[var(--sidebar-w)]` — and below the breakpoint there is no source list to step around, because a drawer absorbs none of the window's left edge. That is the same distinction `--sidebar-w-absorbed` exists to make for the toolbar, and left unmade the bar starts 224px into a 390px window. It pads its own `env(safe-area-inset-bottom)` for the reason the drawer panel does: `AppShell`'s insets are on a box this element is not inside — and it sets its own `bottom: var(--keyboard-inset, 0px)` on exactly the same grounds, because the shell shrinking its box is what lifts the pane's `sticky` footers off a software keyboard and this bar is not in that box. The bar holds the strategy `select`, and the picker iOS opens for a `select` is an interactive widget like the keyboard, so left unmade the operator chooses a strategy behind the thing they are choosing it with. And the spacer that reserves its height has to follow it from one row to three — deliberately over-reserving, because guessing high costs blank space past the last row and guessing low costs a row nobody can reach.
  - **16px is the floor for a control that takes text, and it is a platform rule rather than a type decision.** iOS Safari zooms the page in whenever an `input`, `select` or `textarea` under 16px takes focus, and it never zooms back out — so one tap on the first field leaves every screen after it offset sideways for the rest of the session, with nothing on the page saying why. Three things this deliberately is not. Not a change to `--text-sm`, which is 13 alongside `--text-base` for the reason written beside them in `@theme` and which twenty other things read. Not a `font-size` on `html`, which redefines `rem` and silently takes 12.5% off every spacing and type utility in the app. And not unlayered, so a call site that states its own size still wins. The floor sits on the *controls*, below the breakpoint only, and it has two homes: `max-md:text-[16px]` in `Field`'s `CONTROL_BASE`, which every `Input`, `Select`, `Textarea` and `LimitField` control concatenates, and a `@media (width < 48rem)` block in the legacy layer for whatever is still reaching the element selectors — the query Tailwind v4 emits for `max-md:`, character for character, rather than a max-width, so the breakpoint is one boundary and not two that agree to within a fraction of a pixel. That block is in `legacy` and so loses to any utility, which is the point: it is a floor under the un-migrated, not an override of the kit — but it also means a hand-written control carrying its own `text-sm` is not covered by it and has to repeat the class. There is **exactly one**, and the whole of `src/app/` and `src/components/` was read to establish that: the chat composer. It was two until the branches page's land-strategy `select` went onto the kit's `Select` inside a `Field`, where `CONTROL_BASE` states the floor once for every text control in the app; the second half of that conversion is that the picker in the app's most expensive button row now carries a visible label instead of an `aria-label`. Every other field in the app is a `Field` primitive. Anything new that is not is the second. A **button** is emphatically not in this: a `Button`, a segment and a toggle chip never zoom, and raising their text would widen a `SegmentedControl` that `max-md:flex-wrap` has only just made fit.
  - **A `ListRow` wraps below the breakpoint, and the label's `min-w-32` is what decides when.** Every caller states the control's width on a wrapper rather than on the control (see the note in `Field`) and those widths are absolute — `w-72` is 288px against roughly the same figure a 390px screen leaves inside a `primary` card, the group's border and the row's own padding, so the label was squeezed to nothing and its description came out as a column of single letters. Flex line breaking clamps an item's hypothetical main size by its `min-width`, so a label that cannot have 128px sends the control to a line of its own, and a switch or a short number field — which can — stays on the right where a grouped list puts it. A blanket `basis-full` was the other candidate and is rejected: it moves every switch in Settings off the right edge to fix the four wide selects. The `max-md:justify-end` beside it is what keeps one group from showing two alignments — the label is `flex-1`, so on a line it shares there is no free space and `between` and `end` are the same declaration, but on a *wrapped* line the control is the only item and `space-between` resolves to flex-start for one item. The row's own `max-md:min-h-11` is **not** a hit target — the row is inert — it is the box `Switch`'s 44px overlay has to fit inside without reaching into the rows above and below it.
  - **The workflow canvas is *read* on a phone and *arranged* on a screen, and it says so rather than half-answering a finger.** Every gesture it has already works on touch and none of them was added for it: pointer events fire, and the palette button, the block card and the Link handle each carry `touch-none` — without which a drag on a block would scroll the page as well as move the block, and the two gestures would fight — so a tap on the palette adds a block, a drag moves one, and Link then **Link here** joins two, through the same `handledByPointer` route that already keeps the pointer and the `click` a screen reader dispatches from both firing. What is not answered is *arranging* a graph: a 390px window is about 358px of pane against `canvasGraph.ts`'s `NODE_W` of 232 and `COL_STRIDE` of 328, so it holds exactly one block and the gap to the next, and a gesture for placing blocks against each other through that would be a worse lie than the sentence. So a `md:hidden` line under the toolbar states it, and names the one fact the width takes away — at one column the inspector is **below** the canvas, so the block a tap has just selected is edited somewhere the tap does not reveal. `BlockStatement`'s five facts stay whole at every width and are never put behind a disclosure: they are what a press of Run is approved against, and a page that scrolls to reach them is better than one that hides one of them. Three of this surface's controls are hand-rolled rather than kit primitives, so each repeats the 44px floor itself — the palette buttons and the link condition chip take the plain `max-md:min-h-11`; the Link handle takes `Switch`'s `::after` overlay instead, because the card is a fixed `NODE_H` and a taller *box* would take the twelve pixels the task preview is drawn in. And the scroll region's cap is **tightened** below the breakpoint where `ListView`'s `capped` box releases both of its halves, which is not an exception to that rule but the half of it that transfers: releasing it here is not available, since `overflow-auto` on a 640px sheet inside a 390px pane is the whole of what keeps the *pane* from scrolling sideways. What does transfer is that a nested scroller filling the screen reads as the end of the page — at `62vh` the frame did, and what is past it is the inspector holding the guards. `22rem` is three block-heights, so the surface still shows a column and what is under it is on screen.
  - **A software keyboard is not a viewport unit, and `--keyboard-inset` is the whole of what this app does about it.** `dvh` tracks the *browser's* chrome; a keyboard resizes the **visual** viewport and leaves the layout viewport, and every vh unit derived from it, exactly as it was. So everything anchored to the foot of the pane sits behind the keyboard — the three `sticky bottom-0` footers, the chat composer, a `Sheet`'s one default action — which on a phone is the box being typed into and the button that commits it, both off screen at once. `AppShell` publishes `window.innerHeight - visualViewport.height` on `:root`; the shell's own height is `calc(100dvh - var(--keyboard-inset))` and `--pane-h` subtracts it, so everything measured against the pane moves with it, and a `Sheet` — in the top layer, so outside the shell's box — subtracts it itself. Three things about the measurement are load-bearing and each of them is a bug that was reasoned out rather than seen. It is **not** `visualViewport.offsetTop`: that is how far the browser has scrolled the visible area inside the layout one, and it changes the moment the shell shrinks, so reading it back is a loop between this and the height it sets. A `scale` above 1 reports 0, because a pinch-zoomed page shrinks the visual viewport too and must not fold the shell in half. And anything under `KEYBOARD_FLOOR_PX` reports 0, because a horizontal scrollbar counts in `innerHeight` and not in `visualViewport.height` — which is what keeps a desktop window provably untouched, since under the floor the property is never written at all. It is 0px on the server, on the desktop, in an installed window and on a phone with nothing focused, so it is additive on exactly the grounds `env(safe-area-inset-*)` is.
  - **A `Sheet` is in the top layer, so it owes the window's edges itself** — the same distinction `SidebarDrawer` already makes one component over, and it had none of it. All four `env(safe-area-inset-*)` go on the `<dialog>`, which is `inset-0` and therefore the whole screen rather than the part of it the OS has left alone. The panel's cap is `100dvh` less the keyboard less the vertical pair less 3rem, and it was `100vh`: on a phone that is the viewport with the browser's chrome *hidden*, so the sheet was taller than the screen and its default action below the fold — on the one element in the app whose whole job is to be answered. The panel is what scrolls, not the dialog, which is what keeps Cancel and the default action at the end of a scroll region rather than under the keyboard.
  - **Every mobile change is additive behind a breakpoint prefix.** A `max-md:` rule or a `md:`-prefixed override, never an edit to an unprefixed class — the app at 1440px must be pixel-identical before and after. `env(safe-area-inset-*)` counts as additive on the same grounds: all four are 0 in a browser tab, on the desktop and in an installed desktop window, and non-zero only under `viewportFit: "cover"`, which `layout.tsx` sets for the iOS home-screen install. The insets are applied on `AppShell`'s outer box (all four — `cover` applies to an ordinary iOS *tab* too, where landscape takes ~47px off one side against the pane's 16px gutter) and on the drawer panel, which is a `fixed` dialog and so outside that box; `--pane-h` subtracts the vertical pair. A `sticky bottom-0` bar sticks to the bottom of `<main>`, so padding *on* `<main>` would not have moved it — which is why the inset is on the box around it. And verify the variant in the emitted CSS rather than assuming it: Tailwind emits nothing at all for a spelling it does not know, silently, and `max-md:` is exactly the kind of spelling that looks obvious and would fail without a word.
- **Styling** is Tailwind v4, CSS-first — no `tailwind.config.js`, no CSS modules, no third-party component library. Primitives live in `src/components/ui/`. Four things in `src/app/globals.css` are load-bearing and were each arrived at by measurement, not preference:
  - **The `@layer theme, base, legacy, components, utilities` statement.** Layer precedence is declared, never inferred: `next dev` and `next build` emit the blocks in *different* orders, so an inferred order means the legacy sheet beats utilities in the browser and loses to them in the shipped image.
  - **`@import "tailwindcss" source(none)` plus an explicit `@source`.** Automatic content detection respects `.gitignore`, and `.dockerignore` hides `.gitignore` from the build context — so the container would scan `CLAUDE.md` and `tsconfig.tsbuildinfo` and emit a different stylesheet than the host. A class would work in `next dev` and be missing from the image.
  - **Tokens keep their existing semantic names** (`--bg-raised`, `--fg-muted`, `--warn`) and `@theme inline` maps them to utilities. `inline` is mandatory — without it a utility freezes one theme's value at the definition site. Three theme states come from `color-scheme` + `light-dark()`: absent `[data-theme]` follows the OS, the two explicit values override it. Do not put `font-size` back on `html`; it redefines `rem` and silently shrinks every spacing and type utility by 12.5%.
  - **Variants are typed props with `Record<Union, string>` lookup maps, never `data-[…]` Tailwind variants.** Three reasons, all silent: React renders `data-x={false}` as the string `"false"`, which a bare `data-x:` variant matches on presence; Tailwind scans source as text, so an interpolated `text-${tone}` emits nothing; and `Meter` carries both `data-sev="ok"` and `data-unknown="true"` for an unknown reading (`severityFor(null)` is `"ok"`), where losing the tiebreak paints a solid green 100% bar instead of the hatched indeterminate one. `src/components/Meter.test.tsx` pins that last one. Shared tone unions live in `src/lib/format.ts`, not beside the components, because `src/lib` is what `tsconfig.test.json` compiles. The two attribute selectors on `:root` are not exceptions to this and must not be read as a precedent for one: `[data-theme]` and `[data-sidebar]` are *document* states written before React exists, by the pre-paint script, precisely because they have to be settled before the first paint. They change geometry and `color-scheme` and nothing else, and no component reads either as a variant.
  - The `@layer legacy { … }` block is the migration's remaining surface and shrinks as pages move onto the kit. It still beats Preflight and still loses to utilities. When it is empty, delete it — and with it `--radius`, `--mono` and `--sans`, which exist only for its sake.
- **Design language.** What the kit already decided, so a page does not decide it again differently.
  - **One thing leads on every screen, and elevation says which.** `Card`'s `emphasis` is the whole mechanism: `primary` (extra padding, `shadow-e2`) for the one card a page exists to show, `default` (`shadow-e1`) for everything the reader came for, `quiet` (flat) for a card that is scaffolding — a form section, a picker, a footnote table. More than one `primary` per screen means none of them is. Hierarchy is said with size, weight, elevation and whitespace; a second border or a colour is not a substitute for any of them.
  - **Grouping has a closed vocabulary, and it is seven things.** `docs/ui-density-audit.md` settles it and carries the reasoning; this is the short form, because every feature that landed before it picked its own answer and the answers did not compose. Allowed: a **pane** (a row in `panes.ts` — the list is closed at eight, because ⌘1…⌘8 has eight digits and four things read that file); a **sub-route** for a group that is both a screen's worth and used weekly or less; a **card**, for contents that answer one question a reader could ask out loud, capped at seven *as peers at one level*, at nine controls before it needs an inner `ListGroup`, and at **at most** one `primary` (a page may legitimately have none); a **`ListGroup` with a `label`**, for rows sharing a subject the card's title does not name — three to nine, more than nine is two, and fewer than three only where the *label* states something neither row does; a `ListGroup` *without* a label is a box rather than a group; a **`Disclosure`**, for evidence (a log, a diff, an older list, a preflight report) or a setting whose default is right for nearly everyone; a **`SegmentedControl` tab strip**, for two to five mutually exclusive views of one subject, one strip per page, and never as a way of moving between *subjects* — that is the sidebar's job; and a **`Sheet`**, for a decision that must be answered first or an action that is destructive, irreversible or handles a credential. Never used, each because a build run will reach for it: a ninth pane; an accordion, meaning a *coordinated* set where opening one panel closes another — independent sibling `Disclosure`s are not one; a nested disclosure; a tab strip inside a tab; a **page-level drawer** (the sidebar's is the app's only one, and a second `<dialog>` in the top layer is a second focus trap competing for the same Esc); a tooltip carrying anything the reader needs (no touch equivalent — `Field`'s `hint` and `ListRow`'s `description` are where it goes); and any hover-reveal, since `ListRow` is deliberately inert. The order of moves matters as much as the set: **delete redundancy, then group, then reorder, then hide** — hiding is the last move and not the first, because a reader who cannot find a control concludes it does not exist. And a fact a decision is approved against is **never** folded however rare it is: `BlockStatement`'s sentence, the chat proposal card's facts and the run form's guard summary are all that kind of fact. **A *region* is not an eighth affordance and is not a group**: it is a heading over cards or blocks that are already peers, naming *why* they sit together, and it may hold one of them. Three surfaces landed one — the run inspector's, the dashboard's three cost sources, the editor's block groups — and all three obey the same two rules. It is a `<div>` with an `<h2>` in it and **never** a `<section>`, because `section + section { margin-top: 24px }` is still in the legacy layer and would push every region but the first down 24px, which reads as a spacing decision somebody made; `Card` records being bitten by the same rule. And **no figure, meter, badge, total or comparison is drawn at region level** — on the dashboard that is the never-sum rule made structural, so a card lands in the band whose source it reads and a total across a boundary is visibly wrong rather than merely undocumented.
  - **`ceiling`, `guard` and `limit` are three different words for three different things, and the app says which.** A **ceiling** is a number set in Settings that a window percentage is measured against — Anthropic publishes none, so it is the operator's estimate, and it is never a cap on one run. A **guard** is a threshold on a window (5-hour or weekly) that steps a run aside or ends it; it is a percentage, never dollars and never minutes. A **limit** is a cap on one unit of work — this run, this chat turn, this workflow, this install: work cycles, spend, time. The three are already distinct in the code — `sessionCostLimit` is a ceiling, `maxSessionFraction` is a guard, `maxRunCostUSD` is a limit — and the copy has drifted across them exactly once per surface, which is how "no 5-hour ceiling is set, so this guard has nothing to measure against" reads correctly on one line and "each cycle carries what is left of it as a ceiling" reads wrongly on another. Keep the three apart in new copy; a sentence that needs two of them is usually saying something true about both.
  - **The palette and the type scale are AppKit's, not the web's.** Surfaces are four steps rather than three: `--bg` is the window, `--bg-raised` a card or a sheet, `--bg-inset` a *recess* into one (a field, a meter track, a log), and `--bg-grouped` a grouped list inside a card. The last one moves in opposite directions per scheme — AppKit lightens a grouped row against a dark window and darkens it against a light one — so one hex pair cannot express it and `light-dark()` is what carries the difference; it is also why a bezeled control is `--bezel` and never `--bg-inset`, which is the recess a text field sits in and reads as the same object at a glance. `--border` is a hairline at AppKit weight, far lighter than the box border it replaced, and `--shadow-e1` is now barely more than a seam, so a `default` card reads as a grouped box separated by its hairline rather than a card floating off the page. Body is 13px on the SF stack (`-apple-system` first, so macOS resolves SF rather than whatever `system-ui` has been remapped to), and `--text-sm` is 13px as well, deliberately: AppKit sets a control's own text at body size, and the two names stay apart so a call site still says which of the two it meant and the body step can move again without dragging every control with it. Nothing shouts — `CardTitle` and `Th` are sentence case at a weight step, never uppercase with tracking, and the legacy `th` rule matches them.
  - **There is one accent, and two different things are measured against it.** `--accent` is the *text* blue and clears 4.5:1 as text on `--bg` and `--bg-raised` in both schemes. `--tint`/`--tint-fg` is the fill-and-label pair a filled control wears, and in dark it is a different, deeper blue, because no single one does both jobs — `#4a9bff` carries white at 2.8:1. Where the browser exposes the operator's own accent, `--tint`/`--tint-fg` and everything mixed from `--accent-source` (the ring, the selection wash) switch to it; it is taken as a **pair**, because `AccentColorText` is specified as the colour of text placed on `AccentColor` and that is the only thing keeping a Graphite or Yellow accent legible under its own label. `--accent` is deliberately left alone — nothing guarantees an arbitrary accent reads as body text on a card. The `@supports` test names the whole `color-mix(in oklab, AccentColor …)` expression rather than the keyword alone: the two features shipped years apart, and a browser with one and not the other would leave `--ring` invalid at computed-value time, which is a focus ring in `currentColor` — visible, wrong and silent. `Highlight`/`HighlightText` was the other candidate and is rejected: engines return the selection *wash* there rather than the accent, and a white label on a pale wash is the failure this split exists to prevent.
  - **One focus treatment, stated in one place.** `@layer base` draws `outline: 2px solid var(--ring)` at 2px offset on everything focusable, and the legacy sheet no longer sets `outline: none` on `input:focus` — that suppression is what made a *second* treatment necessary, and it is why a button and the input beside it used to wear different rings. `--shadow-focus` is gone with it; a second way of saying this is how the two drifted apart. A component may override the ring's **colour** and nothing else, which is how `Button` keeps `--ring-danger` on the one control that cannot be undone, and why no component in the kit states an outline width or offset.
  - **Tokens.** Colour and type as above, plus: `--motion-fast|base|slow` (120/180/240ms — a control answering the pointer, something arriving or leaving, something travelling a distance) and `--ease-standard`/`--ease-entrance`; `--control-h` (32px, the floor for anything clickable) and `--control-h-lg` (36px, a button or a text input), stated as `min-h-[var(…)]` so a control keeps its box when its content changes; `--ring`/`--ring-danger` (the focus halo, at 45%) and `--shadow-press` (inset, so a pressed control recesses without moving); `--selection`, the accent wash behind selected text, at an alpha low enough that `--fg` keeps its own contrast whatever accent it turns out to be; `--ok-line`/`--warn-line`/`--danger-line`/`--accent-line`, each tone at 40%, for an *edge* that has to say which tone without outshouting the text it annotates — full strength stays for a conditional warning, the tint is for anything permanently on screen; `--fill-hover`/`--fill-active`, a neutral wash at 8% and 14% of `--fg`, translucent rather than a hex pair because it lands on three different surfaces and has to darken a light one and lighten a dark one — every opaque token in the palette is within 2% of `--bg-inset` in light mode and reads as no change at all. The shell adds three of its own: `--sidebar-w` (14rem, swapped for `--sidebar-w-rail` at 3.5rem by `[data-sidebar="collapsed"]`) and `--toolbar-h` (52px, a floor rather than a height — see the shell notes below). `--canvas-dot` is the workflow canvas's ground, and it is a token rather than the `color-mix` written into the utility that reads it: Lightning CSS emits a fallback declaration for a `color-mix` it cannot resolve, and that fallback is the *first operand at full strength* — a grid of solid `--fg` dots on any browser without it. Behind a `var()` it gets the `@supports` pair every other translucent token here gets. Eight named utilities: `hatched`, `mono`, `ui-transition`, `skeleton`, `sheet-enter`, `dot-grid`, and `app-drag`/`app-no-drag` for Window Controls Overlay — named rather than written as arbitrary values because the property is `-webkit-app-region`, which has no unprefixed spelling that ships anywhere.
  - **Motion is explanation.** `ui-transition` is the one transition an interactive surface wears; it deliberately omits `transform` and `width`, because a control must not move or resize between its states. Nothing loops except `Spinner` and `skeleton`, both of which stay legible frozen — `@layer base` flattens every duration under `prefers-reduced-motion`, and that blanket is not to be defeated with a `!important` or a JS-driven animation.
  - **`SegmentedControl` is how a short, fixed set of choices is offered, and `Icon` is the app's only glyph set.** The control is a radiogroup with a roving tabindex — one tab stop for the whole thing, arrows moving *and* selecting, focus following selection back so the next arrow press announces the right option. Both states carry a border and the same font weight, because a chip that gained either on selection would shift every segment beside it. `Icon` draws every glyph in a 16×16 box and sets the stroke attributes on the `<svg>`, so nothing can arrive a half-weight heavier than its neighbour; a glyph that is genuinely a filled shape cancels the stroke locally. Icons are decorative by default and only take a `title` where the glyph is the whole message — an icon announced beside the label it duplicates is noise. The set covers the seven panes plus disclosure, status and appearance, and the shell's own two (`sidebar`, `search`); a new destination needs a glyph here before it needs a row in `panes.ts`.
  - **`Sheet` is a native `<dialog>`, and that is a correctness decision.** `showModal()` gives the top layer, the inert background, the focus trap and Esc-to-dismiss from the browser; a hand-rolled overlay would be a hand-rolled focus trap, which is the part that silently stops working the day someone adds a control to the footer. Three rules follow from using the element rather than imitating it: it is always rendered and never conditionally mounted, because mounting in the same commit that calls `showModal()` is a race; nothing sets `display` on it, because a `display` utility outranks the UA's `dialog:not([open]) { display: none }` and leaves a closed sheet lying across the page; and `cancel` is prevented so Esc goes through `onDismiss` and React's `open` stays the single source of truth. It takes **one** default action and Cancel, and a `danger` sheet opens with Cancel focused — `showModal` would otherwise land on the first focusable thing, and one Return on a destructive confirmation is not a confirmation.
  - **What a new component owes.** Five interaction states — rest, hover, active, focus-visible, disabled — with **no layout shift between them**, and a hit target of at least `--control-h`. Where two class strings could set the same property under the same variant, both go in the same `Record<Union, string>` entry: split across a shared string and a per-variant one, the winner is Tailwind's internal sort order rather than anything written down (this is why `Button`'s focus outline colour is per variant). Those states are guarded with `not-disabled:` rather than `enabled:`, and that is what lets `ButtonLink` — a button that is a destination, so ⌘-click and middle click still work — share `Button`'s one `VARIANT` map: `:enabled` matches form controls and nothing else, so on an `<a>` every hover and press state would emit and never match, which is a filled control that does not answer the pointer. Verify a variant spelling in the emitted CSS rather than assuming it; Tailwind emits nothing for one it does not know, silently. And the four states that are not interactions — empty, loading, error, stale — are designed, not left to a spinner: `Empty`, `Skeleton`/`SkeletonText`, `Notice`, `Field`'s `error`.
  - **`Field` is finished; do not fork it.** Label, `hint`, `error`, `unit`, `prefix`, `disabled` and the mode-picker-plus-value row (`LimitField`) are all props. A context carries `aria-describedby`, `aria-invalid` and `disabled` down to `Input`/`Select`/`Textarea`/`Switch`, so a hint written as a prop actually reaches the control — children are never cloned, because several Fields hold a fragment. That context is **exported**, and `ListRow` provides it rather than carrying a copy, which is what makes a control behave identically in a grouped row and in a Field. Everything the context supplies is a default the control's own prop overrides. Width is the one thing no control states: two width utilities on one element resolve by stylesheet order, not class order — so a caller that needs a narrow input puts the width on a wrapper, never on the control. **That rule is not about width, and the density pass measured the general case**: Tailwind emits a numeric utility's values *ascending*, so on any element that concatenates a component's own class string with a caller's, the larger value wins whatever the caller wrote. `Field`'s root is `mb-3.5` and `CardTitle`'s is `mb-3`, and `.mb-0{` is at byte 10980 of the emitted sheet against `.mb-3{` at 11231 — so a `className="mb-0"` on either is a **no-op**, and there are three landed `CardTitle className="mb-0"` call sites that render 12px of margin and read as though they do not. A caller that has to cancel a component's own spacing does it on a wrapper (`-mb-3.5`), the same move the width rule already asks for, and verifies it in the emitted CSS rather than assuming.
  - **`ListGroup`/`ListRow` is the grouped inset list, and `Switch` is the control that usually sits in one.** Label left, control right, hairlines between rows, a rounded box, a footnote under it. The box deliberately does **not** clip its overflow: rows carry no background of their own, so a hairline never reaches a corner and nothing needs `overflow-hidden` — which matters, because a caller with a marker in the gutter (the settings page draws an edited rail there) would have it clipped away. A row is inert and has no hover tint: every interaction state belongs to the control inside it, and a row that lit up under the pointer would be claiming to be clickable across a width where only the 38px switch is. `Switch` *is* its track, so the focus halo hugs the pill rather than a padded box around it, and the hit target comes from an `::after` overlay stretched to `--control-h` — a target the pointer hits and the layout never sees. `Toggle` is the same switch with its label on the left, for a stack of Fields with no right edge to align against.
  - **Numbers behave.** Every figure `tabular-nums` (`Stat`, `Th`/`Td` with `num`, `Meter`, `mono`) so it cannot jitter as the page polls, units attached, and an unknown reading says so — the hatched indeterminate meter, never a 0% bar. Reserve space for anything that streams in.
- `better-sqlite3` is a native addon — it must stay in `serverExternalPackages` in `next.config.ts`, and the Dockerfile's `deps` stage carries the build toolchain for it.
