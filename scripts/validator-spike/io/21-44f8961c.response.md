The task reports a single symptom: merge-queue rows never get their status updated, even when a merge is retried and succeeds. The diff attacks exactly that symptom from both ends that could cause it. First, `src/lib/git.ts` is changed so `git()` never rejects — a child that fails to start (`ENOTDIR`, `EMFILE`, etc.) now resolves with a failed `GitResult` instead of throwing, with a new `git.test.ts` case exercising the `ENOTDIR` path. Second, `src/lib/mergeQueue.ts`'s `drainRepo` wraps its per-row work in try/catch so a thrown error can no longer strand a row on `landing`/`resolving` forever — it is instead marked `failed` with an honest "not known whether the merge went through" message, and `startWorker()` is invoked from the `finally` so the loop keeps moving to the next repo. This is covered by a new `mergeQueueDrain.test.ts`, which sets up a real git repo and SQLite DB, breaks the `land` event via a trigger, and asserts the row ends up `failed` (not stuck), the next row is `skipped`, and a subsequent independent run still lands normally. Third, `src/app/branches/page.tsx`'s polling is fixed so the queue panel keeps refreshing even when idle (previously gating the interval on "something was active" made an idle queue an absorbing state that only a same-tab Land press could break out of) — this is the direct "status never updates" mechanism the task names. `src/app/api/branches/queue/route.ts` is switched to `jsonNoStore` to stop any caching layer from serving a stale answer.
