SessionFlow — a mockup of a proposal that argued against what was asked for

The request was “a new tab on the left that records what the session touched and creates a VISUAL FLOW TYPE representation of what the flow touched and changed”.

proposals/SessionFlow/ recommends not building that graph. Its finding is that the only relations in run_events are “a tool touched a file” (a bipartite star round about a dozen tool names) and “a sub-agent was delegated to” (a two-level tree), so the honest picture is a table: a touched/changed reconciliation as a sorted list with counts, inside the run page’s existing tab — not a tenth pane, not a sixth tab, not a canvas.

So the left-hand half of this page is the recommended thing, drawn in the place the proposal puts it. The right-hand half is the refused graph, drawn at the same scale from the same fake run, because “does it become an unreadable hairball” is the question the proposal exists to answer and it should be looked at rather than taken on trust. Nothing here is built beyond the list — and the list itself is the one thing on this branch that is built, in src/components/RunTouches.tsx.

Throwaway sketch, 2026-08-27, against commit 7b158e4. Colours copied out of src/app/globals.css by hand, so they drift the moment that file changes. Every path, count and cost below is invented.

Rejected alternative: the flow graph, same run, same scale

This is what was asked for, drawn honestly rather than flatteringly. The cap prunes the wrong way. capGraph (knowledgeGraph.ts:719-722) drops nodes by degree, largest first — it keeps hubs. Here the hubs are the dozen tool names carrying no information, and the files that answer the question are what gets dropped. The one nearly-generic piece of graph plumbing in this app is generic in the wrong direction for this data.
What a node is
A file path, pulled out of a stored tool call with json_extract(payload,'$.input.file_path') and relativised against COALESCE(work_dir, folder) — or, in the bipartite reading, a tool name from $.name. There is no other kind of entity in run_events.
What an edge is — and why each candidate collapses
tool → file: bipartite with ~11 members on the left. Every file has degree 1–3; every tool has degree in the hundreds. A dozen stars, saying “this run did a lot of Reads”, which toolComposition.ts already prints as a number.
file ↔ file, same work cycle: a clique per cycle. A cycle touching 40 files is 780 edges by construction, not because the run was busy. This is the hairball, and it is the one to look at.
file → file, in sequence: one edge per adjacent pair of calls, so the edge count equals the call count and the only real structure is time. Time is an axis, not a topology — drawn on an axis it is the file × work-cycle grid the proposal defers rather than refuses.
How touched is told apart from changed
Touched = a tool call named the path, and only that: this app records a tool result only when the tool failed (orchestrator.ts:7343-7344), and a failure row carries no id joining it back to its call. So a touch means attempted. Changed = the path appears in the branch diff. The list carries that hedge once, in its header. An edge cannot carry it at all: a line is drawn or it is not, and a hedge has nowhere to live on it.
The fourth group — changed, never named by a tool call — is the interesting one and the graph structurally cannot show it. A file written by a Bash that named no path has no event, so it has no node. In the list it is the group that leads.
What is invented here, because the proposal does not say:
  • The scale. The proposal is explicit that the distinct-file count of a real run is unmeasured — /data is empty and no run_events row was ever quoted. It gives bands instead: under ~50 a graph is a dozen dots; over ~500 it is a hairball; and 13-validation.md names 200–800 with directory clustering as the band that would overturn its own refusal. The large run here is drawn at 431 distinct files over 31 work cycles, chosen to sit in the middle of that band — the case where the answer is least obvious. The small run is 18 files over 3 cycles. Both are fake.
  • Every path, count, cost and file name. Generated from a fixed seed. The paths imitate this repository’s shape so the picture reads plausibly; none of them was read from disk.
  • The run header, the diff numbers and the toolbar buttons are approximations drawn from memory of the real page, not copies of it.
  • What the sidebar’s tenth row would have been called. The request said “a new tab on the left”; “Session flow” is this mockup’s guess at a label for a row the proposal says cannot exist.
What is not invented: the four group labels, their order, the footnotes, the header sentence and all three empty-state wordings are the strings in src/components/RunTouches.tsx at 7b158e4. The tab strip is the real five labels in their real order.
