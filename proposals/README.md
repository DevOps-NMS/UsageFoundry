# Proposals

Design proposals that are not yet decisions. A directory here surveys one
question, gives every candidate its strongest honest case, and ends with a
single recommendation and the fact that would overturn it. Nothing in here
describes the code as it stands — `docs/agent/` is where the invariants that
have already been decided live, and `docs/` proper is what an operator reads.
A proposal is promoted by implementing it and moving its reasoning into those
two places; until then, treat every file here as an argument rather than a
record.

Every factual claim carries a `path/file.ts:42` reference or the command whose
output it quotes. A claim that could not be verified says "assumed" in the
sentence that makes it.

| [UnattendedOperation](<implemented - UnattendedOperation/README.md>) | This app's premise is that a run works while nobody watches. Nothing it produces reaches an operator who is not looking at the page. What should, by what route, and what does each route cost — in money, in code, and in what leaves this machine? | **Promoted**; steps 1, 2 and 4a shipped — `logLifecycle` routes `needs-review`, `blocked` and `failed` at `warn`, `run.error` carries the 429 ladder's `retrying` and `usage_limit`, and the outbound webhook posts six signed fields per ending that wants a person, records every attempt in a bounded table and reports the count since the last success on `/api/status` — with the invariants moved to `docs/agent/run-lifecycle.md` and the operator's half to `docs/install.md`. **Step 4b, the in-app digest, was deliberately not built**, and it is still the better second build for the comparison's own reason: the webhook subscribes, so the ending it cannot reach is the one that leaves no event, and the dead container login is still readable only by looking. All five refusals below stand. What follows is the argument as it was made, kept for the reasoning rather than edited into a record of what shipped: nine endings and waits enumerated from the code — `needs-review`, a refusal park, the 429 ladder, a guard trip, a blocked dependency chain, a merge queue on a dirty checkout, a halted workflow instance, a dead container login, and a boot reconcile that closed runs — and **none of the nine then had any route to a person other than the operator opening a page**. The spine of the comparison is that **the two interrupt rows need opposite mechanisms**: the 429 ladder leaves no state and is only reachable by subscribing, the dead login leaves no event and is only reachable by reading, so nothing scores full marks on the highest-weighted criterion. **Refused by name:** web push (the endpoint is chosen by the browser vendor, reaching a non-host device means exposing the app past `docker-compose.yml:62`'s loopback bind, and RFC 8291 is 300-500 lines of hand-written crypto whose every bug returns 201 and delivers nothing), email as a default (the only channel with no zero-dependency route, and the only one whose usefulness is proportional to its leak — an interrupt can be content-free, a digest cannot, so a useful digest email is the install's work log in plaintext), an MCP tool as scoped (forty lines of tool and a fifth credential shape on the one route `middleware.ts` exempts), the orchestrator chat (paying a model to proxy a `SELECT`), and a chat bot that can act (`docs/agent/run-lifecycle.md:48` forbids a bulk control from answering `needs-review`, and the app has already decided that a decision is taken where the operator can see what they are deciding about). Unverified: **every** frequency — `ls -la /data` is `Permission denied`, the stale in-checkout database has zero `runs` rows and one `ops_events` row, so no park, ending mix, queue depth or dwell time exists anywhere readable and every latency claim here is a mechanism claim; and nothing was ever delivered — no provider contacted, no webhook fired, no egress from this container tested |
| [GrowthLimits](GrowthLimits/README.md) | What breaks first as this install grows — more concurrent runs, more repositories, more months of history — and which ceiling is worth raising before it is hit? | Open; **thirty-one bounds catalogued with file, line and what happens at each one, and the answer to the first half of the question is "nothing"**: zero of the thirty-one fail, throw, corrupt or lose data, and zero numeric bounds are reachable within thirty days at the measured growth rate of ≈88 transcript files and ≈69.6 MB per day. So the recommendation is **against raising any ceiling** — instrument two axes and take one reading. Report the cold transcript scan's duration on `transcriptCacheStats()` and `/api/status` (measured cold **2,985-3,041 ms** against warm **82.5-88.9 ms**, a factor of 36, paid on the first `/api/usage`, `/api/status`, pre-cycle guard or `assistRefusal()` after every restart because the cache is process-local), with no threshold and no warning colour because a 6-second cold scan is a fact about a corpus rather than a fault; then make `walkRepo` return `{files, partial}` so the file price list confesses a short walk, which matters not because the bound is near — measured occupancy is 9.8% and 6.2% on the two readable repositories — but because it is one of only **two** silent truncations in the survey, its reader is an agent frozen with the notice for the life of the run, and the identically-named, identically-justified `MAX_WALK_ENTRIES` in `retention.ts` already returns `partial` and its docblock argues that a bounded walk must say when it stopped. The reason nothing breaks is **the retention defaults**: `eventRetentionDays: 30`, `checkoutRetentionDays: 7` and `transcriptRetentionDays: 30` make three of the four history-growing costs plateau, at ≈2,650 files, ≈2.1 GB, a ≈6.4 s cold scan and cache occupancy of ≈218,000 of 500,000, so `TRANSCRIPT_CACHE_MAX_ENTRIES` is unreachable under the shipped default. Four bounds carry a docblock naming a growth problem in the past tense — **the app is not approaching its ceilings, it has been walking away from them** — and the two costs that would have multiplied with `maxConcurrentRuns` when #68 was written now multiply with neither. `maxConcurrentRuns: 4` is the only non-refused raise and is **deferred on one `docker stats` reading**: `settings.ts:765` says having a ceiling was "Measured, not reasoned" and `settings.ts:205-232` says where it sits rests on ≈1.5 GiB per work cycle, which "is reasoned rather than measured"; near 1.5 GiB and 4 is right, near 600 MB and two thirds of a 10 GiB budget is unused. **Refused by name:** raising the four-mount ceiling (there is no cap in `src/` to raise, `parseMounts` is forbidden from gaining one, and #77's silent fifth slot now refuses the boot, is documented at `docs/install.md:493-505` and unit-tested), hardening the SQLite write path (`SQLITE_BUSY` needs a second writing connection the server lock exists to prevent, and checkpoint starvation needs a long-lived reader — `grep -rc "\.iterate(" src/` sums to **0**, which closes the class more firmly than a load test), and putting `request_log` on a time horizon (rows were chosen over an age deliberately, and the cap is a term in the security argument that keeps `/api/mcp`'s 401 outside `auditMutation`). Seven open issues reconciled with a verdict each and **nothing filed, closed or commented on**; ten distinct sub-issues across them no longer reproduce at HEAD. Two findings correct a neighbour rather than restating it: peak RSS is **323-372 MB** at 973.8 MB of transcripts, not the 1:1 #68 measured, because `SCAN_CONCURRENCY = 12` bounds the fan-out; and a polling browser writes **no** audit rows at all, because `auditMutation` wraps 33 exports plus `/api/mcp`'s POST and **zero** GET handlers, so GapRegister G4's rate driver is agent traffic rather than page loads. Unverified: **every concurrency figure** — Docker is unavailable here, no load test was run, no second run was observed, and the per-child memory number the whole axis rests on cannot be taken from inside the process; **all run history** — `/data` is `Permission denied` and the stale in-checkout copy holds 0 `runs`, 0 `run_events`, 8 `request_log` and 1 `ops_events` row, so every growth rate here comes from the transcript corpus as a proxy; `readCountsFor`'s `json_extract` at a real row count, where 8.29 ms against an empty table is a floor and the project's own 38 ms against 131,572 rows implies ≈950 ms of blocked event loop at `MAX_WORKFLOW_NODES = 25`, the largest synchronous cost found; and **anything about more than two repositories**, n = 2 mounts of one repository each, two orders of magnitude below `MAX_FOLDERS_PER_MOUNT = 400` |
